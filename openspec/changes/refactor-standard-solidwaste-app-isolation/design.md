## Context

数据库拆分已验收并合入 `495aa3e3`。`MaterialClient.exe` 仍同时 `DependsOn` Standard 与 SolidWaste 模块，启动时迁移两套产品 Context。称重界面在 `MaterialClient.UI` 与 `MaterialClient.AttendedWeighing`，宿主项目本身只保留启动壳。Urban、Recycle 已经是独立 WinExe。固废现场现在和标准端共用 `MaterialClient` 安装身份、快捷方式和自启动。

相对路径的数据库和附件都以 `AppContext.BaseDirectory` 为根。新 exe 若换目录，会在新目录生成空库，并找不到原来的照片。

## Goals / Non-Goals

**Goals:**

- Standard 与 SolidWaste 各有一个可独立构建和安装的 WinExe。
- 每个宿主只迁移自己的产品 Context，并固定自己的产品身份。
- 旧固废数据目录可以被新固废宿主直接打开，不复制、不删除数据库和附件。
- 标准端安装不接管固废现场的快捷方式和自启动。

**Non-Goals:**

- 不拆 SQLite 文件，不把内核称重和运单改成两套物理表。
- 不复制有人值守界面，不重写称重、合同、主数据或设备流程。
- 不支持两个宿主同时写同一个数据目录。
- 不做进程内热更新。Urban / Recycle 的宿主和安装包不改。

## Decisions

### 1. 标准宿主保留现有程序，固废新增宿主

`MaterialClient` 继续作为 Standard WinExe，去掉对 `MaterialClient.Common.SolidWaste` 的项目引用和模块依赖。新增 `MaterialClient.SolidWaste` WinExe，引用 Common、内核 EF、`MaterialClient.Common.SolidWaste`、UI 和 AttendedWeighing，不引用 `MaterialClient.Common.Standard`、Urban 或 Recycle。启动壳按现有 `MaterialClient` 的 Program / App / Module 形状新增，不把 AttendedWeighing 的 AXAML 拷进新项目。

另一方案是把两个入口留在同一个 WinExe 里用参数区分。那样仍是一次发布，固废变更还会带着标准端走验收。

### 2. 产品身份由宿主固定

Standard 宿主只允许 `WeighingMode.Standard` 和标准产品码。SolidWaste 宿主只允许 `WeighingMode.SolidWaste` 和固废产品码。授权窗口由宿主传入这一个模式，不再列出另一个产品。

启动读到的默认称重模式若属于另一个产品，宿主记录日志后退出。它不改 `DefaultWeighingMode`，不删授权记录，也不进入称重。新安装没有该设置时，宿主只写入自己的模式。

### 3. 启动迁移按宿主切开

Standard 宿主：内核迁移，然后 `StandardDbContext`。不迁移 SolidWaste、Urban、Recycle，也不执行固废扩展回填。

SolidWaste 宿主：内核迁移，然后 `SolidWasteDbContext`，然后 `ISolidWasteExtensionStore.BackfillMissingAsync`。不迁移 Standard、Urban、Recycle。

这替换 `refactor-standard-solidwaste-schema-isolation` 里“标准宿主迁移两套产品 Context”的启动规则。归档时后归档的变更须保留本规则。

### 4. 显式数据目录承接旧安装

新增可选配置 `Client:DataDirectory`，值为绝对路径。为空时数据根仍是 `AppContext.BaseDirectory`。`DatabaseConnectionStringFactory` 和附件相对路径都使用这个根。配置的目录不存在时启动失败并写日志，不回退到 exe 目录新建空库。宿主不搬移、不删除已有数据库和附件；升级前的恢复备份允许复制数据库。

全新安装使用各自的安装目录。固废升级旧现场时，把 `Client:DataDirectory` 指到现有 `MaterialClient` 目录。

### 5. 安装身份分开

新增 `MaterialClient.SolidWaste.iss`，使用新的 AppId、显示名和默认目录 `{autopf}\MaterialClient.SolidWaste`。卸载不删除数据库、附件目录和被 `Client:DataDirectory` 指向的旧目录。

标准安装包不安装固废 exe。它只在自己的自启动项指向 `MaterialClient.exe` 时更新该路径；当前自启动目标已是 `MaterialClient.SolidWaste.exe` 时不改写。

两个宿主使用不同的产品单实例互斥名，同时对规范化后的实际数据库路径持有跨产品排他锁；无法取得锁时退出。接续旧现场前还须确认旧 MaterialClient 进程已退出，因为旧程序不认识新锁。同一数据目录同时运行两个宿主不作为支持场景。

### 6. 历史行保留

内核称重和运单继续按原模式保留。宿主只把新记录写成自己的模式，不删除另一模式的历史行，也不因为固定产品身份而把这些行过滤掉。

### 7. 接续现场配置，产品身份由宿主最终约束

Client:DataDirectory 仅从新宿主自身配置读取，先确定数据根；旧目录配置不得递归改变该根。配置优先级从低到高为：新宿主 appsettings.json 默认值 → 旧数据目录 appsettings.json → 旧数据目录 appsettings.secret.json → 新宿主 appsettings.secret.json 的显式覆盖。目录相同时去重加载。环境配置覆盖若保留，必须在实现中显式列出并测试优先级，不能暗中替换现场配置。

旧现场的服务端地址、连接字符串及其他现存外部配置按上述规则接续，数据库设置、授权与会话继续从原库读取。身份和允许模式是宿主约束，不能被旧配置或秘密配置改成另一产品。配置只在内存组合，不复制覆盖原配置，不将秘密写日志。指向其他绝对数据库路径时，以最终解析的真实数据库为预检、锁和备份对象。

### 8. 区分首次安装与旧现场接续

配置 Client:DataDirectory 即表示接续模式；安装器为旧 Standard 原地升级写入其原目录，为固废迁移写入所选旧目录，不能把升级当全新安装。接续要求目录、最终数据库文件均已存在且可读，以只读、不创建方式检查 schema、迁移历史和已保存产品模式。存在空目录、缺库、损坏库、未知版本、缺失或冲突的产品身份时均停止并显示可操作原因，绝不调用 GetOrCreate 设置或生成新库。

首次安装仅在未配置接续目录且默认目标无现有数据库时创建新库。默认目标已有库也必须先通过相同的旧库预检，不能绕过身份和结构检查。

首期支持基线是 495aa3e3 所代表的已完成数据库拆分版本：实施时固定 Kernel/产品迁移清单与必要结构的识别规则，并收录 Standard、SolidWaste 样本。更老版本先使用已验证的数据库拆分版本升级，再进入本次应用拆分；不承诺任意历史库直接升级。未列入已验证清单的更高版本也拒绝降级打开。

### 9. 写入前完成身份预检，启动阶段固定

启动顺序为：解析宿主与现场配置 → 确定真实数据库路径并取得产品/数据库排他锁、确认旧进程退出 → 只读结构及产品模式预检 → 为已存在的支持库创建并验证恢复备份 → 执行内核及本产品迁移/回填 → 完成授权与登录 → 接续启动入口并启动业务、设备及后台工作。

ABP 的配置与容器构建可先执行，但所有会写库、回填、修复注册表或启动设备/后台工作的初始化必须延迟到预检通过。拒绝路径允许诊断日志，不允许修改原库、配置、授权、自启动和快捷方式。新安装写入自身模式前不启动称重业务。测试必须观察真实启动阶段，不只单测模式判断函数。

### 10. 自启动和快捷方式由产品拥有

Standard 保留注册表值名 MaterialClient，SolidWaste 使用 MaterialClient.SolidWaste。安装器、运行期 WindowsAutoStartService 和设置同步都使用同一宿主身份配置；启用、禁用、检查仅作用于自己的项。

旧固废接续在数据库预检、迁移与授权成功后执行一次：只有旧 MaterialClient 项或快捷方式目标规范化后确实指向所选旧安装的 MaterialClient.exe 时，才把它转交到固废入口并保留原启用状态。先写入验证新入口，再清除匹配的旧入口；重复运行幂等。指向其他安装的项不修改，无法确认归属时明确报告，不自动删除。旧安装卸载不得删除新产品拥有的入口。

标准安装器覆盖旧目录前也要识别固废身份；若为固废，拒绝标准升级并指引固废安装包，不能先覆盖可执行文件再靠启动退出兜底。卸载固废只清理其自己拥有的启动入口，保留原库和附件。首次接续失败则不提交启动入口切换，旧包与恢复备份保留。

### 11. 恢复以已验证程序、数据和配置快照为单位

升级前旧进程停止且应用排他锁取得后，对实际数据库制作一致性备份并校验可读性，记录原安装包版本、配置与启动入口快照；不能只复制可能缺少 WAL 内容的主 db 文件。秘密快照维持原访问权限，恢复清单不输出秘密。迁移成功、产品冒烟通过后才完成入口交接；备份保留到规定验收完成。

升级失败时保持业务停用并报告恢复路径，不自动在部分迁移库上启动旧包。回退需恢复匹配的程序、数据库、配置与入口并验证。新版本已经产生业务数据时，不自动覆盖恢复旧快照；保留新库，先完成新增数据对账与恢复方案，防止静默丢单。本次不提供任意旧包直接读取新库的降级保证。

### 12. 验证矩阵与交付条件

覆盖 Standard/SolidWaste 全新安装、支持基线升级、原附件与授权/配置接续、历史查询与新建业务、自启动启停及同机不同目录并存；覆盖错产品、缺库、未知/损坏结构、迁移中断、重复运行、旧进程占用、入口交接失败和成套恢复。加入各宿主引用/迁移范围检查，以及共享路径修改对 Urban/Recycle 的回归。

自动检查固定测试样本、命令和证据位置；目标 Windows 环境验证安装、自启动与核心业务。硬件与现场证据缺失时明确未验证，不以构建或任务勾选替代验收。新写入后的回退对账规则须有失败场景测试，不承诺全自动无损降级。

## Risks / Trade-offs

- [数据目录指错会打开另一套库] → 目录、已有数据库、支持的结构和产品身份均在写入前检查；不符合就停止，详见决策 8、9。
- [标准安装包把固废现场的自启动改回去] → 标准安装包看到自启动目标已是固废 exe 时不改。
- [先归档数据库 change 会把启动规则写回“一个宿主迁两套”] → 本 change 的 delta 是最终规则，归档顺序以本规则为准。
- [固废明细视图仍在共享界面项目中] → 标准宿主不注册 SolidWaste 模块，写入走现有空实现；固废宿主注册真正的扩展存储。

## Migration Plan

1. 先加入数据目录解析和固废宿主，标准宿主仍可构建。
2. 去掉标准宿主的 SolidWaste 依赖和迁移，加上模式不符即退出。
3. 增加固废安装包，并让升级配置指向旧数据目录。
4. 用一份已有固废库验证：固废宿主能完成自己的迁移并读到原附件；标准宿主对同一目录退出且不改模式。
5. 按决策 11 的成套恢复方案处理失败，不能仅重装旧包并直接打开未经兼容验证的新库。

## Open Questions

研究记录里的“同机并存”和“是否共享数据目录”在本设计中关闭：只有不同数据目录的两套安装可以同时存在；同一个目录只由匹配其默认模式的宿主使用。
