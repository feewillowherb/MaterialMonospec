> 知识状态：对象划分 `INFERRED`（从四页和两跳上传归纳）。表名、列类型、是否拆表都是 `PENDING_VALIDATION`。

## 1. 候选对象

名称只表示业务对象，不是最终表名。

| 对象 | 页面 | 主要写入方 | 市接口对照 | 备注 |
|------|------|------------|------------|------|
| 车辆信息池 | 车辆管理 | Web | §2.6 的车牌、运输人、电话；皮重不进 §2.6 | 未启用或未命中时，工控上传不能算出净重 |
| 合同 | 合同管理 | Web | §2.4 | 合同编号供运输清单引用 |
| 合同产品明细 | 合同管理 | Web | §2.4 `contractDetail` | 可与合同同一行的 JSON，也可拆表。见 Q2 |
| 日产量 | 生产管理 | Web | §2.5 | 与运输清单净重没有加减关系 |
| 运输清单 | 运输清单 | 工控写入毛重、车牌、时间、现场照片引用；平台写入皮重和净重；Web 补合同、产品、收货 | §2.2 | 工控上传的落点 |
| 同步状态 | 各页「上报状态 / 发送时间」 | Worker | 本地 | 可以是业务行上的列，也可以是尝试历史。见 Q4 |

附件文件可以继续走现有 Uploads 目录，用业务 Id 区分路径。附件元数据归 Recycle 侧记录，是否复用城管附件表见 Q3。

厂标识 `pointNumber`、`dischargePointNumber` 来自配置，不做成每行业务字段，除非讨论后改口。

## 2. 运输清单上已能对上的量

这些是字段职责，不是列名或精度。

| 职责 | 谁写入 |
|------|--------|
| 车牌 | 工控 |
| 毛重 | 工控 |
| 称重或出货时间 | 工控 |
| 现场照片引用 | 工控上传后的平台附件 Id |
| 皮重 | 按车牌从车辆信息池带出 |
| 净重 | 平台计算：毛重 − 皮重 |
| 合同、产品、卸点、收货时间、收货凭据 | Web 后补 |

一车一单还是一次称重一单，见 Q1。本地工控的 `WeighingRecord` 只作为来源记录 Id，不把客户端 SQLite 表结构原样搬到 SQL Server。
