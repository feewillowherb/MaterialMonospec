# UrbanManagement Entity 语义化分析 — 调研总览

> **日期**：2026-09-02  
> **范围**：`repos/UrbanManagement/src/UrbanManagement.Core/Entities/` 及关联 EF 映射、Service 用法  
> **类型**：代码考古 / 数据模型现状评估（非 OpenSpec 提案）

## 结论摘要

UrbanManagement 当前共 **10 个持久化 Entity**（含 `UrbanPassageRecordAttachment` 同文件定义）。整体呈现 **「新旧并存、类型纪律不一致」** 特征：

| 维度 | 现状 | 严重程度 |
|------|------|----------|
| 可空属性占比 | 核心实体 61%–94% 属性为 nullable | 中–高 |
| 枚举 vs `int` | `SyncStatus` 已在称重侧 enum 化，通行/遗留同步仍用 `int?` 魔法值 | 高 |
| 字符串代替枚举 | `SiteType`、`VehicleType`、`DeviceType`、`Status` 等大量自由字符串 | 中 |
| 业务语义命名 | `BuildLicenseNo` / `AccessCode`、`ProId` 类型不统一、遗留 `GovSyncData` 全字符串化 | 中–高 |
| 正向范例 | `UrbanPassageRecord` 的 `PassageSource` / `UrbanInOutType` / `UrbanSiteType`；`AttachmentFile.AttachType` | — |

**核心判断**：问题并非「nullable 用得多」本身，而是 **nullable + 弱类型（string/int）叠加**，导致领域边界模糊、Service 层充斥魔法值（`0/1/2`）、跨实体字段语义不一致。遗留表 `GovSyncData` 与新版 `UrbanWeighingRecord` / `UrbanPassageRecord` 形成两套平行模型，加剧理解成本。

**已确认 refactor 方向**（2026-09-02，详见 [04 §2](./04-改进建议与优先级.md#2-已确认决策)）：

- **执行**：SyncStatus enum + API 字符串名；RetryCount 统一；ProId required Guid；SiteType 仅改类型；`EnableSync`→`IsSyncEnabled`；移除 FdBuildLicenseNo；**Legacy WIP 不入库**；**停止 GovSyncData 双写**。
- **Intake**：[INT-005](../intake/2026-09/INT-005-urban-entity-accesscode-rename.md)（AccessCode 挂起）、[INT-006](../intake/2026-09/INT-006-legacy-gov-sync-reimplementation.md)（Legacy 后续重构）。
- **挂起 / 不做**：BuildLicenseNo→AccessCode（INT-005）；VehicleType/PlateColor。
