# 02 · 字段映射与缺口

## 1. 入站模型对照

| XiaoShanServe `mGovRequestWeight` | UM `UrbanWeighingRecordReceiveInputDto` / 实体 | 映射建议 |
|-----------------------------------|-----------------------------------------------|----------|
| `carNo` | `PlateNumber` | 直拷 |
| `carColor` | `VehicleColor` | 直拷 |

| `carType` | `VehicleType` | 直拷（字符串「大车/小车」） |

## 2. 硬缺口与已确认项

### 2.1 `ClientRecordId` 幂等键

Modern Receive **强制**非空 Guid，并以此去重。Legacy 报文无此字段。

| 策略 | 优点 | 风险 |
|------|------|------|
| **A. 每次 `Guid.NewGuid()`** | 实现简单 | 客户端重试产生重复称重行 |
| B. 确定性 Guid（如 UUID v5：`AccessCode|snapTime|carNo|deviceID|goodsWeight`） | 同报文重试幂等 | 字段碰撞 / 合法修正被当成同一条需约定 |
| C. 适配层本地映射表（旧主键 ↔ Guid） | 可控 | 又引入状态存储 |

**已确认（2026-09-03）：采用方案 A。**

- `LegacyGovSyncAppService` 每次构造 Receive 入参时 `ClientRecordId = Guid.NewGuid()`（非 Empty）。
- **不**做报文级幂等：同一地磅重复 POST → 多条 `UrbanWeighingRecord`（可接受）。
- 与挂起批迁（INT-007）分离：批迁仍为 `ClientRecordId = Guid.Empty`，见 [06](./06-XiaoShanServe历史数据迁移.md)。

### 2.2 拒收暂存表（临时，供开发补救）

**已确认（2026-09-03）：** 业务校验失败、无法写入 `UrbanWeighingRecord` 时，在 **UM** 写入一张**临时拒收表**，保留报文关键字段 + **图片 Base64**，供开发人员后期人工修复/重放；**不需要索引**。

建议形状（命名可改）：

```csharp
/// <summary>Legacy 入站拒收暂存（临时表，无业务索引）。</summary>
public class LegacyWeighingRejectStaging : Entity<Guid> // 或 AuditedEntity
{
    public DateTime RejectedAt { get; set; }
    public string? RejectReason { get; set; }      // 如「对接码未接入」
    public string? AccessCodeAttempted { get; set; }
    public string? FdAccessCodeAttempted { get; set; }
    public string? PlateNumber { get; set; }
    public string? PayloadJson { get; set; }       // 去图或含业务字段的 JSON
    public string? SnapImagesBase64Json { get; set; } // 图片 Base64 数组序列化；可很大
    // 其它便于修复的平铺字段可选：DeviceId、SnapTime、GoodsWeight 等
}
```

约束：

| 项 | 规则 |
|----|------|
| 落库位置 | **UrbanManagement**（与转换核心同仓）；**不是** XiaoShanServe SQLite |
| 索引 | **不要**建业务索引（含 AccessCode / PlateNumber / RejectedAt 等）；仅主键即可 |
| 触发 | `LegacyGovSyncAppService` 在拒收分支写入；仍返回旧版 `{ success:false, msg, code }` |
| 成功路径 | **不**写本表；只写 `UrbanWeighingRecord` + 附件 |
| 生命周期 | 临时；修复重放后可删行；非长期归档权威 |
| DI / 映射 | 按 `minimal-di`；禁止为纯映射注册 Service |

开放（实现时写入 design）：表名最终 CLR/SQL 名；Base64 单列 vs 多行子表（默认单列 JSON，简单）。

### 2.3 图片与文件：XiaoShanServe 不再落盘，权威在 UM

**已确认（2026-09-03）：** 切流后 **XiaoShanServe 本地不再落盘**（不再写 `FilesPhysicalPath/TempUpload/...`）。成功入站的图片与业务数据一律进 **UM**。

成功路径：

```text
snapImages[] base64
    →（UM）IFileService.SaveAndCompressImagesAsync / SaveAndCompressImageBytesAsync
    → AttachmentIds
    → ReceiveAsync → UrbanWeighingRecord + UrbanWeighingRecordAttachment
```

拒收路径：

```text
snapImages[] base64 → §2.2 拒收暂存表（保留 Base64）
（无本地 jpg 文件）
```

注意：

- AttachType：**已确认全部 `Lpr`(5)**（D9）；不再用 `UrbanPhoto` 作为 Legacy 默认。
- 权威存储 = UM `AttachmentFile` + 配置的 Storage 根；**禁止**双写 XiaoShanServe 磁盘。
- 切流（D11）：同机异端口，Serve 入口 **仅 HTTP 转发**到 UM，转发层也**不得**落盘。

### 2.4 `ProId` / 项目主数据

- 适配层**只**用报文 `buildLicenseNo` 查 UM `GovProject.AccessCode`
- **`fdBuildLicenseNo` 已停用：忽略**（D12）；不换码、不查凡东表
- 两码皆空，或城管码查不到项目 → **拒收** → §2.2 暂存
- `ProId = project.Id`，`ProName = project.ProName`

### 2.5 重量单位

Spec：`TotalWeight` = **千克**。Legacy `goodsWeight` / `grossWeight` 现网亦为 kg 语义 → 直接 decimal，**不要**再 ×1000。

## 3. ApiController 现行权重逻辑（须复现）

```text
goodsWeight → syncData.goodsWeight
若 grossWeight 有值且 > 0 → 覆盖为 grossWeight 字符串
```

UM Legacy 转换应对齐，避免与历史 XiaoShanServe 行为漂移。

## 4. 响应契约

XiaoShanServe 成功时大致：`{ success, msg, code: 200 }`（经 `JsonDate(result)`）。

UM Legacy stub：`code: 501`。

对外兼容：保持旧响应形状。拒收（含已写入 §2.2 暂存）仍返回 `success=false` + 明确 `msg`；**不要**因暂存成功而返回业务成功。

**鉴权（D10）：** Legacy `POST /Api/Post` **不需要鉴权**（AllowAnonymous / 与现网旧口一致的无登录态）。
