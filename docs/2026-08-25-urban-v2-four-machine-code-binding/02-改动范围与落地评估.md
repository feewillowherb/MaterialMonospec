# 02 — 改动范围与落地评估

## 1. 目标（已确认）

| 场景 | 结论 |
|------|------|
| **A. 多机并存（同时在线称重）** | **已选定**（继承 2026-08-06；上限升为 **4**） |
| B. 主备切换 | 不采纳 |
| C. 仅预登记 | 不作为本期方案 |
| D. 改写存量 5001 为多槽 | **不采纳**；5001 保持单机覆盖 |

选定方案：

- **新增 ProductCode（Urban V2）**
- 项目级 **设备1…设备4** 四槽（场地 ↔ 槽 1:1）
- F4 改为成员校验；每台 JWT 仍绑定本机码；发码选槽覆盖写入
- AccessCode / AuthEndTime 项目级共享；**无**独立解绑/清空

设计母本见 [归档双机调研](./archive/2026-08-06-urban-dual-machine-code-binding/00-调研总览.md)。

## 3. 方案对比

### 方案 1：新 ProductCode + 四槽 + 发码选槽（已选定）

**模型**：Urban V2；设备1…4；每台 JWT 只含本机 `machineCode`；验签 `jwtMachineCode ∈ {槽1…槽4}`。

| 层 | 改动要点 |
|----|----------|
| **BasePlatform** | 注册 V2 产品；四槽存储（列扩展或子表）；发码 UI 必选槽 1–4，展示各槽当前码（遮掩）；Redis 载荷带 `Slot`；激活 API 支持 V2 且按槽覆盖；`BuildLicenseFile`/`RefreshJwt`：请求机签发且 ∈ 四槽；**不做**解绑 UI；**5001 路径保持单字段覆盖** |
| **UrbanManagement** | 识别 V2 ProductCode；`GovProject`（或并列结构）同步四槽；F4：V2 走成员包含，5001 仍相等；激活代理按槽 upsert；Catalog 拉取允许 V2；AccessCode/AuthEndTime 仍单字段共享 |
| **MaterialClient** | 枚举/设置增加 Urban V2；激活带 V2 ProductCode；本地仍存本机码；仅本机所在槽被覆盖时 DeviceChanged；`StaticLicenseChecker` 仍比对本机 claim |
| **OpenSpec** | 新/改 specs：urban V2 auth、F4、catalog（`ProductCode ∈ {5001, V2}` 或分端点） |

**优点**：多场地并存；5001 客户零行为变化；换机目标明确；无解绑扯皮。  
**缺点**：跨三仓 + 新产品注册；发错槽会覆盖错机；Catalog/同步边界要显式接纳 V2。

### 方案 2：直接把 5001 扩成四槽（已不采纳）

与「新增一种授权 V2」冲突；存量项目语义突变，迁移与灰度成本高。

### 方案 3：复用 `Material_MachineCode` 多行表（备选存储形态）

可作为 V2 四槽的存储实现之一；须与激活 / LicenseFile / Catalog / F4 全链路打通，并与物料 `AuthType` 隔离，避免串表。

### 不推荐的捷径

- 仅改客户端或绕过 `StaticLicenseChecker`。  
- 逗号拼接多码塞进现有单字段而不改签发/验签。  
- 独立解绑/清空（与 D5 冲突）。  
- 只改 UM/Client、不动 BP 权威源。

## 4. 可落地改动清单

### 4.1 BasePlatform（阻塞依赖，优先）

- [ ] `JC_Product` / `ProductExtEnum`：注册 Urban V2 ProductCode（数值待定）  
- [ ] 数据模型：V2 四槽（字段或子表）；与 5001 单字段路径隔离  
- [ ] 发码 UI：V2 必选设备1…4；展示各槽当前机器码（遮掩）  
- [ ] Redis 激活码载荷：`Slot` + V2 `ProductCode`  
- [ ] 激活：`ActivateUrban` 扩展或 `ActivateUrbanV2`；按 `Slot` 覆盖；**不提供**清空  
- [ ] `LicenseFile` / `RefreshJwt`：按请求 `machineCode` 签发，校验 ∈ 四槽  
- [ ] AccessCode / AuthEndTime：项目级单值，四槽共享  
- [ ] 项目目录 API：纳入 V2（至少一个槽非空即可入目录）  
- [ ] **回归**：5001 仍单机覆盖、按钮与下载条件不变

### 4.2 UrbanManagement

- [ ] 常量/选项：支持 V2 ProductCode（与 5001 并存）  
- [ ] `GovProject`：四槽存储 + 迁移（仅 V2 项目使用；5001 仍单字段或槽1）  
- [ ] 激活代理：按槽同步，禁止无脑覆盖其它槽  
- [ ] `JwtAntiTamperService` F4：V2 成员包含；5001 相等  
- [ ] `RefreshJwt`：使用客户端 JWT 中的 machineCode  
- [ ] `GovProjectPullManager`：接受 catalog 中的 V2  
- [ ] 单测：四机均 Pass；覆盖一槽旧机 Fail、其它槽仍 Pass；5001 回归  
- [ ] **不做**解绑/清空 API 或 UI

### 4.3 MaterialClient

- [ ] ProductCode / WeighingMode（若需要）映射 Urban V2  
- [ ] 激活请求携带 V2 ProductCode；错误文案（槽满/发错槽/签发失败）  
- [ ] 设备吊销：仅本机所在槽被覆盖时触发  
- [ ] 项目信息 UI（可选：本机码 / 已占用 n/4）  
- [ ] 回归：5001 启动门闩、恢复窗、上传 `SubmitMachineCode`

### 4.4 Monospec / OpenSpec

- [ ] `proposal` / `design` / delta specs / `tasks`（主仓库 `openspec/`）  
- [ ] Impact：BasePlatform、UrbanManagement、MaterialClient  
- [ ] design 写入 D1–D7 + 已收口 D8+（对照 [03](./03-openspec-decision-checklist.md)）；effort 仅进 `.openspec.yaml`

## 6. 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| BasePlatform 未改、只改 UM/Client | 高 | 权威仍单字段，四机无法成立 |
| V2 数值未统一导致激活/目录过滤失败 | 高 | 枚举 / JC_Product / Catalog / 客户端必须同日锁定 |
| 误把 5001 路径改成四槽 | 高 | 破坏存量；须分支清晰 + 回归用例 |
| 发错槽覆盖错机 | 中 | 发码页展示当前槽绑定；无解绑则再发码覆盖回来 |
| Catalog 丢槽 / 只认 5001 | 中 | 拉取会把 V2 项目漏同步或打回单码 |
| `RefreshJwt` 仍用权威单码签发 | 高 | 其它槽机拿到错误 claim → StaticLicenseChecker 失败 |
| 会话低估「新产品 + 四槽 + 三仓联调」 | 中 | 建议按仓拆会话（XL） |

## 7. 落地规模（effort，token 口径）

| 块 | 档位参考 |
|----|----------|
| OpenSpec 提案 / design / specs | M |
| BasePlatform：新产品 + 四槽 + 发码 + 激活 + 签发 + Catalog | L |
| UrbanManagement：数据 + F4 分支 + 激活同步 + 拉取 + 测试 | L |
| MaterialClient：ProductCode + 激活/吊销/展示 + 回归 | M |
| 联调（多机真机 + 槽覆盖 + 5001 回归） | L |
| **合计** | **XL**（约 100万+ token；跨仓鉴权主路径，建议分仓/分阶段会话） |

**可行性结论**：

- 技术可落地；组织上依赖 BasePlatform 先落地 V2 产品与四槽权威。  
- MaterialClient 单独改无法完成。  
- 验收以「V2 发码选槽覆盖 + 最多 4 机并存 + 5001 行为不变 + 无解绑」为准。

## 8. 建议落地节奏

1. 主仓库开 OpenSpec，写入 D1–D7 及 [03](./03-openspec-decision-checklist.md) 中已收口项，`.openspec.yaml` 标注 `effort.tier: XL`。  
2. 与 BP 锁定 **D8–D11**（ProductCode / 存储 / Catalog / 激活 API）。  
3. 先实现 BP V2 + 四槽 + 发码选槽 + 按请求机签发，再改 UM F4 分支，最后客户端。  
4. 验收用例至少覆盖：  
   - 四槽先后激活后，已激活机均能上传  
   - 激活槽 N **不**导致其它槽 DeviceChanged  
   - 再发槽 1 码换机 A→E 后：E 可用、A 吊销、槽 2–4 仍可用  
   - AccessCode / AuthEndTime 各机一致  
   - **5001** 仍后激活覆盖、第二机踢第一机  
   - **无**解绑/清空入口  
   - 第 5 台无法获得第五槽（发码仅 1–4）

## 9. 对齐说明

对应改动核心：

**在新增 Urban V2 ProductCode 上，把「唯一权威机器码 + 全局覆盖 + 严格相等」改成「设备1…4 四槽 + 发码选槽覆盖 + 成员校验 + 按请求机签发 JWT；AccessCode/AuthEndTime 共享；无解绑」。存量 5001 保持单机覆盖。**

客户端改动相对可控；**BasePlatform 新产品注册与四槽权威是主体。**
