## 3. 方案对比

### 方案 1：双槽 + 发码选槽（已选定）

**模型**：设备1 / 设备2；每台 JWT 仍只含自己的 `machineCode`；验签 `jwtMachineCode ∈ {槽1, 槽2}`。

| 层 | 改动要点 |
|----|----------|
| **BasePlatform** | 存储两槽（如 `MachineCode` + `MachineCode2` 或等价）；发码 UI 必选设备1/2，Redis 载荷带 `Slot`；`ActivateUrban` 按槽覆盖写入；`BuildLicenseFile`/`RefreshJwt`：用**请求机**签发 JWT，且要求请求机 ∈ 两槽；**不做**解绑/清空 UI |
| **UrbanManagement** | `GovProject` 同步两槽；`JwtAntiTamperService`：成员包含；`RefreshJwt` 传提交 JWT 对应机；激活代理按槽 upsert；AccessCode/AuthEndTime 仍单字段共享 |
| **MaterialClient** | 本地仍存本机码；被覆盖槽的旧机触发 DeviceChanged；另一槽激活不影响本机；`StaticLicenseChecker` 可比对本机 claim |
| **OpenSpec** | 新/改 specs：urban auth、F4 设备绑定、catalog 字段（按需） |

**优点**：同时在线；换机目标明确；无解绑权限扯皮。  
**缺点**：跨三仓 + BP 库结构/发码 UI；发错槽会覆盖错机。

### 方案 2：维持单权威（已不采纳）

仅主备换机体验优化；不满足同时在线。

### 方案 3：复用 `Material_MachineCode` 多行表（备选实现形态）

可为两槽的存储实现之一；须与 `ActivateUrban` / LicenseFile / Catalog / F4 全链路打通，避免目录按 ProId 取 latest 丢第二槽。

### 不推荐的捷径

- 仅改客户端、绕过 `StaticLicenseChecker` 或共享 JWT 文件。  
- 逗号拼接两个码塞进现有单字段而不改签发/验签。  
- 做独立解绑/清空（与 D5 冲突，本期不做）。

## 4. 可落地改动清单（按已确认 Decision）

### 4.1 BasePlatform（阻塞依赖，优先排期）

- [ ] 数据模型：第二槽字段或子表；迁移回填（现有单码 → 设备1）  
- [ ] 发码 UI：必选设备1/设备2；建议展示各槽当前机器码（遮掩）  
- [ ] Redis 激活码载荷：增加 `Slot`  
- [ ] `ActivateUrban`：按 `Slot` 覆盖对应槽；**不提供**清空接口  
- [ ] `LicenseFile` / `RefreshJwt`：按请求 `machineCode` 签发，且校验 ∈ 两槽  
- [ ] AccessCode / AuthEndTime：保持项目级单值，两槽共享  
- [ ] 项目目录 API：两槽字段契约（兼容旧 UM 拉取）

### 4.2 UrbanManagement

- [ ] `GovProject`：两槽存储 + EF 迁移；AccessCode/AuthEndTime 仍各一字段  
- [ ] `UrbanAuthActivateAppService`：按槽同步，禁止无脑覆盖另一槽  
- [ ] `JwtAntiTamperService` F4：相等 → 成员包含  
- [ ] `RefreshJwt` 入参：使用客户端 JWT 中的 machineCode  
- [ ] `GovProjectPullManager` / DTO / 管理端展示（可选）  
- [ ] 单测：双机均 Pass；槽覆盖后旧机 Fail、另一槽仍 Pass；旧单码兼容  
- [ ] **不做**解绑/清空 API 或 UI

### 4.3 MaterialClient

- [ ] 激活错误文案（如发错槽/签发失败）  
- [ ] 设备吊销：仅当本机所在槽被覆盖时触发（另一槽激活不踢本机）  
- [ ] 项目信息 UI（可选：本机码 / 已占用槽位数）  
- [ ] 回归：启动门闩、恢复窗、上传 `SubmitMachineCode`

### 4.4 Monospec / OpenSpec

- [ ] `proposal` / `design` / delta specs / `tasks`（主仓库 `openspec/`）  
- [ ] 明确 Impact：BasePlatform（仓外）、UrbanManagement、MaterialClient  
- [ ] Decision 写入 design：D1–D5

| 项 | 说明 |

## 6. 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| BasePlatform 未改、只改 UM/Client | 高 | 权威仍单字段覆盖，双机无法成立 |
| 发错槽覆盖错机 | 中 | 发码页展示当前槽绑定可缓解；无解绑则只能再发码覆盖回来 |
| Catalog 按 ProId 取 latest 丢第二槽 | 中 | 拉取同步会把两槽打回单码 |
| `RefreshJwt` 仍用权威单码签发 | 高 | 第二台拿到错误 claim → StaticLicenseChecker 失败 |
| 仅改字符串拼接不改验签 | 高 | 行为不可预测 |
| 工期低估「仓外 BP + 发码 UI」 | 中 | 往往占一半以上工作量 |

## 7. 工期与可行性（粗估，人天）

| 块 | 粗估 |
|----|------|
| 需求/OpenSpec 设计 | 1–2 |
| BasePlatform 模型+发码选槽+激活+签发 | 3–5 |
| UrbanManagement 数据+F4+激活同步+测试 | 2–4 |
| MaterialClient 激活/提示/展示/回归 | 1–2 |
| 联调（两台真机 + 槽覆盖换机） | 1–2 |
| **合计** | **约 8–15 人天** |

**可行性结论**：

- 技术可落地；组织上依赖 BasePlatform。  
- MaterialClient.Urban 单独改无法完成。  
- 本期无解绑功能，验收以「发码选槽覆盖」为准。

## 8. 建议落地节奏

1. 主仓库开 OpenSpec，写入 D1–D5。  
2. 与 BP 确认两槽存储与目录 API。  
3. 先实现 BP 两槽 + 发码选槽 + 按请求机签发，再改 UM F4，最后客户端。  
4. 验收用例至少覆盖：  
   - 设备1、设备2 先后激活后两机均能上传  
   - 激活设备2 **不**导致设备1 DeviceChanged  
   - 再发设备1 码换机 A→C 后：C 可用、A 吊销、设备2 仍可用  
   - AccessCode / AuthEndTime 两机一致  
   - 历史单码升级后归设备1，行为兼容  
   - **无**解绑/清空入口

## 9. 对齐说明

对应改动核心：

**把「唯一权威机器码 + 全局覆盖 + 严格相等」改成「设备1/设备2 两槽 + 发码选槽覆盖 + 成员校验 + 按请求机签发 JWT；AccessCode/AuthEndTime 共享；无解绑」。**

客户端改动相对小；**服务端与 BasePlatform 是主体。**
