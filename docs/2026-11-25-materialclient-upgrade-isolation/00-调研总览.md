# 00 · 调研总览：MaterialClient 升级与迁移代码隔离方案

- **日期**：2026-11-25
- **范围**：`repos/MaterialClient` 四个桌面宿主（Standard / SolidWaste / Urban / Recycle）与独立迁移/升级项目（`MaterialClient.DatabaseUpgrade` / `MaterialClient.Toolkit`）
- **生命周期**：`ACTIVE`
- **知识状态**：`CONFIRMED`（5 项边界决策已由用户拍板；产品代码变更须按 OpenSpec change 实施）

## 背景与动因

1. `repos/MaterialClient/src/` 当前已膨胀至 **16 个项目**，在数据库迁移与版本升级上处于“半隔离、双轨并存”状态。
2. 2026-11-25 Urban 100 周期称重 FEV（[`2026-11-24-materialclient-urban-100-weighing-sqlite-busy-fev`](../2026-11-24-materialclient-urban-100-weighing-sqlite-busy-fev/00-FEV-Urban100条称重数据SQLiteBusy.md)）实证暴露了本体内嵌历史兼容胶水（`SqliteMigrationHistoryMigrator`）提前建空库导致 WAL 丢失的副作用（已在 `fix-sqlite-wal-on-migration` 中紧急修复）。
3. 经过用户明确范围收敛，**不需要为 4 个产品做重型统一升级器**，相反可以大幅做减法，把历史迁移与升级代码从本体与解决方案中彻底瘦身。

## 已拍板决策（2026-11-25）

| # | 决策项 | 用户拍板结论 | 对架构的直接简化 |
|---|---|---|---|
| **D1** | 全新空库创建方 | **由客户端本体创建** | 4 个宿主均保留空库首次初始化（创建最新 Schema + `WAL`），不依赖外部工具 `init`，不破坏开发/测试体验。 |
| **D2** | 需要迁移/升级的产品范围 | **仅 Standard 与固废**（历史） | Urban 与 Recycle 彻底不背负任何旧库迁移、legacy history 重命名或升级门禁复杂度。 |
| **D3** | `MaterialClient.Toolkit` 处置 | **已淘汰，不再使用** | 直接从 `MaterialClient.sln` 与 `src/` 移除，消灭整套旧 CSV / 加密库迁移代码。 |
| **D4** | `Migrations` 归属范围 | **当前仅服务于 Standard** | 只有 Standard 需要维护 EF `Migrations/`；Urban / Recycle / SolidWaste 不再以增量 `Migrations` 作为演进手段。 |
| **D5** | 固废升级需求 | **现场已完成升级，后续无升级需求** | `MaterialClient.DatabaseUpgrade` 使命已结束，可退役移除；本体中固废升级门禁与兼容读取可同步瘦身。 |
