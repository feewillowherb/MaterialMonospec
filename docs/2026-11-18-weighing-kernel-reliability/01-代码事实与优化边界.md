# 代码事实与优化边界

先读 [00-调研总览.md](00-调研总览.md)。以下位置均基于该文档记录的 HEAD，行号随实现变动需重新核对。

## 1. 当前调度边界

源码：`repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/AttendedWeighingService.cs`。

- 约 242 行，组合流按 Status 做 DistinctUntilChanged，持续稳定采样不再次触发处理器。
- 约 281 行，异步操作以 Merge(maxConcurrent: 5) 执行，先入队不等于先完成。
- 约 406–436 行，createScheduled 已阻止同回调 transition 与 backup 重复调度。
- 约 449 行，稳定任务先等待 CaptureAllCamerasAsync，再调用建单服务。
- 约 500–522 行，下磅收尾也调度进异步队列。

结论：局部标志不负责周期隔离、建单幂等或任务失败后的恢复。不能把保留 backup 分支解释成自动重试能力。

## 2. 周期信息读取与回写

源码：`repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/WeighingRecordService.cs`。

CreateWeighingRecordAsync 约 105 行起，在执行时读取当前车牌、DeliveryType 和车辆信息；事务完成后约 155 行才写入当前 stateManager 的 recordId。附件阶段还读取当前周期 LPR candidate。

ResetCycle 位于 `repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/WeighingStateManager.cs` 约 231 行，清除 recordId、车辆信息及 LPR candidate，没有使已在途的稳定任务失效。

推断风险：A 车任务等待抓拍时，若下磅重置和 B 车识别先完成，A 车闭包重量可能组合 B 车实时信息；事务中跨周期时也可能把旧记录 ID 写回新周期。该风险即使只有一个稳定任务也需要验证。

候选方向：明确周期身份与周期数据快照；在提交及状态回写边界验证归属。仅在抓拍结束后检查一次周期号不足以证明事务期间安全；仅取消 Task 也不能证明已提交数据回滚。晚到车牌改写是既有行为，不能无条件冻结全部字段而取消它。

## 3. 入口幂等

CreateWeighingRecordAsync 没有通用的已有 recordId 检查或按周期互斥。Urban stableUpload 分支使用 BlocksProducedPlate，但不能泛化为所有模式的并发防重。

候选方向：把同周期创建的并发约束与周期身份一起设计。只加一次 recordId 非空判断会产生检查与写入之间的竞争；按车牌永久去重会误伤同车正常再次过磅。是否有多个生产调用入口需继续核查，不能把直接调用测试等同于正常流程一定可达。

## 4. 失败与恢复

CreateWeighingRecordAsync 最外层 catch 记录异常后返回 Task 成功完成；OnWeightStabilizedAsync 随后仍执行后续抓拍与匹配。调用方无法区分建单失败、车牌缓存命中跳过、创建成功及创建后附件失败。

RewriteAndResetCycleAsync 约 488 行先改牌，再 FinalizeWeighingCycleAsync，最后 ClearCache 与 ResetCycle；前置步骤异常会跳过清理。

候选方向：以命名 record 或明确结果类型表达阶段结果；设计记录已提交但附件失败时的修复语义，并明确下磅收尾失败如何恢复。不能对整个建单流程盲目重试，也不能直接用 finally 无条件清空尚未收尾的数据。

## 5. 范围限制与负面发现

- 未发现支持修改 Merge 并发度、重写状态机或替换响应式框架的测量证据。
- 本轮未证明现场故障频率、数据库重复写入的当前运行时可达性、所有模式行为或硬件超时上界。
- 不顺带清理 tuple、字段赋值、DI 等存量技术债；实际 change 触及相关实现时仍遵守项目约束。
