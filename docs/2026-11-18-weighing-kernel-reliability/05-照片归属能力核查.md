# 照片归属能力核查

先读 [00-调研总览.md](00-调研总览.md)。2026-11-18 源码核查，未进行硬件实验或厂商协议验证。

## 普通摄像头

`WeighingCaptureService.CaptureAllCamerasAsync` 构造 BatchCaptureRequest，调用 HikvisionService.CaptureJpegFromStreamBatchAsync。批量结果保存原 Request，包含设备、通道及保存路径；内部同步调用 CaptureJpeg 或 CaptureJpegFromStream，结果沿原调用返回。

因此当前具备“照片文件对应哪次应用调用”的关联基础。但上层仅接收 List<string>，没有周期身份；请求可能排队、降级或在全失败后软重置重试。即使由 A 的任务发起，实际取图也可能已到 B 上磅时。请求归属不能证明画面中的车一定是 A，也不能保证设备缓冲帧的真实拍摄时刻。应同时区分原请求周期、实际调用区间及结果是否跨周期，不得把晚执行的 A 请求结果挂给 B。

## 车牌抓拍机（LPR）

VzvisionLprService.TriggerCaptureAsync 调用 VzLPRClient_ForceTrigger；HikvisionLprService.TriggerCaptureAsync 调用 NET_DVR_ContinuousShoot。两者当前对上层仅表示触发调用完成，照片和识别信息通过独立回调发布 LicensePlateRecognizedEventData。

该事件包含 PlateNumber、DeviceType、DeviceName、Timestamp、LprImagePath 等，未携带请求 ID 或称重周期 ID；两种设备发布事件时 Timestamp 都赋为 DateTime.Now，是应用发布时刻，不能直接当作设备拍摄时刻。

结论：当前应用链路没有足够信息可靠证明某个 LPR 回包属于 A 或 B 发起的具体命令。车牌文本和到达时间只能提供线索，不能排除迟到回包、被动识别与主动抓拍混合。这里只确认现有实现缺少关联，不能据此断言厂商 SDK 本身一定不支持请求序号或设备时间；原始结构与实机能力仍需调查。

## 诊断与实施影响

- 普通摄像头可按请求/设备/尝试记录 SDK 调用到照片可用的耗时；当前尚未在 ExtraProperties 实现，且需区分重试、解码、落盘和完整业务等待时间。
- LPR 的触发调用耗时不等于收到照片的耗时。没有可靠配对时，记录关联未知或单独保留发送/接收观测，不能伪造准确的往返耗时。
- 下一步先核查原始 SDK 字段及实机回包，随后验证跨周期、主动/被动混合、多设备与超时后迟到结果。缺乏可靠归属时按 04 的业务决策舍弃结果或保留不完整记录，不阻塞同步。
