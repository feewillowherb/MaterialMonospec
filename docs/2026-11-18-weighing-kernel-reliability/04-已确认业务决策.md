# 已确认业务决策

先读 [00-调研总览.md](00-调研总览.md)。来源：Human 于 2026-11-18 的本 topic 对话。以下为已确认的业务约束，不是实现完成或方案可行性证据；产品实现仍经 OpenSpec。

## 1. 迟到数据与车辆归属 — Human APPROVED

- 抓拍设备延迟返回的数据可能缺少可靠请求标识，不能假定可准确赋予称重周期。
- A 车离磅后的迟到数据允许丢弃；A 车允许形成不完整记录。不要据此默认删除已经提交的称重记录。
- B 车数据应来自 B 车自己触发的采集，不得把 A 的迟到结果仅因到达时间落在 B 周期就归给 B。
- 无法确认归属的照片可以舍弃；不能为了补齐照片或车牌而跨周期借用数据。无法确认是否属于 B 自己触发的结果时，按无法归属处理，允许 B 记录不完整。
- 可在 ExtraProperties 增加异常标记表达迟到、归属不明或数据不完整；具体字段名、值域及何时写入由后续设计明确。

上述授权允许后续方案选择丢弃迟到采集结果或保留不完整记录，不要求两种路径同时实现。记录已经落库后的异常补记与恢复行为仍需明确，不能把数据归属问题简化成一个时间阈值。

## 2. 图片与车牌不得阻塞同步 — Human APPROVED

没有图片或车牌也允许上传，不能因此阻止同步。Human 最新澄清：已有附件上传失败时保留 Pending 重试的现行规则不变；此前“图片上传失败也不能阻止同步”的解释被此澄清替代。异常标记本身不应自动成为阻止同步的条件。

后续设计需核查客户端、服务端及实际同步链是否接受缺失字段；不伪造车牌或图片来绕过验证。数据库写入失败等非图片/车牌错误的恢复规则仍待定义。

## 3. 抓拍耗时诊断 — Human APPROVED

在称重记录 ExtraProperties 中新增开发者诊断字段，用于记录抓拍命令发送到收到照片的间隔时间。

Human 补充：这里的照片同时包含车牌抓拍机（LPR）照片和普通摄像头照片，两条链路都在调查与诊断范围内。

后续设计要求：

- 区间起点为实际发送抓拍命令，终点为实际收到照片；不能把等待队列或写附件时间混算为设备返回耗时。
- 明确单位（建议毫秒）、多设备/多次抓拍的表达方式，以及超时、无照片、无法关联的记录方式；本轮不预先锁定字段名和 JSON 结构。
- 耗时测量建议采用单调时钟。若设备没有可靠请求关联能力，不能将“距最近命令的时间”冒充某次请求的准确往返耗时；需表达关联可信度，无法可靠配对时不能写成已确认的耗时。
- 被丢弃且没有对应称重记录的结果，不能为了保存诊断信息挂到 B 车 ExtraProperties；其日志记录位置需在设计中明确。
- 诊断字段缺失或诊断记录失败不能阻塞正常建单与同步。

## 4. 周期身份与下磅失败恢复 — Human APPROVED

- 使用 Guid CycleId 标识每次称重周期，建单后关联 RecordId。旧任务只使用、修改所属周期的数据，不能回写下一周期的当前状态。
- 下磅收尾失败时，下一车继续正常称重；旧记录保留异常标记，后台有限重试收尾。
- 恢复任务固定携带旧 CycleId 和 RecordId，不能从实时状态重新取得下一车的车牌或记录 ID；不得重跑整段建单而重复创建记录。
- 重试耗尽后保留记录、异常及诊断信息，不无限重试，不阻塞下一车。
- 重试次数、间隔、恢复状态保存方式及进程重启后的处理，需在后续设计中明确；本次批准不代表这些机制已经实现或经过验证。

## 5. 仍待明确的部分

- 周期身份采用上述 Guid CycleId；重新上磅及 Urban 缓存边界优先保持既有行为，核对后形成明确设计，不自行改变正常称重规则。
- 先验证各设备是否有请求标识、回调携带信息及取消/隔离能力，再决定可靠归属方案。不承诺仅靠应用周期号就能识别设备的旧回包。
- 下磅收尾恢复按上述已批准规则；建单失败、提交后附件失败的具体恢复步骤仍需明确，允许无图无牌同步不等于任意失败都可忽略。
