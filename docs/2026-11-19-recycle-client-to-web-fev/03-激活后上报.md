# 2026-11-20 激活后上报

## 问题

客户端完成 5020 在线激活之后，已保存的称重能否进入 138 的 Recycle Web。

## 实验

- 激活窗口关闭后，进程停在称重主界面。本地许可对应文一西路西延工程这个 5020 项目。
- 当时正在运行的程序是 2026-11-19 的构建，程序集里没有 `RecycleWebReceiveUploader`。已改用带该上报器的新构建，并沿用同一条本地许可，没有再次提交激活码。
- 138 的 Recycle 绑定改到这次激活的项目，并把该行的机器码写成与令牌一致。验签公钥与客户端配置的指纹一致，并挂进 Recycle 容器。
- 网关 5333 没有把 `/api/transports/receive` 转到 Recycle。这次上报指向 Recycle 自己的端口 5334。
- 本地称重 68（4.08 吨，已有车牌）被标成待接收。客户端每 5 秒 POST 一次。

- 接收门闩在中间件里查 `GovProjects`，当时请求还没有工作单元。ABP 拒绝创建 DbContext，门闩把异常收成空 401。
- 修复：在设备门闩之前调用 `UseUnitOfWork()`，只重建并换上 Recycle 镜像。

## 证据

| 观察 | 结果 |
|------|------|
| 修复前 `POST /api/transports/receive` | HTTP 401，本地记录保持 Pending |
| 换上带工作单元的镜像后同一次上报 | HTTP 200，耗时约 4.5 秒 |
| 本地称重 68 | `RecycleWebReceiveState=Accepted` |
| `RecycleTransportRecords` 中来源记录 68 | 1 |

## Verdict

`FEASIBLE`。激活后的客户端可以把已保存称重写入 138 的 Recycle Web。这不是 Capability 交付。
