# 03 - 改进方案与老客户端兼容设计

本文档给出面向 **MaterialClient.Urban** 与 **UrbanManagement**（含老客户端 `Fdsoft.Weight.GovClient` 兼容）的系统性改进方案（知识状态：`PENDING_VALIDATION`，待 Human 评审后拆分为 OpenSpec change 实施）。

> [!IMPORTANT]
> 本方案严格遵守仓库既有架构约束：
> - **热路径全 Redis**：心跳、设备状态、上下线绝不在 SignalR/Ingest 热路径写 EF（遵守 `urban-signalr-hub-resilience`、`device-online-status-persistence`）。
> - **跨仓 C# 规范**：多值类型使用命名 `record`（禁用 tuple）、状态变更归属类型自身方法（`type-owned-methods`）、纯逻辑不注册 DI（`minimal-di`）、表间无数据库外键（`no-database-fk`）、UI 层不注入 Repository（`viewmodel-no-repository`）。

---

## 1. 目标架构与核心设计原则

1. **单一真实身份（Single Client Identity）**：同一台工控机在设备上报、心跳、日志拉取、称重/通行上报中必须使用**同一个 `ClientId`**，彻底消除身份分裂。
2. **显式保活 + 合理超时（Active Keepalive + Sane Timeout）**：在线判定不再寄生于「设备状态翻转」，而是由客户端定期发送轻量保活包驱动 Redis Live TTL，配合合理的 SignalR 超时阈值（分钟级感知掉线，而非小时级）。
3. **显式客户端分级与能力声明（ClientKind & Capabilities）+ 非称重维护统一**：
   - **统一原则（2026-11-25 确认）**：非称重业务上的细节，在客户端管理维护上必须统一。`MaterialClient.Urban`（5001）与 `MaterialClient.Recycle`（5020）客户端代码与运维需求几乎一致，**共用同一套 SignalR 心跳、设备状态、日志拉取与 Windows 常驻机制**，不再维护独立的 `RecycleDeviceStatus` 并行体系与 `/recycle/device-status` 页面。
   - 服务端与 Admin 明确区分两类协议形态（外加 `ProductCode` 区分 5001 / 5020 业务归属），让 UI 如实呈现能力边界而非以空态掩盖：
     - `MaterialClientSignalR`（`MaterialClient.Urban` 5001 与 `MaterialClient.Recycle` 5020 统一）：支持周期心跳、实时设备明细、远程日志拉取、远程审批推送（按产品能力位声明）。
     - `LegacyHttp`（老版 `Fdsoft.Weight.GovClient`）：仅支持 HTTP 业务上报（被动活跃判定），明确标示不支持设备详情与日志拉取，且**永不退回「未注册」**。
4. **最小侵入老客户端（Zero-Breakage Legacy Compat）**：优先在服务端与中继层（`UrbanManagement.Ingest` / `XiaoShanServe`）解决老客户端兼容问题，**不强求对存量 .NET 4.8 现场工控机做全量强推升级**。

## 2. 模块一：统一身份、心跳与在线判定改进

### 2.1 统一 `ClientId` 生成规则（Urban 客户端）
抽取纯逻辑静态方法（不注册 DI，符合 `minimal-di`）：
- 优先级：`Client:Id`（`!string.IsNullOrWhiteSpace`）→ 持久化/确定性机器标识（如 `Environment.MachineName` 或 `MachineCode` 前 16 位 + 主机名，避免空串 bug）。
- `DeviceStatusEventHandler`、`ClientLogPullService`、`UrbanWeighingRecord` 上报、`UrbanPassage` 上报全部复用同一 `ClientId` 解析方法。

### 2.2 引入客户端轻量周期心跳与元数据上报
解决「无状态翻转则 TTL 过期」与「缺乏版本/能力元数据」两个核心问题：
- **协议扩展**（向后兼容旧版 `MaterialClient.Urban`）：
  - 在 `DeviceStatusHub` 新增 `ClientHeartbeat(ClientHeartbeatDto payload)`（或在既有 `UploadStatus` 之外提供轻量 `ReportHeartbeat`，老版已部署的 `MaterialClient.Urban` 继续靠 `UploadStatus` 也能正常工作）：
    ```csharp
    public sealed record ClientHeartbeatDto(
        string ClientId,
        string ProId,
        string ProName,
        string AppVersion,
        string ClientKind,        // "UrbanSignalR"
        string? MachineName,
        string? MachineCode,
        ClientCapabilitiesDto Capabilities,
        DateTime TimestampUtc);

    public sealed record ClientCapabilitiesDto(
        bool SupportsDeviceStatus,
        bool SupportsLogPull,
        bool SupportsApprovalPush);
    ```
  - **心跳频率与服务端超时对齐**：
    - 客户端周期发送间隔：**30 秒**（连接建立/重连成功立即发 1 次，之后每 30s 1 次）。
    - 服务端 `SignalROptions` 收敛：`KeepAliveIntervalSeconds = 15`，`ClientTimeoutIntervalSeconds = 60`（**撤销 `appsettings.json` 中的 `3600`**），Redis Live TTL = `max(60, ClientTimeoutIntervalSeconds) * 2 = 120s`（覆盖 3~4 个心跳周期）。
    - 效果：正常连接永不因设备稳态而过期；断电/断网后 **60~120 秒内** Admin 即可准确翻转为「离线」。
- **修复客户端重连状态机**：
  - 在 `DeviceStatusSignalRClient.TryReconnectWindowAsync` 连接成功后立即设置 `_isStarted = true`，确保开机首连失败后重连能恢复正常发送。
  - 移除 `OnConnectionRestoredAsync` 中的重复 `RepublishActiveStatuses()` 调用（保留单一路经）。
- **新客户端不靠业务 API 上传兜底在线 + 三代客户端并存分层兼容（2026-11-25 确认）**：
  - **原则**：新客户端上线周期心跳后，在线态以 SignalR 心跳为单一权威来源，**不给通行记录新增 `TouchOnlineAsync`**，避免 `SubmitMachineCode` 造成双实例幽灵记录、掩盖 SignalR 通道故障或因离线补传产生「假在线」。
  - **三代并存平滑过渡**（应对现场新客户端无法一次性全量升级）：
    1. **新版 `MaterialClient`（已发 `ClientHeartbeat`）**：纯 30s 心跳 + 120s Redis TTL；不接受业务 API Touch 覆写在线态。
    2. **未升级的旧版 `MaterialClient`（连上 SignalR 但未发 `ClientHeartbeat`）**：SignalR 底层 15s Ping + 60s `ClientTimeout` 仍可即时触发 `OnDisconnectedAsync` 标离线；为防止稳态 Redis TTL 到期误离线，由单实例 `UrbanManagement.Realtime` 后台按 Hub 内存活跃连接每 60s 代为续期 Redis TTL（或对该类连接给长 TTL + 靠 `OnDisconnectedAsync` 摘除）。原有称重 `TouchPresenceFromReceiveAsync` 仅作过渡保护（且避免制造双 `ClientId`），待全网新客户端均上报 `AppVersion`/心跳后下线。
    3. **老客户端 `GovClient`（无 SignalR）**：保留 `/Api/Post` 7 天留存 + `ActiveUntilUtc` 动态在线判定。
  - **协议增量兼容**：`DeviceStatusHub` 保留旧 `UploadStatus` 等签名不变，新增 `ClientHeartbeat`；所有新增元数据字段可空带默认值，Admin UI 显式区分「新版（vX.Y）」「旧版（无心跳，待升级）」「老客户端（HTTP）」。
- **消除 500 截断**：
  - `DeviceStatusAppService.GetClientListAsync` 改为与 `GovProjectAppService` 共用无截断的 `GetLiveClientConnectionsAsync()`，分页在聚合/筛选后执行（或提供按当前页 `ProId[]` 批量查询接口 `GetClientConnectionsByProIdsAsync(IReadOnlyCollection<Guid> proIds)`，从根本上避免前端一次拉 1000 条）。

## 3. 模块二：设备在线状态监控改进

### 3.1 客户端采集补齐（`MaterialClient.UI` / `MaterialClient.Common`）
1. **摄像头周期巡检**：在 `SharedDeviceStatusTracker` 为 `Camera` 增加 `Timer`（建议 **30 秒**间隔），复用 `CheckCameraStatusOnceAsync` 逻辑，消除「只查启动一次」盲区。
2. **道闸 IO 纳入状态追踪**：
   - 在 `IGateIoControlService` 暴露 `IsOnline`（或连接/心跳状态查询）。
   - 在 `DeviceStatusCatalog` 与服务端 `DeviceStatusService.ValidDeviceTypes` 新增 `"GateIO"`（显示名「道闸IO」）。
3. **多路设备明细写入 `AdditionalData`**：
   - 对 `Camera`、`LPR`、`Scale` 等可能多路部署的设备，保持顶层 `Status` 为汇总状态（兼容现有展示），同时将各路明细序列化为轻量 JSON 放入 `DeviceStatusMessage.AdditionalData`（如 `[{"name":"入口相机","ip":"192.168.1.10","online":true},{"name":"出口相机","ip":"192.168.1.11","online":false}]`）。
   - 顶层状态可区分 `Online`（全在线）、`Degraded`（部分在线，待确认是否引入）或保持 `Online`/`Offline` 并在详情弹窗中展开每路状态。
4. **修复客户端既有 Bug**：
   - 修复 `DeviceStatusEventHandler` 节流命中后补上 `return`（或实现真正的尾沿合并发送）。
   - 修复 `MinimalWebHostService` `/api/device/online-status` 从 `ISharedDeviceStatusTrackerRegistry` 获取活动实例并统一 `"LPR"` 大小写。
   - **`MaterialClient.Recycle` 统一接入 SignalR 维护链路**：让 Recycle 与 Urban 共用 `DeviceStatusSignalRClient`、`SharedDeviceStatusTracker` 与 `ClientLogPullService`（不再禁用 SignalR 推送，也不再走独立 `RecycleDeviceStatus` 表/服务），同时下线 Admin 侧独立的 `/recycle/device-status` 页面。

### 3.2 服务端与 Admin 展示一致性修复（`UrbanManagement`）
1. **修复 `OpenDeviceModal` `SourceProId`**：`ProjectManagement.razor:552` 改为传入 `project.SourceProId == Guid.Empty ? project.Id : project.SourceProId`。
2. **修复「客户端离线但设备在线」矛盾**：
   - 当客户端处于离线态（Redis Miss 降级读 EF，或 `ClientConnectionCacheItem.IsConnected == false`）时，`GetLiveClientDevicesAsync` 应将返回的设备状态统一标注为 `Offline`（或在 DTO 中显式携带 `IsStaleSnapshot = true` + `ClientIsConnected = false`，UI 灰显并提示「客户端已离线，以下为最后快照」）。
3. **统一时区与补齐字段**：
   - `ProjectManagement.razor` 设备弹窗 `LastUpdateTime` 统一 `.ToLocalTime()` 格式化。
   - 补齐 `DeviceStatusAppService.GetListAsync` 中 `DeviceStatusQueryDto.ProName` 的填充。
   - 清理 `ProjectManagement.razor` 中无入口的死代码授权弹窗。

## 4. 模块三：客户端日志拉取可靠性与安全加固

### 4.1 可靠性修复（两端协同）
1. **客户端 `ClientLogPullService`**：
   - `Client:Id` 使用 `string.IsNullOrWhiteSpace(...) ? Environment.MachineName : ...`，并与统一 `ClientId` 规则对齐。
   - **0 字节文件处理**：当 `fileInfo.Length == 0` 时，发送 1 个空分片（`chunkIndex = 0, totalChunks = 1, data = Array.Empty<byte>(), totalFileSize = 0`），避免服务端挂死 120s。
   - **异常快速回包**：`HandleLogListRequestAsync` 拒绝非法路径时返回空列表或错误描述（而非静默 `return`）；修复第 373 行 `await _signalRClient?.ReturnFileErrorAsync(...)` 潜在空引用。
   - 删除死配置引用 `LocalLogApi:Port`（或明确标注 deprecated）。
2. **服务端 `ClientLogAppService` & `ClientLogController`**：
   - **流式落盘替代 `MemoryStream`**：`PullAndCacheAsync` 接收分片时直接写入临时 `FileStream`，传输完成再原子重命名到目标路径，避免大日志文件 OOM。
   - **修复批量 ZIP 下载清理**：使用 `FileOptions.DeleteOnClose` 或 `HttpContext.Response.OnCompleted(...)` 在流传输结束后删除临时 ZIP，杜绝 Windows 文件锁泄漏。
   - **清理策略**：在 `UrbanManagement.Worker` 增加按保留天数/容量上限清理 `ClientLogs/` 缓存目录的定时任务。
3. **Admin UI `ClientLogs.razor`**：
   - 统一 `LogFileToPullDto.FilePath` 语义（明确拆分为 `DateFolder` + `FileName`，放宽或校验目录长度），修复「拉取选中文件」路径拼接错误。
   - 修复 `PullLogsByDateAsync` 后不再清空 `_pullFailures` 与成功提示；区分 `_successMessage`（绿色样式）与 `_queryError`（红色样式）。

### 4.2 安全加固（高优先级）
- **Gateway / Realtime 鉴权收口**：
  - `GET /api/client-log/download/{id}`、`POST /api/client-log/download-batch` 及 `/ClientLogs/*` 静态文件不得对未登录用户暴露。建议由 `UrbanManagement.Admin` 提供带 `[Authorize]` 的下载代理端点转发至 `um-realtime /internal/client-log/*`，并在 Gateway 移除 `/api/client-log/*` 与 `/ClientLogs/*` 的直通路由。
  - `DeviceStatusHub` 逐步补齐客户端鉴权（如激活签发的 JWT 或项目 `AccessCode` + `MachineCode` 握手校验），避免匿名客户端伪造任意 `ProId` 的设备状态。

## 5. 模块四：老客户端（`Fdsoft.Weight.GovClient`）分层兼容设计

老客户端存量运行在大量工地现场，无法假设短期内全部替换为 `MaterialClient.Urban`。兼容设计的核心是**「服务端兜底不丢态、UI 诚实展示能力边界、可选中继轻量增强」**。

### 5.1 解决「30 分钟后退回未注册」的根本方案
现有问题根源在于 `legacy:{AccessCode}` 仅设置了 30 分钟 Redis TTL，到期即删除，既没有离线态留存，又大概率错过 24 小时 EF 快照。

**推荐方案（双层时间字段 + 长 TTL 留存，零热路径 EF 写）**：
1. 在 `ClientConnectionCacheItem` 中增加：
   - `ClientKind`（`"UrbanSignalR"` / `"LegacyHttp"`）
   - `ActiveUntilUtc`（老客户端 = `LastSeenAt + LegacyLiveTtlMinutes`；新客户端可不依赖或等于 `LastSeenAt + LiveTtl`）
2. 老客户端 `TouchOnlineAsync` 写入 Redis 时：
   - **Redis 键本身使用 `OfflineRetentionDays`（7 天）TTL**，而不是 30 分钟！
   - 读取判定在线时，由模型自身方法计算（遵守 `type-owned-methods`）：
     ```csharp
     public bool IsEffectivelyConnected(DateTime utcNow) =>
         ClientKind == ClientKinds.LegacyHttp
             ? ActiveUntilUtc.HasValue && utcNow <= ActiveUntilUtc.Value
             : IsConnected;
     ```
3. **效果**：
   - 称重上报后 30 分钟内：`IsEffectivelyConnected == true` → Admin 显示 **「在线（老客户端）」**。
   - 超过 30 分钟无上报：键仍在 Redis 中（留存 7 天），`IsEffectivelyConnected == false` → Admin 稳定显示 **「离线」** 并保留准确的「最后在线时间」，**绝不会退回「未注册」**。
   - 24 小时 EF 快照必定能捕获到该 7 天留存键并落库；超过 7 天无上报则平滑降级到 EF，继续显示「离线 + 最后在线时间」。

### 5.2 老客户端心跳与中继增强（可选，无需改老客户端安装包）
- **现状约束**：`Fdsoft.Weight.GovClient` 萧山 1 模式下 `agentTmer_Heart.Enabled = false`，且仅在有称重数据时向 `XiaoShanServe`（`Api/Post`）发请求。
- **分级策略**：
  1. **零改动老客户端（默认推荐）**：采用 5.1 节方案，将 `LegacyLiveTtlMinutes` 配置为符合工地作业间隔的阈值（如 60~120 分钟，或区分「活跃/静默」），并在 Admin 明确标注「被动在线（基于最近业务上报）」。
  2. **若部分老客户端运行在联通模式（已每 59s 发 `POST heartbeat`）**：在 `LegacyApiController` 新增 `[HttpPost("heartbeat")]` 轻量接口，接收 `{ buildLicenseNo, equipmentNumber }` 后按 `buildLicenseNo` 匹配项目并调用 `TouchOnlineAsync(proId, $"legacy:{project.AccessCode}", proName)`，返回 `{ code: 200, success: true }`。这样无需改老客户端代码即可让联通模式老客户端获得 59 秒级真实心跳！
  3. **不建议强改老客户端实现 SignalR/日志拉取**：.NET Framework 4.8 WinForms 引入 ASP.NET Core SignalR 客户端与远程日志分片维护成本高、现场替换阻力大；应将老客户端定位为**存量过渡态**，引导新装与重点监控工地平滑迁移至 `MaterialClient.Urban`。

### 5.3 Admin UI 老客户端能力边界清晰化
在 `ProjectManagement.razor` 与 `/client-logs` 做最小但清晰的语义区分：
- **项目列表「客户端」列**：
  - 新客户端：`在线` / `离线` + 版本/类型角标（如 `Urban v1.x`）
  - 老客户端：`在线(旧)` / `离线(旧)`（Tooltip 说明：老版客户端仅基于业务上报判定活跃，不支持设备明细与远程日志）
- **「设备」弹窗**：
  - 若该项目仅存在 `LegacyHttp` 实例，显示明确提示：「当前项目使用老版客户端（HTTP 上报），不支持外设在线状态采集」，而非误导性的「暂无设备数据」。
- **日志管理页 `/client-logs`**：
  - 仅展示 `SupportsLogPull == true` 的客户端，并在页面顶部提示说明仅支持新版 Urban 客户端，避免运维反复排查为什么搜不到老工地。

## 5.5 模块五：Windows 客户端常驻保活与 Admin 异常派单视图

围绕「**Windows 安装 Urban 后始终运行**」与「**Admin 随时发现故障/异常客户端派人处理**」的核心业务诉求，补充以下设计（明确将**远程推送更新客户端**列为 Non-Goal，不在本阶段建设）：

### A. Windows 侧常驻保活（`MaterialClient.Urban` + 安装包）
1. **安装包内置开机自启 + 定时巡检拉起（Task Scheduler）**：
   - 在 `MaterialClient.Urban.iss` 中注册 Windows 计划任务（`schtasks` / XML）：
     - 触发器 1：用户登录时自动启动（工控机配合 Windows 自动登录）；
     - 触发器 2：每 **1~2 分钟** 周期触发一次，配合 `Program.cs` 已有的单实例 `Mutex`（`MaterialClient_Urban_SingleInstance_Mutex`）实现零侵入看门狗——程序正常运行则新进程秒退，程序崩溃或被误关则 1~2 分钟内自动拉起。
   - 同步修复 `MaterialClient.Urban.iss:47-48`，将 `appsettings.json` / `appsettings.secret.json` 改为 `onlyifdoesntexist`，避免重装覆盖现场配置。
2. **进程内防误关与启动自报**：
   - 主窗口关闭行为增加工控保护（二次确认或管理员密码/最小化托盘，防止现场误点关闭）。
   - 心跳元数据中附带 `ProcessStartedAtUtc`（本次进程启动时间），服务端据此可识别客户端是否在短时间内**频繁崩溃重启**。

### B. Admin 侧「故障 / 异常客户端」运维视图（面向派人处理）
在 `ProjectManagement.razor`（或新增顶部「异常监控」快捷筛选/标签）中，基于现有 Redis 实时连接 + 设备状态数据，直接计算每个项目的**健康度等级**，无需运维逐一点开弹窗：

| 健康状态 | 判定规则（示例，可配置阈值） | 运维动作 |
|----------|------------------------------|----------|
| 🟢 **正常** | 客户端在线，且所有已启用核心外设（地磅、LPR、摄像头、道闸）均在线 | 无需处理 |
| 🟡 **外设异常** | 客户端在线，但任一已启用核心外设离线超过阈值（如 2 分钟），或客户端近 1 小时重启 ≥ 3 次 | 远程拉取日志排查，确认硬件故障后派人 |
| 🔴 **客户端掉线** | 曾上线项目当前离线（持续离线时长显式展示，如「已离线 15 分钟」） | 确认工控机断电/断网/进程异常，派人处理 |
| ⚪ **未接入/未启用** | 从未注册上线，或 `IsSyncEnabled == false` | 区分未交付/停工项目，不干扰日常告警 |

- **列表默认支持「仅看异常（掉线 + 外设异常）」一键过滤**，并直接展示：异常类型标签、离线持续时长、故障外设名称、客户端版本/类型（新/老）以及一键跳转「设备详情」和「拉取日志」。
- **为未来远程更新预留的最小接口（Non-Goal 边界）**：
  - 本阶段**不实现**远程下发安装包、断点续传、静默覆盖与回滚机制。
  - 仅在 `ClientHeartbeatDto` 中持续上报 `AppVersion` 与 `Capabilities`（未来可扩展 `SupportsRemoteUpdate`），使 Admin 现阶段即可看清各工地版本分布，未来叠加远程更新时无需重构心跳与身份协议。
