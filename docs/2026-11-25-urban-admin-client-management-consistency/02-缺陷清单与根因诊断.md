# 02 - 缺陷清单与根因诊断

本文档汇总本次三仓源码核对及 138 实验室观察中发现的 **31 项**一致性缺陷与业务缺口，按严重级别（P0 阻断/失真、P1 功能缺陷/逻辑矛盾、P2 体验与运维缺口）和业务域分类列出。所有源码路径与行号均经直接核对（`CONFIRMED`）。

## 1. 心跳与客户端在线判定域

### [P0-1] 无定时心跳导致健康客户端在 Redis TTL 过期后被误判离线/未注册
- **源码定位**：
  - 客户端：`repos/MaterialClient/src/MaterialClient.UI/Services/SharedDeviceStatusTracker.cs:251`（`if (getOnline() == online) return;`）
  - 服务端：`repos/UrbanManagement/src/UrbanManagement.Core/Hubs/DeviceStatusHub.cs:180-264`、`Services/DeviceStatusService.cs:104, 698-713`
- **根因**：
  - 服务端依赖客户端调用 `UploadStatus` 来执行 `TouchOnlineAsync` 续期 Redis Live TTL（SignalR 框架层的 KeepAlive Ping 帧不会触发 Hub 方法，也不会刷新 Redis）。
  - 客户端 `SharedDeviceStatusTracker` 仅在设备在线状态发生 `true <-> false` 翻转时发布事件。当工控现场设备持续稳定在线超过 2 小时（或无称重上报）时，Redis 键自然过期，Admin 列表将该客户端显示为「离线」甚至「未注册」，尽管 SignalR TCP 长连接仍然存活。

### [P0-2] `DeviceStatusSignalRClient._isStarted` 在开机首连失败后永不置 `true`，导致重连后永远只入队不发送
- **源码定位**：`repos/MaterialClient/src/MaterialClient.Common/Services/DeviceStatusSignalRClient.cs:203-224, 256, 457-477`
- **根因**：
  - `MaterialClient.Urban` 作为工控客户端开机自启，极易在网卡/路由尚未就绪时执行首次 `StartAsync()`。
  - 首连失败进入 `catch` 后转入后台 `ReconnectLoopAsync()` -> `TryReconnectWindowAsync()`。当后续网络恢复、`_connection.StartAsync()` 在第 464 行成功时，代码**漏掉了 `_isStarted = true`**。
  - 后续所有 `UploadStatusAsync()` 均命中第 256 行 `if (_connection == null || !_isStarted)`，消息永远进入内存队列而不再向服务端发送，Admin 侧该客户端彻底“失联”。

### [P0-3] `ClientTimeoutIntervalSeconds` 被配置为 `3600`（1 小时），导致异常掉线感知极度滞后
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Hosting/appsettings.json:59`
- **根因**：
  - 代码默认 `ClientTimeoutIntervalSeconds = 60`，但配置文件覆写为 `3600`（1 小时）。
  - 现场工控机断电、拔网线或进程强杀（无 TCP FIN）时，SignalR 需等待长达 1 小时才触发 `OnDisconnectedAsync`，且 Redis Live TTL 被放大为 `3600 * 2 = 7200s`（2 小时），Admin 在 1~2 小时内持续误报「在线」。

### [P1-1] `GetClientListAsync` 硬截断 500 条导致与 `GovProjectAppService` 在线筛选口径矛盾
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/DeviceStatusAppService.cs:35, 42-48`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ProjectManagement.razor:445-460`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/GovProjectAppService.cs:65-89`
- **根因**：`ProjectManagement.razor` 拉取 `MaxResultCount = 1000`，但 `DeviceStatusAppService.GetClientListAsync` 内部硬限制 `MaxRegistryIteration = 500`；而 `GovProjectAppService.GetListAsync` 查全量 `GetLiveClientConnectionsAsync()`。当连接注册表超过 500 条（含 7 天离线留存记录）时，后端已按「在线/离线」筛出的项目，在前端表格中会因为拿不到客户端记录而渲染为「未注册」。

### [P1-2] 业务上报 `TouchOnlineAsync` 口径混乱且新客户端不应依赖 API 兜底在线
- **源码定位**：
  - 称重 Touch：`repos/UrbanManagement/src/UrbanManagement.Core/Services/UrbanWeighingRecordAppService.cs:117-128`（以 `SubmitMachineCode` 作为 `clientId` 写入 Redis）
  - 通行未 Touch：`repos/UrbanManagement/src/UrbanManagement.Core/Services/UrbanCheckpointPassageAppService.cs:32-64`、`UrbanFinishedProductPassageAppService.cs:32-64`
- **根因与收敛结论（2026-11-25 确认）**：
  - 称重接口用 `SubmitMachineCode` 调用 `TouchOnlineAsync`，与 SignalR 使用的 `ClientId`（`MachineName`）不一致，容易在 Redis 中制造双实例幽灵记录；且用业务 API 兜底在线会掩盖 SignalR 通道断链故障、离线补传也会导致「假在线」。
  - **结论**：新客户端引入周期心跳后，**不再为通行记录新增 `TouchOnlineAsync` 兜底**；在线态以 SignalR 心跳为唯一权威来源，称重 `Touch` 仅对未升级旧版客户端作过渡兼容，升级完成后退出。

### [P2-1] 缺乏客户端版本与运行环境元数据
- **源码定位**：
  - `repos/MaterialClient/src/MaterialClient.Urban/MaterialClient.Urban.csproj`（未定义 `<Version>`）
  - `repos/UrbanManagement/src/UrbanManagement.Core/Models/ClientConnectionCacheItem.cs`、`Entities/ClientOnlineStatus.cs`
- **根因**：协议与模型均未定义 `AppVersion`、`MachineName`、`MachineCode`、`ClientKind`、`OsVersion` 等字段，Admin 无法在界面上判断现场跑的是哪一版客户端，也无法支持灰度升级与问题排查。

## 2. 客户端日志管理域

### [P0-4] 默认 `appsettings.json` 中 `Client:Id` 为空字符串，导致 Urban 日志拉取能力默认完全失效
- **源码定位**：
  - `repos/MaterialClient/src/MaterialClient.Urban/appsettings.json:21-23`（`"Client": { "Id": "" }`）
  - `repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs:68, 93, 123`
- **根因**：
  - 第 68 行写法为 `_configuration.GetValue<string>("Client:Id") ?? Environment.MachineName;`。
  - 因为配置值为 `""` 而非 `null`，`??` 不会回退到 `Environment.MachineName`，导致 `_clientId = ""`。
  - 第 93 行与第 123 行均有 `if (string.IsNullOrEmpty(_clientId)) return;`，结果 `RegisterLogCapability` **永远不会被调用**，Admin `/client-logs` 下拉框永远看不到默认配置的 Urban 客户端。
  - 即使人工填了自定义 `Client:Id`，也会与 `DeviceStatusEventHandler.cs:88` 硬编码的 `Environment.MachineName` 产生**同一客户端两个不同 `ClientId`** 的身份分裂。

### [P0-5] `/api/client-log/*`、`/ClientLogs/*` 与 `/hubs/devicestatus` 经 Gateway 直通无鉴权 `Realtime` 服务
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Gateway/appsettings.json`（Order 1, Order 12）
  - `repos/UrbanManagement/src/UrbanManagement.Realtime/UrbanManagementRealtimeModule.cs:36-43`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Hubs/DeviceStatusHub.cs:17`
- **根因**：`UrbanManagement.Realtime` 未启用 `AdminSsoAuthentication` 或 JWT 鉴权，`DeviceStatusHub` 无 `[Authorize]`，Gateway 又将日志下载/静态目录与 Hub 直接路由至 `realtime`。任何可访问 Gateway 的客户端无需登录即可枚举/下载已缓存的客户端日志或向 Hub 发送伪造状态。

### [P1-3] `ClientLogs.razor`「拉取选中文件」存在 `FilePath` 语义错配与 `[StringLength(20)]` 校验冲突
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ClientLogs.razor:600-604`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/ClientLogAppService.cs:236-239, 314-318`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Models/ClientLogInputDtos.cs:43`
- **根因**：
  - `PullAndCacheAsync` 将 `file.FilePath` 当作**目录**拼接 `Path.Combine(clientCacheDir, file.FilePath, file.FileName)`，且 DTO 限制 `[StringLength(20)]`。
  - `PullSelectedFilesAsync` 直接把客户端返回的 `LogFileDto.FilePath`（相对路径，含文件名或更长路径）原样传给 `FilePath`，轻则触发 20 字符验证失败，重则在服务器上拼出 `.../xxx.log/xxx.log` 异常路径。

### [P1-4] `ClientLogs.razor`「拉取到服务器」后结果反馈被立即清空，且成功文案被渲染为错误框
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ClientLogs.razor:498-499, 558-559, 642`
- **根因**：
  - `PullLogsByDateAsync` 调用 `ApplyPullSummary(...)` 写入成功/失败列表后，第 559 行紧接着调用 `await QueryLogFilesAsync()`，而后者在第 498–499 行无条件清空 `_queryError = null; _pullFailures.Clear();`，用户看不到任何失败明细。
  - 第 642 行将 `"成功拉取 X 个文件"` 写入 `_queryError`，前端以红色错误告警样式（`log-alert--error`）渲染。

### [P1-5] 客户端遇到 0 字节日志文件或非法 `dateFolder` 时不回包，导致服务端挂死至超时
- **源码定位**：`repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs:237-242, 344-364, 373`
- **根因**：
  - 0 字节文件导致 `totalChunks = 0`，发送循环 0 次，既不发 `ReceiveFileChunk` 也不发 `ReceiveFileError`，服务端 `PullAndCacheAsync` 阻塞整整 120 秒直至超时。
  - `HandleLogListRequestAsync` 拦截非法路径时直接 `return`，未调用 `ReturnLogList`，服务端阻塞 30 秒。
  - 第 373 行 `await _signalRClient?.ReturnFileErrorAsync(...)` 在 `_signalRClient` 为 null 时会抛 `NullReferenceException`（`await null`）。

### [P1-6] `ClientLogController.DownloadBatch` 在 `finally` 中删除正在流式读取的临时 ZIP 文件
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Realtime/Controllers/ClientLogController.cs:71-90`
- **根因**：`return File(stream, ...)` 返回的是惰性流，方法体退出即执行 `finally { File.Delete(result.FilePath); }`。Windows 下文件被 `FileStream` 锁定导致删除失败被静默吞掉，长期在 `ClientLogs/` 下泄漏 `_batch_*.zip` 垃圾文件；Linux 容器下虽能 unlink，但缺乏规范的 `FileOptions.DeleteOnClose` 或响应完成后清理机制。

### [P2-2] `PullAndCacheAsync` 串行拉取大日志且全程驻留内存 `MemoryStream`
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Core/Services/ClientLogAppService.cs:168-286`
- **根因**：单个日志文件最大配置 50MB（最高 500MB），服务端用 `MemoryStream` 全量缓存在内存后再落盘，多用户并发或单文件过大时有 OOM 风险；且 `ClientLogs/` 服务端缓存目录缺乏定时清理策略。

## 4. 老客户端（`Fdsoft.Weight.GovClient`）兼容域

### [P0-8] 老客户端 30 分钟 TTL 到期后静默退回「未注册」，而非「离线」
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/DeviceStatusService.cs:698-713`（`LegacyLiveTtlMinutes = 30`）
  - `repos/UrbanManagement/src/UrbanManagement.Core/Backgrounds/ClientStatusSnapshotBackgroundWorker.cs:16-74`（24h 快照周期）

  - `repos/Fdsoft.Weight.GovClient/Fdsoft.Weight.GovClient/Fdsoft.Weight.GovClient/BLL/RSACryption.cs:17-90`

  - `networkCompany = 3`（萧山 1）将 `agentTmer_Heart.Enabled = false`，无车过磅时服务端完全收不到任何包（半天无车即视为不活跃）。

## 5. Windows 客户端常驻运行与 Admin 运维异常发现域

### [P0-9] Urban 安装包未配置 Windows 开机自启与进程守护，无法保证「一直启动」
- **源码定位**：
  - `repos/MaterialClient/scripts/installer/MaterialClient.Urban.iss`（全文件无 `[Registry]` 启动项、无 `{commonstartup}`、无 `schtasks` 计划任务）
  - `repos/MaterialClient/src/MaterialClient.Urban/Program.cs:22, 43-46`（虽有自启动目录对齐注释，但仅在 `RequestRestartOnExit == true` 时自重启）
  - `repos/MaterialClient/src/MaterialClient.Urban/App.axaml.cs:86, 91-95`
- **根因**：
  - `MaterialClient.Urban.iss` 仅配置了防火墙放行与安装后启动一次，**未注册 Windows 开机自启或守护任务**，工控机断电重启后客户端不会自动拉起。
  - `App.axaml.cs:86` 设置 `desktop.ShutdownMode = ShutdownMode.OnMainWindowClose`，现场人员误点关闭或程序在启动/运行期抛出未捕获异常（第 91–95 行）时，进程直接退出且无外部看门狗拉起。
  - 附带发现：`MaterialClient.Urban.iss:47-48` 对 `appsettings.json` 与 `appsettings.secret.json` 使用 `Flags: ignoreversion`（与 `openspec/specs/materialclient-urban-installer/spec.md:21` 要求的 `onlyifdoesntexist` 不符），覆盖安装时存在清空现场配置的风险。

### [P1-12] Admin 缺乏「故障/异常客户端」运维视角，无法直接支撑派人处理
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ProjectManagement.razor`
- **根因**：
  - 当前项目列表仅提供粗粒度三态（`在线` / `离线` / `未注册`），没有面向运维派单的**异常聚合与筛选视图**：
    - 无法一眼筛出「**曾经在线但已掉线超过阈值**」的故障站点（与从未上线/已停工的离线站点混在一起）。
    - 无法在列表层识别「**客户端在线，但地磅/车牌识别/摄像头/道闸等关键外设离线**」的半故障站点（必须逐个项目点开「设备」弹窗才能发现）。
    - 未记录或展示离线持续时长、客户端启动时间/重启次数、授权到期预警等派单关键上下文。

### [P2-4] 未留存客户端状态/异常历史记录，故障排查缺乏时间线
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Core/Entities/DeviceStatusLog.cs`（未加入 `UrbanManagementDbContext`）
- **根因**：Redis 只保留当前快照，EF 快照每 24 小时覆盖一次，客户端频繁闪断、某时段设备掉线等历史事件无迹可查，运维派人前难以判断是偶发抖动还是持续硬件故障。

## 6. Admin 布局壳与业务 UI 交互域（合并自 138 观察与源码核对）

### [P1-13] `AdminLayout` 无边界前缀匹配导致 `/weighing-approval` 误命中「称重记录」标签（原 U1）
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Admin/Pages/AdminLayout.razor:102-135`
- **根因**：`_navItems` 中 `new("/weighing", "称重记录")` 排在 `new("/weighing-approval", "异常审批")` 之前，而 `UpdateActiveRoute()` 使用无路径段边界的 `_activeRoute.StartsWith(n.Route, StringComparison.OrdinalIgnoreCase)`。访问 `/weighing-approval` 时侧栏 `NavLink` 按路径段高亮「异常审批」，但顶栏标签栏先命中了 `/weighing`，导致不创建「异常审批」标签且高亮脱节。

### [P1-14] `_Host.cshtml` 缺少 `HeadOutlet` 且 `ClientLogs.razor` 漏写 `<PageTitle>`，浏览器标题恒为「设备监控」（原 U3）
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/_Host.cshtml:7-15`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ClientLogs.razor`
- **根因**：各业务页已编写 `<PageTitle>`，但 `_Host.cshtml` 的 `<head>` 中缺少 `<component type="typeof(HeadOutlet)" render-mode="Server" />`，导致 Blazor `<PageTitle>` 全部不生效，`document.title` 永远停留在静态的 `UrbanManagement - 设备监控`；此外 `ClientLogs.razor` 漏写了 `<PageTitle>`。

### [P1-15] 独立 `RecycleDeviceStatus` 平行体系为未接入空壳，违背「客户端维护统一」原则
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/RecycleDeviceStatus.razor`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/RecycleDeviceStatusAppService.cs`
  - `openspec/specs/admin-recycle-device-status/spec.md`
- **根因**：`MaterialClient` 并未调用 `RecordHeartbeatAsync`，导致 `/recycle/device-status` 始终为空；同时 `add-admin-recycle-project-page` 已复用 `ProjectManagement.razor` 与 `IDeviceStatusAppService`。Urban（5001）与 Recycle（5020）客户端维护代码与功能高度一致，不应并存两套设备在线系统。

### [P2-5] 分页非当前页按钮渲染 `aria-current="false"`（原 U2）
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ProjectManagement.razor:164`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/WeighingRecord.razor:232`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/WeighingApproval.razor:237`
- **根因**：三处分页按钮均写成 `aria-current="@(pageNum == _currentPage ? "page" : "false")"`，非当前页仍输出 `aria-current` 属性，不符合 WAI-ARIA 最佳实践（非当前页应传 `null` 不渲染）。

### [P2-6] 通行类列表硬编码 `min-width: 1400px` 导致常规屏必然横向滚动（原 U4）
- **源码定位**：
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/FinishedProductPassage.razor:24`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/CheckpointPassage.razor`
- **根因**：11 列表格硬编码 `style="min-width: 1400px;"`，在常见 1440px 屏幕减去 200px 侧栏后必然触发横向滚动，主列与操作列可读性下降。

### [P2-7] 称重/审批默认「今天」空态提示未说明筛选区间（原 U5）
- **源码定位**：`repos/UrbanManagement/src/UrbanManagement.Admin/Pages/WeighingRecord.razor:195, 392`、`WeighingApproval.razor:200`
- **根因**：默认筛选今日时间范围时，空表仅显示通用文案「暂无数据」，容易让运维或业务人员误判为无业务数据，建议在空态文案中提示可调整时间范围（或由产品拍板调整默认区间）。
