# 07 - 2.0 演进并存与局部隔离策略

创建日期：2026-11-25。生命周期：`ACTIVE`。知识状态：部署现状核对为 `CONFIRMED`（基于 `repos/UrbanManagement/deploy/docker/compose.yaml` 与 `UrbanManagement.Gateway/appsettings.json`）；2.0 并存与隔离策略为架构决策记录（暂不进 `docs/intake/` 与 `openspec/`，不修改业务代码）。

---

## 1. 核心决策结论

面对 **Admin 与 Urban / Recycle 的 2.0 大更新**，确立以下两条边界：

1. **Recycle（5020）尚未正式发布 → 零历史兼容包袱**：
   - `um-recycle` 与 `MaterialClient.Recycle` 直接按 2.0 目标一步到位演进，**无需** 1.0/2.0 并行容器，也**无需**为旧 `RecycleDeviceStatus` 表、独立心跳接口或 `/recycle/device-status` 页面保留过渡兼容，可直接清理并统一接入 SignalR 客户端维护体系。
   - **称重异常设计边界（2026-11-25 确认）**：Recycle 保留与 Urban 一致的称重异常等设计，但该设计对 **Recycle Web（5334）** 无业务意义（不展示、不耦合进资源化业务流程），**仅用于 Admin 运维人员统一查看称重记录的提交与异常情况**。
2. **仅对已正式在网的城管（5001）+ Admin 做 1.0 / 2.0 并存与平滑过渡**：
   - **不推荐**把 1.0 与 2.0 整栈复制成两套独立微服务集群（同源项目/称重/SMB 照片无法双库割裂，`um-worker` 双跑会向政府重复上报，且宿主机内存资源紧张）。
   - **推荐「共享数据底座 + 局部微服务容器并行隔离（Strangler Fig）」**：复用现有 `um-gateway`（YARP）与 Docker Compose 角色拆分，仅对有灰度/故障隔离价值的服务并行拉起 2.0 容器。

## 2. 分层并存与隔离矩阵

| 架构层级 | 当前容器 / 组件 | 1.0 与 2.0 关系 | 是否独立拉 2.0 容器 | 隔离与兼容边界 |
|----------|----------------|----------------|---------------------|---------------|
| **数据与出口底座** | `mssql`、`redis`、SMB `Uploads/`、`um-worker` | **必须共用一套** | ❌ 不拆 | DB 对 1.0 Urban 表仅做向后兼容的增量迁移（Expand-Only：只加可空列/新表，不删改 1.0 在用列）；Redis 新字段可空带默认值；`um-worker` 保持单实例防政府重复推送。 |
| **Admin 前端层** | `um-admin` | **1.0 / 2.0 并行灰度** | ✅ **推荐独立容器** | 可拉起 `um-admin-v2`（独立端口与独立 DataProtection/Cookie），直连同一套 DB / Redis / Uploads。运维先切 2.0 验收，有问题秒切回 1.0 零影响。 |
| **Recycle 站点层** | `um-recycle` | **直接原地演进 2.0** | ❌ 无需双跑 | 未正式发布，无需 `um-recycle-v2` 与旧接口兼容。 |
| **实时信令层** | `um-realtime` | **按风险决定** | ⚠️ **可选独立容器** | 若 2.0 新心跳、流式日志拉取与鉴权改造风险较高，可在 YARP 新增 `/hubs/devicestatus-v2` 指向 `um-realtime-v2` 实现**故障隔离**（与 1.0 共用 Redis 键空间，Admin 2.0 统一读取）；若改动克制，也可在同容器内以新增 RPC 向后兼容。 |
| **无状态接入层** | `um-ingest`（x2）、`um-attachment` | **接口增量/版本兼容** | ❌ 通常不拆 | 通过可空字段或 `/api/v2/...` 同时承接 1.0 客户端（单图/旧协议）与 2.0 客户端（海康双图/新协议）。 |
| **客户端侧** | `GovClient`、`MaterialClient.Urban` 1.0 / 2.0、`MaterialClient.Recycle` 2.0 | **城管分批升级并存；Recycle 直接 2.0** | 天然按工控机隔离 | 城管侧按 [`03-改进方案与老客户端兼容设计.md`](03-改进方案与老客户端兼容设计.md) §2.2 的三代兼容策略平滑过渡；Recycle 直接以 2.0 上线。 |

## 3. 零停机切换节奏

1. **底座先行（Expand）**：`um-migrator` 执行增量兼容迁移；`um-ingest` / `um-attachment` 先具备同时承接 1.0 与 2.0 的能力。
2. **2.0 并行灰度**：上线 `um-admin-v2`（及按需 `um-realtime-v2`）；Recycle 直接发 2.0；城管挑选试点工地升级 2.0 客户端并验收。
3. **全量切流与清理（Contract）**：城管在网客户端与运维全部切到 2.0 稳定运行后，下线 `um-admin` 1.0 容器、移除过渡期兼容分支，最后再清理历史废弃列/旧表。

## 4. 2.0 远程推送更新（OTA）选型与无人值守工控机约束

> 本节为 2.0 远程更新的方向选型与目标边界（仅作架构决策记录，不修改业务代码，暂不进 `docs/intake/` 与 `openspec/`；1.x Phase 1–4 仍保持只预留 `AppVersion` / `Capabilities` 字段）。

### 4.1 推荐选型：**Velopack 私有静态源 + 现有 Admin/SignalR 控制面 + Windows 计划任务看门狗**

Urban（5001）与 Recycle（5020）**统一共用**同一套推送更新机制（仅按产品目录区分包源）：

| 层面 | 选型与职责 | 说明 |
|------|-----------|------|
| **控制面（灰度与状态）** | 复用 `um-admin` + `um-realtime` | Admin 上传/指定目标版本并按「单台 / 试点项目 / 全量」下发；在线时经 `DeviceStatusHub` 实时推送指令，离线时由下次 30s `ClientHeartbeat` 响应兜底带回 `TargetVersion`；客户端通过心跳回传更新状态（`Idle / Downloading / ReadyToRestart / Applied / Failed`）。 |
| **数据面（包托管与下载）** | **Velopack 私有 HTTP 静态源**（**无需新增微服务**） | 构建时用 `vpk pack` 生成 `releases.win.json`、`*-full.nupkg`、`*-delta.nupkg`（支持 Delta 差量包省工地带宽）；直接挂在现有 `um-attachment`（或现有静态卷 / Nginx）经 `um-gateway` 提供带鉴权的 HTTP GET 下载，零新增容器。 |
| **常驻与拉起** | **Windows 任务计划程序（Task Scheduler）** | 系统自带（`schtasks`），配置「用户登录时」+「每 1~2 分钟重复」双触发器，配合 `MaterialClient` 已有单实例 `Mutex` 实现零成本看门狗；相比 Windows Service 避开了 Session 0 无法直接拉起 Avalonia 前台窗口的问题。 |

### 4.2 无人值守工控机必须满足的 4 条硬规则

1. **装机前置**：开启 Windows 自动登录、关闭自动休眠与锁屏超时、关闭 Windows 崩溃弹窗（WER，防止崩溃时卡在对话框不退出）。
2. **数据彻底外置 + 免 UAC + 放弃外部 `appsettings.json`**：程序安装至非 `Program Files` 路径（如 `C:\MaterialClient\<Product>\`），SQLite 数据库与本地缓存照片全部外置到固定数据目录（如 `C:\ProgramData\MaterialClient\<Product>\`）；配置体系全面收敛为「代码内置默认值 + SQLite DB」（适用于全部 4 个宿主，详见独立专题 [`2026-11-25-materialclient-db-first-config`](../2026-11-25-materialclient-db-first-config/00-调研总览.md)），从根源消除外部 JSON 损坏导致启动失败的风险。
3. **安全切换门禁 + 自动回滚**：
   - 后台静默下载并完成 SHA256 校验后，**必须检测业务空闲**（无在磅车辆、无进行中写库/上传）再执行切换重启；支持配置低峰时间窗（如 `01:00–05:00`），并允许 Admin 对单台下发「下次空闲即刻更新」；
   - 更新切换期间写短暂更新锁标记，避免计划任务在替换目录的几秒内抢跑拉起；
   - 新版本启动后须稳定运行满阈值（如 30 秒）并连上心跳才写「健康标记」；若连续闪退则**自动回滚至上一版本目录**并向 Admin 上报失败原因，杜绝工控机“变砖”。
4. **前台防误关**：主窗口禁用直接关闭（或退出需管理员口令），保证无人值守工控机始终处于前台运行。
