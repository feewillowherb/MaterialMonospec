# Urban 与 Admin 客户端管理一致性调研报告

创建日期：2026-11-25。生命周期：`ACTIVE`。知识状态：代码事实部分为 `CONFIRMED`（基于三仓当前源码核对）；改进方案与拆包建议为 `PENDING_VALIDATION`（待 Human 评审拍板后进入 OpenSpec）。

> [!NOTE]
> 本 Topic 属于可复用调研知识（`docs/`），**不是** OpenSpec change，也**不**直接授权修改产品行为。所有产品改动须经 Human `APPROVED` 后在主仓库 `openspec/` 发起变更。

## 调研背景与目标

### 核心业务诉求（Goal）

目标 Windows 工控机在安装 **MaterialClient.Urban**（以及同源的 **MaterialClient.Recycle**）后，期望客户端程序**始终处于运行状态（开机自启 + 进程常驻/异常自愈）**；同时运维人员在 **Admin**（`repos/UrbanManagement`）上能够**随时发现故障或异常的客户端**，第一时间定位问题并**派人到现场处理**。

> [!IMPORTANT]
> **统一架构原则（2026-11-25 确认）**：**非称重业务上的细节，在客户端管理维护上必须统一**。Urban（5001）与 Recycle（5020）的客户端代码与运维需求高度一致，**不应实现两套客户端在线/设备监控/日志维护系统**；双方共用同一套 SignalR 心跳、设备状态、日志拉取与 Windows 常驻机制，移除独立的 `RecycleDeviceStatus` 平行空壳与 `/recycle/device-status` 页面。Admin 导航也不必拆成两套平行维护菜单。

核心覆盖：

1. **客户端常驻与心跳在线**：Windows 安装即具备开机自启与崩溃/误关保护；Admin 实时准确反映客户端是否在线、离线时长、多实例并发与断线收敛。
2. **故障与异常可发现（面向运维派单）**：不仅看“客户端在线/离线”，还要在 Admin 一眼识别「已掉线需处理」「客户端在线但关键外设（地磅/LPR/摄像头/道闸）故障」「频繁重启/授权异常」等异常站点。
3. **日志远程管理**：派人前或远程排查时，支持从 Admin 查询、拉取、缓存并下载现场客户端日志。
4. **老客户端兼容**：在 `Fdsoft.Weight.GovClient`（.NET Framework 4.8 WinForms）存量并网运行期间，确保 Admin 展示可信、语义一致，不误报、不丢失状态。
5. **Admin 布局与交互质量（合并自 138 观察）**：修复侧栏/多标签路由前缀误匹配（U1）、`document.title` 失效（U3）、分页 `aria-current`（U2）等前端缺陷，保持统一的 Layui 卡片壳体验。

### 明确非目标（Non-Goal）

- **远程推送更新客户端（OTA / 远程静默升级）**：属于未来演进方向，**不在本次改进范围（Non-Goal）内**。当前仅在心跳/注册元数据中预留 `AppVersion` 与 `Capabilities` 扩展字段，为未来接入远程更新留好演进接口，不提前建设升级分发与客户端热更机制。

本次调研对以下三个仓库的当前源码及 `openspec/specs/` 既有规范做了端到端交叉核对：

- **新客户端（Urban）**：`repos/MaterialClient/src/MaterialClient.Urban`、`MaterialClient.Common`、`MaterialClient.UI`（并对照 `MaterialClient.Recycle`）
- **管理端与服务端（Admin / Realtime / Ingest / Worker / Gateway）**：`repos/UrbanManagement/src/`
- **老客户端（GovClient）**：`repos/Fdsoft.Weight.GovClient/`

## 核心结论摘要

### 1. 现状判定：链路已搭骨架，但关键闭环存在断裂（`CONFIRMED`）

| 能力域 | 现状评级 | 核心问题摘要 |
|--------|----------|--------------|
| **心跳与在线判定** | 🔴 严重不一致 | 客户端**无定时心跳**，仅在设备状态布尔翻转时发 `UploadStatus`；服务端 `ClientTimeoutIntervalSeconds` 被配置为 `3600`（1 小时，导致掉线感知极慢），且超过 2 小时无设备状态翻转会触发 Redis Live TTL 过期，健康客户端反而被判离线；开机首连失败后 `_isStarted` 永不置 `true`，重连成功后永远只入队不发送。 |
| **日志远程拉取** | 🔴 默认不可用 | Urban 默认 `appsettings.json` 配置 `"Client": { "Id": "" }`，`ClientLogPullService` 用 `??` 回退失败导致 `_clientId == ""`，**永远不会调用 `RegisterLogCapability`**；此外还存在 0 字节文件挂死拉取、选中文件 `FilePath` 语义错配及 `[StringLength(20)]` 冲突、拉取结果提示被瞬间清空、ZIP 下载句柄泄漏及 Gateway 直通 `realtime` 缺乏鉴权。 |
| **设备在线监控** | 🟠 局部失真 | 摄像头仅在启动时检测一次（无定时器）；道闸 IO（`GateIoControlService`）未纳入采集与上报；多路相机/LPR 被压扁为单一布尔值；Admin 端 EF 降级读取设备状态时未强制标记 `Offline`，导致「客户端离线但设备在线」矛盾；`OpenDeviceModal` 传入 `project.Id` 而非 `SourceProId`，导致 5020 项目查错；超过 500 实例时列表截断与筛选口径不一致。 |
| **Windows 常驻与运维派单视图** | 🔴 能力缺失 | `MaterialClient.Urban.iss` 未配置开机自启与进程守护；主窗口关闭即退出进程，初始化或运行时崩溃直接静默退出无拉起机制；Admin 仅展示「在线/离线/未注册」，缺乏「故障/异常客户端」汇总视图与异常分类（离线超时、在线但关键外设故障、频繁重启等），无法直接支撑运维派人处理。 |
| **老客户端兼容** | 🟠 语义退化 | `Fdsoft.Weight.GovClient` 无 SignalR、无设备状态上报、无日志能力，萧山 1 模式甚至关闭了 HTTP 心跳；服务端虽通过 `/Api/Post` 写入 `legacy:{AccessCode}`（30 分钟 TTL），但到期后无离线写入且 24 小时 EF 快照大概率错过该窗口，导致**有真实称重上报的老客户端在 30 分钟后静默退回「未注册」**，且 Admin UI 无法区分老客户端与新客户端的能力边界。 |
| **Admin 布局与导航统一** | 🟠 缺陷与冗余并存 | 138 观察（Run `admin-ui-layout-observe` / `2026-11-25T101234`）与源码核对确认：`AdminLayout.razor` 无边界 `StartsWith` 导致 `/weighing-approval` 误命中「称重记录」标签（U1）；`_Host.cshtml` 缺 `HeadOutlet` 导致 `document.title` 恒为「设备监控」（U3）；分页多按钮 `aria-current="false"`（U2）；通行表硬编码 `min-width: 1400px`（U4）；且 `/recycle/device-status` 为客户端未接入的独立空壳，应统一回 `DeviceStatusHub` 体系并下线。 |

### 2. 建议改进路线（摘要）

建议按「**止血修复 + UI 壳收口 → 协议与心跳闭环（含 Recycle 统一） → 设备与日志完善 → 老客户端分层兼容**」4 个阶段拆分为独立 OpenSpec change 推进：

- **Phase 1（P0 止血 + Admin 壳修复）**：修复 Urban `Client:Id` 空串回退与身份统一、修复 `DeviceStatusSignalRClient._isStarted`、修复 `ClientLogs.razor` 交互反馈与 `FilePath` 语义、修复 0 字节文件挂死、收敛 `ClientTimeoutIntervalSeconds`、补齐 `/api/client-log/*` 鉴权、修复 `OpenDeviceModal` `SourceProId`；同步修复 Admin 壳缺陷（U1/U2/U3，及可选 U4/U5）。
- **Phase 2（心跳、常驻与双端维护统一）**：引入客户端轻量周期心跳保活（避免 TTL 饥饿且不写 EF 热路径）、补充客户端元数据（`AppVersion` / `ClientKind` / `Capabilities` / `MachineCode` / `ProcessStartedAtUtc`）、**将 `MaterialClient.Recycle` 纳入同一套 SignalR 维护体系并移除独立 `RecycleDeviceStatus` / `/recycle/device-status`**、**建立三代客户端并存分层兼容（新版纯心跳驱动、旧版新客户端由 Hub 活跃连接代续期 Redis TTL、老客户端靠 `/Api/Post` 7 天留存）且不再给通行记录新增业务 API Touch 兜底**、消除 `GetClientListAsync` 500 截断、安装包补齐开机自启与看门狗。
- **Phase 3（设备在线闭环与派单视图）**：为 `Camera` 补齐周期巡检、纳入 `GateIO` 状态采集、通过 `AdditionalData` 承载多路外设明细、统一 EF 降级离线语义与时区、修复 `DeviceStatusEventHandler` 节流/双重重发；Admin 增加「仅看异常（掉线/外设异常/频繁重启）」派单视角。
- **Phase 4（老客户端分层兼容）**：服务端为 `legacy:*` 引入独立的离线留存转换（防止退回「未注册」），显式建模 `ClientKind`（`MaterialClientSignalR` / `LegacyHttp`）与能力位（`SupportsDeviceStatus` / `SupportsLogPull`），Admin UI 清晰展示客户端类型与降级说明。

### 3. 落地规模评估（按 `effort-token-estimate` 口径）

> 遵循 `traits/effort-token-estimate-trait.md`，采用 AI Agent token / 上下文规模档位作为评估参考，不使用人天指标。

- **总体落地规模**：**XL**（跨 `MaterialClient`、`UrbanManagement` 两仓为主，视情况轻量触及 `Fdsoft.Weight.GovClient` 中继层，合计约 **100万+ token** 量级），**建议按 Phase 1–4 拆分为 4 个独立 OpenSpec change 分会话实施**。
- 分阶段档位参考：
  - Phase 1（P0 止血修复）：**M**（~15万–40万 token，跨两仓局部修复与单测）
  - Phase 2（心跳、身份与元数据闭环）：**L**（~40万–100万 token，跨两仓协议/Redis/Admin 查询主路径）
  - Phase 3（设备监控闭环与 UI 修复）：**M**（~15万–40万 token，两仓设备采集与 Admin 弹窗）
  - Phase 4（老客户端兼容与能力分级）：**M**（~15万–40万 token，服务端 `legacy:*` 生命周期与 Admin 展示）
