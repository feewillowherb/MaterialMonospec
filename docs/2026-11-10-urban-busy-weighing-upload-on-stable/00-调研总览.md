# 00 调研总览 — Urban 繁忙过磅与稳定后上传

> 状态：`ACTIVE`。对照 2026-11-10 `MaterialClient` 源码。  
> 这不是 OpenSpec change，不能当授权改代码。

## 1. 诉求

提高 `MaterialClient.Urban` 对称重的吞入量。现场繁忙时，前车还没下磅后车可能已经上磅。现行一车一周期、必须等重量回到空磅阈值以下才结束本周期，不支持这种叠车繁忙模式。

设想（设置里可选、默认关）：重量稳定后选出一张有效车牌，立即绑定并升到可上传，不必等下磅。

## 2. 范围

| 记录设想方案的主风险与未决点 | 改道闸 / 异常规则产品行为 |

## 3. 结论

| # | 结论 | 状态 |
|---|------|------|
| C1 | 稳定时只建单与拍照；`SyncStatus` 从 `WeighingInProgress` 升为 `Pending` 发生在下磅收口 `FinalizeWeighingCycleAsync` | `CONFIRMED` |
| C2 | 已有 `recordId` 且重量仍高于 `MinWeightThreshold` 时，状态被压在 `WaitingForDeparture`，不会开下一车 | `CONFIRMED` |
| C3 | 前车未下磅、后车已上磅时，重量下不了阈值 → 第一单停在 `WeighingInProgress`，第二单不会建 | `CONFIRMED` |
| C4 | 设置里 `EnablePlateRewrite` / `EnableLatestPlateNumber` / `EnableMatchOnStable` 都不升 `Pending`，也不重置周期；Urban 还跳过运单匹配 | `CONFIRMED` |
| C5 | 「有效车牌」在代码里没有独立定义；现有只有最频繁/最近一次、颜色优先级、推荐纠错和格式校验 | `CONFIRMED` |
| C6 | 若在重量仍高于阈值时 `ResetCycle`，状态流可能立刻再进 `WaitingForStability` 并再建单，重量可能是叠车重量 | `INFERRED` |
| C7 | 稳定瞬间抓拍可能早于车牌识别；提前上传会放大空牌 / `CaptureFailure` 异常单 | `INFERRED` |
| C8 | 道闸出口开闸绑 `WaitingForDeparture`，清会话绑 `OffScale`；提前收口对道闸的影响待核对 | `PENDING_VALIDATION` |
| C9 | 车牌会误识别。次数、最近一次、格式合法都证明不了「磅上这一辆」是哪张牌（Human，2026-11-10） | `CONFIRMED`（Human） |

| C11 | 同一段在磅稳定若按每次稳定边沿上传，已上传数据会再传，产生大量无效单（Human，2026-11-10） | `CONFIRMED`（Human） |
| C12 | 一次一传与选牌都不需要保存整段地磅变化曲线。现有流只有约 3 秒滑动窗口；够用的是空磅阈值穿越，以及上一笔已上传的稳定重量 | `CONFIRMED` |
