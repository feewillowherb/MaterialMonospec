# 02 设想方案与缺口

> 下列「设想」是候选方向，**不是**已批准产品方案。落地须另开 OpenSpec change，并经 Human `APPROVED`。

## 1. 设想（可选开关，默认关）

目标：提高连续过车吞入量，支持「前车未下磅、后车已上磅」的繁忙现场。

候选行为：

1. 重量进入 `WeightStabilized` 并完成本单建单 / 抓拍后  
2. 从本周期 LPR 缓存中选出一张**有效车牌**并写回 `WeighingRecord`  
3. 立刻走与下磅收口等价的上传准备：异常重算 + `WeighingInProgress` → `Pending`  
4. 结束本周期（清车牌缓存、`ResetCycle`），**不必**等重量掉到 `MinWeightThreshold` 以下  

设置入口可放在现有「称重配置」旁（与 `EnableMatchOnStable` 同区），与运单匹配开关分离——Urban 不需要 `TryMatchEvent`。

与现有开关对照：

| 能力 | `EnableMatchOnStable` | 本设想 |
|------|----------------------|--------|
| 稳定后动作 | 发运单匹配事件 | 绑车牌 + 升 Pending + 结束周期 |
| Urban 是否生效 | 否（策略跳过匹配） | 是（城管上传路径） |
| 是否等下磅 | 是 | 否 |

## 2. 已知问题：哪张牌可靠（Human，2026-11-10）

车牌会误识别。现行选择器回答的是「缓存里哪张更常出现 / 更新」，回答不了「磅上这一辆是哪张」。

| 现有手段 | 能做什么 | 不能做什么 |
|----------|----------|------------|
| 次数最多 / 最近一次 | 在多帧里挑一张 | 误识别若连拍多次，错牌会赢 |
| 配置的低优先级颜色 | 该颜色降权，无高优先级时才用 | 不证明是磅上车辆 |
| `RecommendPlateNumberService` | 把近似牌纠到推荐牌 | 两张都真实时会纠错或混票 |
| `PlateNumberValidator` 格式 | 丢掉明显非法串 | 格式合法的错牌仍会入选 |
| `UrbanAnomalyDetector` 空牌 | 空牌标 `EmptyPlate` | 有字的错牌不算异常 |

待定（产品决策，源码里没有答案）：

1. 可靠是否要求同一牌在稳定窗口内达到次数，且与另一张差开？  
2. 现场只有一台识别机，不能按 `Enter` / `Exit` 分票。同一机位短时间出现两张都像真的牌时怎么办？  
3. 两张都像真牌时：下磅后仍然上传，牌用缓存挑中的那张；异常只作标记。以前的模式已经是这样。  
4. 稳定瞬间无牌：等待短暂窗口 / 记异常后仍上传 / 退回等下磅？

「非空」和「格式合法」都不够称为有效车牌。

## 2.1 异常规则（与「可靠」不是一回事）

[`UrbanAnomalyDetector`](../../repos/MaterialClient/src/MaterialClient.Common/Services/UrbanAnomalyDetector.cs) 规则：

| 规则 | 条件 | 原因 |
|------|------|------|
| 0 | 无 LPR 附件 | `CaptureFailure` |
| 1 | `PlateNumber` 空/空白 | `EmptyPlate` |
| 2 | 重量超上限（含偏差%） | `OverUpperLimit` |
| 3 | 重量低于下限（含偏差%） | `UnderLowerLimit` |

重量上下限、有无 LPR 图是另一套异常规则。错牌只要非空且重量在限内，检测器判为正常。

## 3. 已知问题：一台识别机看到两张牌，以及重复上传（Human，2026-11-10）

稳定时前车还在磅上、后车已经靠近。现场只有一台识别机，A 和 B 都从这一台推上来，推送不带 `Enter` / `Exit`。重量可以是单车，也可以是两车都压在磅上。

现行缓存把 `Scale` 上所有识别并成一池。稳定后按次数或最近时间在 A、B 里挑一张，会绑错车。配置里的 `UrbanInOutType` 改变不了「只有一台机器」这个事实。

同一段在磅还会反复进入稳定（读数在阈值附近抖动，或提前 `ResetCycle` 后重量仍高又稳定一次）。若每次稳定都建单并升 `Pending`：

1. 已上传的这一称重会再传  
2. 平台侧堆积重量相近、车牌在 A/B 之间跳变的无效单  

状态：重复上传的现场后果为 Human 已知；「提前收口后状态机会立刻再稳定」为源码归纳（`INFERRED`），见下一节。

因此繁忙开关至少要同时有两道门闩，缺一不可：

| 门闩 | 作用 |
|------|------|
| 归属 | 只有一台识别机，不能靠 `Enter` / `Exit` 分侧。下磅后的单仍要上传；异常只是标记，不代替上传条件 |
| 一次一传 | 本段在磅已经升过 `Pending` 之后，后续稳定边沿不再建单、不再上传，直到出现新的一车（例如先见到低于阈值的空磅，或重量相对已上传值有明确的新稳态） |

## 3.1 地磅变化曲线不是必要判断条件

现场没有连续保存的地磅数值曲线，也捕不到「上磅 / 下磅形状」当规律。源码与此一致：[`WeighingStreamPipeline`](../../repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/WeighingStreamPipeline.cs) 每 `StabilityCheckIntervalMs`（默认 200ms）取一个点，再用 `StabilityWindowMs / 间隔`（默认约 15 点、3 秒）做滑动窗口，算完即丢。`DistinctUntilChanged` 只把「稳 / 不稳」往下传。没有会话级曲线、没有落盘。

| 判断 | 要的信号 | 要整段曲线吗 |
|------|----------|----------------|
| 选哪张牌（误识别、同一台机器上的 A 与 B） | 这一台机器的推送序列里，牌是否只剩一张可信 | 不要。重量形状分不出两张牌，现场也没有第二台机器可标进出 |
| 同一段在磅不要再传 | 本段已经升过 `Pending` 的闩，加上重量是否仍高于 `MinWeightThreshold` | 不要。阈值穿越就是空磅边沿 |
| 没看到空磅就想认「又来一辆」 | 活读数是否离开上一笔已写下的单车稳态。各车平均约 45 吨时，相邻两辆的单车稳态可以只差不到 `MinWeightDiff`（默认 1 吨，今天用于运单匹配） | 不要整段曲线。留上一笔稳定重量即可 |

所以繁忙模式的重量条件停在：当前是否过空磅阈值、当前约 3 秒窗口是否稳定、上一笔稳定重量是多少。先把这三项用上。整段变化曲线留到有 Human 要求「按上下磅形状拆车」时再单独立项。

## 3.3 文档时序图与 Graph 重放

两者都不用场地。输入都是脚本：约 45 吨的平稳段、0.5 吨空磅、同一台识别机的牌。叠车活读数是写死的示意。

| | `03` / `07` 的时序图 | Graph 重放 |
|--|----------------------|------------|
| 做什么 | 人把每个场景的预期写成表和图：几笔、什么重量、哪张牌 | 程序按同一脚本跑两套规则，打出实际的笔数、重量和牌 |
| 规则从哪来 | 读源码后写进表里。表改了，结果就改了 | 重放代码里的稳定窗、状态和收口。和表不一致时，这一次 cook 失败 |
| 留下什么 | 文档 | `runs/` 里的一次证据。P0–P3 只说明重放与 `07` 一致 |
| 改不了什么 | 现场合重、道闸时序 | 同样改不了。道闸行保持未模拟 |

时序图是预期。Graph 是把这份预期拿去跑。两边一起改场景；只改图、不重跑，图上的新结果仍然只是写出来的。

## 4. 叠车再建单（源码归纳）

`ResetCycle` 只清 `recordId` 与本周期 LPR 候选，**不**把重量清零。状态流在 `OffScale` + `weight > MinWeightThreshold` 时会立刻再进 `WaitingForStability`。

若两车叠在磅上、读数仍落在稳定窗口内：

1. 第一单在稳定后被提前收口并 `ResetCycle`  
2. 管道看到 `recordId == null` 且重量仍高 → 再次 `WaitingForStability` → 可能再次 `WeightStabilized`  
3. 第二单的 `TotalWeight` 可能是**叠车合重**，而非后车单车重  

状态：重放已核对 `ResetCycle` 本身不改状态。run `pipelines/graphs/materialclient/urban-busy-weighing-sim/runs/2026-11-10T114324`。只清记录时，重量仍高也不会立刻再建单。若收口时把状态写成 `OffScale`，下一采样在窗口仍稳定时就会再建单。现场合重仍未测量。

## 5. 车牌滞后于稳定抓拍

稳定瞬间会立刻抓拍并建单。LPR 事件常晚于该时刻；现行下磅收口仍可用 `EnablePlateRewrite` / `FinalizeWeighingCycleAsync` 内的最频繁车牌再写一次。

提前升 `Pending` 会缩短改写窗口：

- 无牌 → `EmptyPlate` 异常  
- 无 LPR 附件 → `CaptureFailure`  
- 上传队列可能先把异常单发出去（是否允许取决于产品）

状态：`INFERRED`。

## 6. 道闸边沿

现行：`WaitingForDeparture` 开出口；`OffScale` 清会话。

若稳定后立刻结束周期并人为跳到可再建单的状态，出口道闸可能：

- 过早开闸（后车还在上磅）  
- 或与「等待下磅」语义脱节  

状态：`PENDING_VALIDATION`。本夹不改道闸逻辑；实现 change 须单独核对 `GateIoControlService` 与现场闸杆时序。

| 车牌归属 | 单机位序列。下磅后的单仍上传，异常只作标记。不读取 `UrbanInOutType` 当现场方向 |
| 测试 | 误识别不压过真牌；同一台机器先后出现 A 与 B 时不绑错；重复稳定不产生第二张 Pending |

以上不是授权清单；effort 开 change 后只写 `.openspec.yaml`。

## 8. 建议的决策顺序

1. 定义「磅上这一辆」的牌：只有一台识别机，误识别与双真牌时宁可不传。  
2. 定义一次一传：同一段在磅的重复稳定不得再上传。  
3. 叠车合重是否允许成为新单，还是必须先见空磅。  
4. 核对道闸是否与上传解耦。  
5. 以上有 Human 裁定后，再考虑设置开关和 `/opsx:propose`。
