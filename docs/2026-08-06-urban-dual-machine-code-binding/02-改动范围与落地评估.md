# 02 — 改动范围与落地评估

## 1. 目标（已确认）

| 场景 | 结论 |
|------|------|
| **A. 双机并存（同时在线称重）** | **已选定**（2026-08-06） |
| B. 主备切换 | 不采纳 |
| C. 仅预登记 | 可作为 A 的运营增强，非替代 |

选定方案：**项目级允许名单（最多 2）**；F4 改为成员校验；每台机 JWT 仍绑定本机码。

## 2. 方案对比

### 方案 1：允许名单（推荐，对应双机并存）

**模型**：项目级最多 2 个机器码；每台机 JWT 仍只含自己的 `machineCode`；验签改为 membership。

| 层 | 改动要点 |
|----|----------|
| **BasePlatform** | 存储从单字段升级为：`MachineCode` + `MachineCode2`，或子表/`JSON`/`分隔串`；`ActivateUrban` 从「覆盖唯一值」改为「加入名单（满 2 拒绝或替换策略）」；`BuildLicenseFile`/`RefreshJwt`：用**请求机**签发 JWT，且要求请求机 ∈ 名单 |
| **UrbanManagement** | `GovProject` 同步名单；`JwtAntiTamperService`：`jwtMachineCode ∈ allowed`；`RefreshJwt` 传**提交 JWT 对应机**而非单一权威机；激活代理同步改为 upsert 名单而非覆盖 |
| **MaterialClient** | 本地仍存本机码；激活失败提示「已满两台」；项目信息可展示「本机 + 已绑定台数」；`StaticLicenseChecker` 逻辑可不变（仍比对本机 claim） |
| **OpenSpec** | 新/改 specs：urban auth、F4 设备绑定、catalog 字段、项目信息展示 |

**优点**：语义清晰，两台可同时在线。  
**缺点**：跨三仓 + BP 库结构/运营 UI；需定义「第三台怎么办、如何解绑、是否踢旧」。

### 方案 2：维持单权威，仅优化换机体验（对应主备）

不改「只能一台有效」：

- 运营文档化：换机 = 重新激活  
- 可选：激活前提示「将使旧设备失效」  
- 可选：UM 管理端显示「当前绑定机」+ 手动清空机器码

**优点**：改动小、风险低。  
**缺点**：不满足「两台同时绑定」。

### 方案 3：复用 `Material_MachineCode` 多行表

物料产品已有 `Material_MachineCode`（ProId ↔ 多 MachineCode）。可为 5001 新开类似表或扩展现有表。

**优点**：多机存储自然。  
**缺点**：当前 ActivateUrban / LicenseFile / Catalog / F4 **完全未走该表**；改造面与方案 1 同级，且需理清与 `JC_ProductAuthority.MachineCode` 的主从关系，避免目录 API「按 ProId 取最新一条」丢第二台。

### 不推荐的捷径

- 仅改客户端、绕过 `StaticLicenseChecker` 或共享 JWT 文件：破坏设备绑定，安全与合规风险高。  
- 逗号拼接两个码塞进现有 `MachineCode` 字段而不改签发/验签：RefreshJwt 与 claim 会错绑，极易出现「两台都偶发 DeviceChanged」。

## 3. 可落地改动清单（方案 1 粗粒度）

### 3.1 BasePlatform（阻塞依赖，优先排期）

- [ ] 数据模型：第二机器码或子表；迁移与回填（现有单码 → 名单第 1 项）  
- [ ] `ActivateUrban`：满员策略（拒绝 / 替换最旧 / 需运营解绑）  
- [ ] `LicenseFile` / `RefreshJwt`：按请求 `machineCode` 签发，且校验 ∈ 名单（**现状 BuildLicenseFile 用库中单字段写 claim，双机时必须改**）  
- [ ] 授权管理页：展示/编辑最多 2 台；解绑入口  
- [ ] 项目目录 API：`MachineCode` 字段契约（主码？列表？兼容旧 UM 拉取）

### 3.2 UrbanManagement

- [ ] `GovProject`：`MachineCode` → 名单结构（或 `MachineCode` + `MachineCodeSecondary`）+ EF 迁移  
- [ ] `UrbanAuthActivateAppService`：同步名单，禁止无脑覆盖导致误踢  
- [ ] `JwtAntiTamperService` F4：相等 → 成员包含  
- [ ] `RefreshJwt` 入参：使用客户端 JWT 中的 machineCode（已通过成员校验）  
- [ ] `GovProjectPullManager` / DTO / Blazor 项目表单  
- [ ] 单测：双机均 Pass；第三台/名单外 Fail；旧单码数据兼容

### 3.3 MaterialClient

- [ ] 激活错误文案与「已绑定两台」分支  
- [ ] 项目信息 UI（可选显示绑定台数/本机是否在名单）  
- [ ] 设备吊销流程：仅当本机被移出名单时触发（勿因第二台加入而踢第一台）  
- [ ] 回归：启动门闩、恢复窗、上传 `SubmitMachineCode`（可不动）

### 3.4 Monospec / OpenSpec

- [ ] `proposal` / `design` / delta specs / `tasks`（主仓库 `openspec/`）  
- [ ] 明确 Impact：BasePlatform（仓外）、UrbanManagement、MaterialClient  
- [ ] 更新 `urban-project-info-display`、反篡改/激活相关 specs（若已有归档变更可新开）

## 4. 关键产品决策（写入 proposal 前必须定）

1. **满 2 台后再激活**：拒绝 vs 替换指定槽位 vs 需运营后台解绑？  
2. **解绑权限**：仅 BasePlatform 运营，还是 UM 管理员也可？  
3. **两台是否共享同一 AccessCode / 同一授权有效期**？（预期是，仍一套项目授权）  
4. **历史项目**：仅有一台码时行为保持不变？  
5. **Catalog / 政府同步**：第二台码是否需要下发到外部系统？

## 5. 风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| BasePlatform 未改、只改 UM/Client | 高 | 权威仍单字段覆盖，双机无法成立 |
| F4 语义回退导致授权被共用 | 高 | 名单必须有上限与解绑审计 |
| Catalog 按 ProId 取 latest 丢第二码 | 中 | 拉取同步会把名单打回单码 |
| `RefreshJwt` 仍用权威单码签发 | 高 | 第二台拿到「第一台 claim」的 JWT → 本机 StaticLicenseChecker 失败 |
| 仅改字符串拼接无改验签 | 高 | 行为不可预测 |
| 工期低估「仓外 BP + 运营 UI」 | 中 | 往往占一半以上工作量 |

## 6. 工期与可行性（粗估，人天）

假设目标为 **场景 A 双机并存**，且 BasePlatform 可排期：

| 块 | 粗估 |
|----|------|
| 需求/OpenSpec 设计 | 1–2 |
| BasePlatform 模型+激活+签发+运营 UI | 3–5 |
| UrbanManagement 数据+F4+激活同步+测试 | 2–4 |
| MaterialClient 激活/提示/展示/回归 | 1–2 |
| 联调（两台真机 + 踢机/解绑） | 1–2 |
| **合计** | **约 8–15 人天** |

场景 B（接受换机踢旧）：**0–2 人天**（文案/运维说明即可）。

**可行性结论**：

- **技术上可落地**，路径清楚，无未知黑盒算法问题。  
- **组织上依赖 BasePlatform 改动**；若 BP 短期不可排期，则双机并存不可交付，只能做场景 B。  
- MaterialClient.Urban **单独改无法完成**真实双绑定。

## 7. 建议落地节奏

1. **产品拍板**场景 A 或 B（本调研默认用户期望接近 A）。  
2. 与 BP 负责人确认：第二字段 vs 子表、满员策略、目录 API 兼容。  
3. 主仓库开 OpenSpec change，tasks 分列 BasePlatform / UrbanManagement / MaterialClient。  
4. 先实现 BP 名单 + 签发，再改 UM F4，最后客户端提示与展示。  
5. 验收用例至少覆盖：  
   - 机 A、机 B 先后激活后均能上传  
   - 机 A 在 B 激活后**不被** DeviceChanged  
   - 机 C 第 3 台按策略失败  
   - 解绑 A 后 A 被吊销、B 仍可用  
   - 单机旧数据升级后行为不变

## 8. 与已确认期望的对齐

用户已确认：**同时在线称重** = 场景 A。

对应改动核心不是「多存一个字段给 UI」，而是：

**把「唯一权威机器码 + 覆盖写 + 严格相等」改成「最多 2 台允许名单 + 成员校验 + 按请求机签发 JWT」。**

客户端改动相对小；**服务端与 BasePlatform 是主体。**

开 OpenSpec 前仍待确认（见 §4）：满员策略、解绑权限、目录 API 是否下发第二码。
