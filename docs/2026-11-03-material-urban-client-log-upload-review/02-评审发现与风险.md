# 02 评审发现与风险

> 知识状态：标注于各条 · 日期 2026-11-03  
> 本文件是评审意见，**不**授权改代码。落地须 OpenSpec change。

## 1. 做得对的地方

| ID | 发现 | 证据 |
|----|------|------|
| G1 | 客户端启动不因日志能力失败而阻塞 UI | `MaterialClientUrbanModule` fire-and-forget + 后台最多 5 次注册 |
| G2 | 列表/文件路径有目录穿越与「必须在 Logs 根下」检查 | `ClientLogPullService` |
| G3 | 读日志用 `FileShare.ReadWrite`，降低与正在写的 Serilog 文件冲突 | 文件分片循环 |
| G4 | 扫描兼容标准日期目录与遗留布局 | `ClientLogScanner` |
| G5 | Admin / Realtime 拆进程后，命令走 internal HTTP、下载走网关直达 Realtime，职责清晰 | `RemoteClientLogAppService`、`ClientLogInternalApi`、Gateway 路由 |
| G6 | 缓存与业务附件卷分离（`um-clientlogs` vs Uploads） | compose + `ClientLogAppService` ContentRoot |

## 2. 风险与缺口

| ID | 级别 | 发现 | 影响 | 建议（未立项） |
|----|------|------|------|----------------|
| R1 | **高** | Hub 能力表与传输缓冲均为 **进程静态**（`DeviceStatusHub` + `ClientLogAppService` static ConcurrentDictionary） | Realtime 重启 →「在线客户端」清空，进行中拉取失败；**不能**水平扩 Realtime | 与 Phase 3 一致：保持单实例；中长期才外置字典 + sticky |
| R2 | **高** | 传输缓冲在内存拼文件（`_pendingFileBuffers`） | 大日志 / 并发多文件时 Realtime 内存尖峰，逼近 512m 上限可能 OOM 重启 | 限制单文件大小 / 并发；或落临时文件再 rename |
| R3 | 中 | 产品与文档称「上传」，实现是 **Pull**；`ApiPort`/`LocalLogApi` 易被当成 HTTP 上传口 | 排障时找错协议；新人可能加死代码 | 文档统一称「服务端拉取」；清理或标明未使用字段 |
| R4 | 中 | `MaxConcurrentDownloads=3` 注册了，客户端发送侧未见按该值限流 | 服务端若并行拉多文件，客户端可能打满 Hub | 服务端串行已部分缓解（`PullAndCache` 按文件循环）；显式对齐语义 |
| R5 | 中 | 按日拉取 = 列表 + 每文件最多 120s；Admin→Realtime HTTP 超时 30min | 日志很多的日期可能接近超时或长时间占住 Admin 电路 | UI 进度/取消；或异步任务化 |
| R6 | 中 | `ClientLogs.razor` **无** `@attribute [Authorize]`；spec `client-log-management-ui` 要求 `UrbanManagement.ClientLogs` | 能进 Admin 的人即可拉任意在线客户端日志（含敏感业务日志） | 若 Admin 将加鉴权，须把该权限一并落地 |
| R7 | 低 | Gateway 无独立文件日志；拉日志失败时 Gateway 侧证据弱 | 502/路由问题与 Realtime 问题不好分 | 见诊断 topic 建议：Gateway Logs volume |
| R8 | 低 | 列表超时 30s 与文件 120s 写死在代码 | 慢盘工控机易误报超时 | 配置化 |
| R9 | 低 | 断开时 Hub 按 ConnectionId 清理能力登记；客户端依赖重连事件再注册 | 短暂闪断后有窗口「页面显示不在线」 | 已有重连重注册；可接受 |
| R10 | **高**（正确性） | 空 `.log`：`totalChunks = Ceiling(0/64K) = 0`，客户端不发 chunk；服务端 `chunkIndex == totalChunks - 1` 永不成立 → 等满 **120s** 才记失败 | 按日拉取若含空文件会显著拖慢；误报超时 | 0 字节直接完成 TCS 或发「空文件」结束帧 |
| R11 | **高**（正确性） | `PullLogsByDateAsync`：`FilePath = input.DateFolder.TrimEnd('/')`，**覆盖**列表项的 `f.FilePath` | 根目录文件（`FilePath=""`）或遗留布局相对路径会被错拼；手动勾选拉取用真实 `FilePath`，两条路径行为不一致 | 改为 `FilePath = f.FilePath` |
| R12 | 中 | `PathMap`（下载 Guid→路径）仅在进程内存；Realtime 重启后旧 Guid 失效，须 browse/list 重建 | 书签式下载链接、刷新后偶发失败 | 确定性 Guid（已有路径哈希趋势）持久化或仅允许 browse 后短时下载 |
| R13 | 中 | Hub / `ClientLogController` / internal API 在本功能文件内**无** `[Authorize]`；能进 Admin 或能连 Hub 即可触及日志内容 | 工控机业务日志外泄面偏大 | 与 Admin 鉴权一并设计；下载与 `/ClientLogs` 静态同样审计 |
| R14 | 低 | 遗留面仍在：Hub 上 `RequestLogList`/`RequestFileContent`/`SubscribeToLogResponses`、`SaveCachedFileAsync`、能力里的 `ApiPort` | 双路径混淆排障 | 文档标明主路径；未用则后续 change 清理 |

补充核对来源：代码深挖与 [Explore Urban client log](9a4b09a7-3bae-4371-9d79-02b2d68e7c48) 一致；R10/R11 已在源码复验。

## 3. 规格 vs 实现（抽样）

| Spec | 实现对照 |
|------|----------|
| `client-log-signalr-pull`：启动连 Hub 并注册 | Urban 使用共享 `IDeviceStatusSignalRClient`，能力由 `ClientLogPullService` 注册；**不**自建第二条 HubConnection（优于重复连接） |
| `server-log-pull-api`：内存能力字典 + 静态 GetAll | 仍在；微服务后必须落在 Realtime 进程 |
| `client-log-view-page`：菜单「客户端日志」、路由 `/client-logs` | `AdminLayout` + `ClientLogs.razor` 一致 |
| `client-log-management-ui`：权限 `UrbanManagement.ClientLogs` | **页面层未见强制**；是否另有全局过滤器未证 |

## 4. 排障清单（运营）

拉取失败时建议顺序：

1. 客户端是否 Connected，日志是否有 `Log capability registered successfully`。
2. Realtime：`GET /hubs/devicestatus` 是否映射（无 connection id 时期望 400）；`docker inspect` RestartCount / OOM。
3. Admin 容器访问 `http://um-realtime:8080/internal/client-log/online-clients` 是否 200。
4. 网关 `/api/app/client-log/online-clients` 是否 200；`/internal/...` 是否仍 404。
5. Realtime `/app/ClientLogs` 与 `/app/Logs/log-*.txt`；客户端本机 `Logs/` 是否确有目标日 `.log`。

## 5. 后续可选工作（非本夹范围）

1. **修正确性**：R10 空文件、R11 `PullLogsByDate` 路径（适合小 `fix-*` change）。
2. OpenSpec：权限与 Admin 鉴权对齐；或正式声明「验收环境无细粒度权限」（R13）。
3. OpenSpec：大文件落盘缓冲 / 大小上限，降低 R2。
4. 文档 / UX：文案从「上传」改为「拉取客户端日志」。
5. 运维：Realtime RestartCount + `um-clientlogs` 磁盘监控纳入巡检 Graph。

## 6. 总结句

功能在 **MaterialClient.Urban ↔ Realtime Hub** 上闭环可用，微服务拆分后命令面与下载面划分正确；结构风险绑在 **um-realtime** 进程状态，另外已确认两条正确性缺陷（空文件卡超时、按日拉取改写 `FilePath`），修它们比先做水平扩展更划算。
