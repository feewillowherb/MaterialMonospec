# AI Pipeline 设计哲学与生成草图

> **日期**：2026-08-13  
> **目标**：抽出一套**与具体业务无关**的 AI Pipeline 指导哲学，以及一份 AI 可直接执行的**生成草图**。给定任意场景需求，Agent 应能按本目录快速生成可重复的 pipeline 工件。  
> **范围**：抽象原则、本体、生成协议、图模型、sample。不含任何真实产品模块、页面或表名；**不含**三维内容宿主（DCC）场景与术语。  
> **状态**：设计完成；命令已落地：`/gen-pipeline`、`/run-pipeline` 与 `/gen-<family>-pipeline`、`/run-<family>-pipeline`（见 `.cursor/commands/`、`pipelines/`）。  
> **吸收**：既有生成/执行实践，以及管线 trait 的 Graph / Node / Socket / Gate 结构哲学（已剥离 DCC 宿主表述）。

---

## 这份文档解决什么

已有的 pipeline 实践（生成命令 / 执行命令 / `pipelines/<slug>/` / 证据包 / 人闸）证明了一件事：

> **Agent 不该「当场即兴干活」。Agent 应该先落下可重复工件，再按工件跑，最后把证据交给人。**

若每次换场景都重写一套命令与目录约定，成本会线性膨胀。需要的是：

1. **哲学**：无论场景是观察界面、导入数据、探测接口还是对账，判断标准不变。  
2. **草图**：一份填空协议。场景进、族出、工件出。AI 按卡片生成，而不是从零发明结构。

本目录是**元设计**（meta-design），不是某条业务 pipeline 的调研。

---

## 核心结论

| 结论 | 一句话 |
|------|--------|
| 同构 OpenSpec | `generate` 对 `propose`，`run` 对 `apply`：先工件，后动作 |
| 三层持久化 | 可提交配置 / 不可提交密钥 / 不可覆盖的 runs |
| 族，不是脚本 | 先把场景归入 **family**，再实例化；不要每条需求发明一种目录 |
| 图，不是散文 | 现行协议是可 cook 的 **Graph + Gate**；交接靠 Socket，认对象靠 Context |
| 证据优于神谕 | Agent 采证与自评；**人**判定业务对错；缺证必须声明 |
| 代码隔离 | 管线脚本默认 `experimental`；进业务必须经 OpenSpec 并引用该 Graph |
| 生成草图可执行 | 场景简述 → 填 `pipeline-brief` → 脚手架 →（可选）执行 |

## 一句话

> **AI Pipeline = 可提交的意图工件 + 可 cook 的 Graph（Socket 交接）+ 不可静默的 Gate + 不可覆盖的证据 run。用 family 吃掉场景差异；用 Goal 互斥避免两套现行验法；脚本隔离至 OpenSpec 落地。**

---

## 刻意排除

- 真实产品名、模块名、路由、库表、验证码接口  
- 三维内容宿主（DCC）场景：具体工具链、视口、场景对象、资产网格等  
- 某次 run 的截图/日志路径  
- 业务修复方案（那是 OpenSpec change，不是 pipeline）

需要对照「一条真实 pipeline 如何长出来」时，另读既有专项调研；**生成新场景时不要把专项调研当模板**，用本目录。

**落地入口（本仓）**

| 动作 | 命令 |
|------|------|
| 生成工件 | `/gen-pipeline` 或 `/gen-observe-pipeline` 等 |
| 执行 Graph | `/run-pipeline <slug>` 或 `/run-<family>-pipeline <slug>` |
| 实例目录 | `pipelines/<slug>/` |
