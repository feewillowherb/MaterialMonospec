## 2. 入口方案（D2）

目标 Docker 环境是宿主上的 Hyper-V 虚拟机，外部流量的路径是：`191.12.234.212:5233`（Windows 宿主）→ 虚拟机 IP → `um-gateway`（D13 后直接切 Phase 2 栈；网关发布虚拟机 `5333`。Phase 1 的 `um-app` 无网关形态见 D11，已不再使用）。两种方案的区别在于宿主上谁接住 5233。验收期（D8）宿主只需把 `5333` 转发到虚拟机 `5333`，与 IIS 的 5233 互不影响。

### D2-A：宿主端口转发，网关容器直接接流量

- 停掉 IIS 上占用 5233 的站点（释放端口）。
- 宿主把 TCP 5233 转发到虚拟机：`netsh interface portproxy add v4tov4 listenport=5233 listenaddress=0.0.0.0 connectport=5233 connectaddress=<虚拟机固定 IP>`（依赖 IP Helper 服务），或在 `New-NetNat` 方案下用 `Add-NetNatStaticMapping`。做法与现有 2222 → 22 一致。
- 宿主转发目标为虚拟机 `5333`（`um-gateway`）。TCP 层转发对 WebSocket 透明，且保留 Host 头。
- 回滚：删除转发规则 → 启动旧 IIS 站点。

### D2-B：IIS 保留 5233，只做反向代理（阶段 1 推荐）

- IIS 安装 **URL Rewrite** + **Application Request Routing (ARR) 3.0**，启用代理。
- 新建站点 `UM-Proxy`（应用池"无托管代码"），绑定 `*:5233`，平时保持**停止**。
- 唯一一条重写规则：`(.*)` → `http://<虚拟机固定 IP>:5333/{R:1}`（`um-gateway` 发布到虚拟机 `5333`）。
- 必配项：

| 配置 | 值 | 原因 |
|------|-----|------|
| ARR `preserveHostHeader` | `true` | tus `Location` 必须是 `191.12.234.212:5233` |
| WebSocket 协议（服务器角色功能） | 启用 | SignalR |
| ARR `responseBufferLimit` | `0` | SignalR SSE / LongPolling 不被缓冲 |
| ARR 代理超时 | ≥ 300 s | 客户端上传超时 240 s |
| `requestLimits maxAllowedContentLength` | ≥ 16777216（建议 33554432 留余量） | 附件上传 |
| 移除 WebDAV 模块/处理程序；允许 `PATCH`/`DELETE`/`HEAD` | — | tus |
| 服务器变量 `HTTP_X_FORWARDED_PROTO` = `http` | 在重写规则中设置 | tus `Location` 协议 |

- 切换 = 停旧站点、启 `UM-Proxy`；回滚 = 反过来。两站点绑定相同端口，同一时刻只能启动一个。
- 应用不再由 IIS 托管，IIS 只是"转发器"，满足 C4。稳定后可改为 D2-A，彻底退出 IIS。
