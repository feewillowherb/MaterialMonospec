# 05 部署、切换与回滚

## 1. 宿主可行性（FEV：Unknown → Experiment → Evidence → Verdict）

MSSQL 官方容器镜像只有 Linux 版（Windows 版 SQL Server 容器镜像早已停止维护），因此"MSSQL 跑在 Docker 里"等价于"这台 Windows 主机必须能跑 Linux 容器"。Docker Desktop 不支持 Windows Server，且商用需授权，不作为选项。

| ID | Unknown | Experiment | 通过标准（Evidence） |
|----|---------|------------|----------------------|
| U1 | 主机 OS 版本、是否为虚拟机、是否支持虚拟化 | `systeminfo`、`Get-ComputerInfo`；若主机本身是 VM，确认宿主开了嵌套虚拟化 | Server 2022/2025 → 可走 WSL2；Server 2019 → 只能 Hyper-V Linux VM |
| U2 | 能否运行 Linux 容器 | 方案 A：WSL2 + Ubuntu + Docker Engine；方案 B：Hyper-V Ubuntu VM + Docker Engine。各跑 `docker run hello-world` 与 `mssql/server:2022-latest` | MSSQL 容器健康检查通过，可建库 |
| U3 | 外部能否访问 5233 | 从另一台机器 `curl http://191.12.234.212:<测试端口>/health/live` | WSL2 默认 NAT：需 `netsh interface portproxy` 或 WSL 镜像网络（mirrored）；或走 D2-B 由 IIS 反代到 `127.0.0.1` |
| U4 | 主机重启后无人登录时能否自动拉起 | 重启主机，不登录，等待 5 分钟后外部探测 | 工控客户端 7×24 依赖服务端；WSL 发行版默认随用户会话启动，需用"任务计划程序 → 开机时运行"启动 WSL + Docker；Hyper-V VM 设"自动启动" |
| U5 | 卷 IO 性能 | 在容器内对卷做 1 GB 写入/小文件读写测试 | WSL2 下卷放在 Linux 文件系统（ext4）内，**不要**挂 `/mnt/d`（跨 9P 文件系统很慢） |
| U6 | 现网 IIS 配置 | 导出站点绑定、应用池身份、WebSocket、URL 重写规则、`appsettings.secret.json` 实际值 | 无遗漏的隐藏配置（如 IIS 层重写/响应头） |
| U7 | 现网 Redis 在哪 | 查看现网 `Redis:Configuration`，主机上是否有 Redis 服务 | 明确是迁入容器还是继续用宿主 Redis |
| U8 | 镜像如何上机 | 主机能否访问 `mcr.microsoft.com` / 内网镜像仓库 | 不能则用 `docker save` / `docker load` 离线传输（mssql 镜像约 1.5 GB） |
| U9 | MSSQL 版本授权（D3） | 结合 [`04`](04-数据库迁移SQLite到MSSQL.md) §4.1 的库体积普查 | 确定 Express 或 Standard |

**Verdict 规则：** U1–U4 任一不通过 → 本蓝图的部署方式不成立，需回到 D1 重新选择（例如 MSSQL 改为宿主原生安装、仅应用容器化）。`FEASIBLE` 只说明方案可行，不代表交付完成。

## 2. 入口方案（D2）

### D2-A：网关容器直接监听 5233

- 停掉 IIS 上占用 5233 的站点（释放端口），`um-gateway` 发布 `0.0.0.0:5233`。
- WSL2 下需确保外部流量能进 WSL（U3）。
- 回滚：停网关容器 → 启动旧 IIS 站点。

### D2-B：IIS 保留 5233，只做反向代理（阶段 1 推荐）

- IIS 安装 **URL Rewrite** + **Application Request Routing (ARR) 3.0**，启用代理。
- 新建站点 `UM-Proxy`（应用池"无托管代码"），绑定 `*:5233`，平时保持**停止**。
- 唯一一条重写规则：`(.*)` → `http://127.0.0.1:15233/{R:1}`（`um-gateway` 发布到 `127.0.0.1:15233`；WSL2 的 localhost 转发对本机 `127.0.0.1` 默认可用）。
- 必配项：

| 配置 | 值 | 原因 |
|------|-----|------|
| ARR `preserveHostHeader` | `true` | tus `Location` 必须是 `191.12.234.212:5233` |
| WebSocket 协议（服务器角色功能） | 启用 | SignalR |
| ARR `responseBufferLimit` | `0` | SignalR SSE / LongPolling 不被缓冲 |
| ARR 代理超时 | ≥ 300 s | 客户端上传超时 240 s |
| `requestLimits maxAllowedContentLength` | ≥ 16777216（建议 33554432 留余量） | 附件上传 |
| 移除 WebDAV 模块/处理程序；允许 `PATCH`/`DELETE`/`HEAD` | — | tus |
| 服务器变量 `HTTP_X_FORWARDED_PROTO` = `http` | 在重写规则中设置 | tus `Location` 协议 |

- 切换 = 停旧站点、启 `UM-Proxy`；回滚 = 反过来。两站点绑定相同端口，同一时刻只能启动一个。
- 应用不再由 IIS 托管，IIS 只是"转发器"，满足 C4。稳定后可改为 D2-A，彻底退出 IIS。

## 3. 切换 Runbook（Phase 1）

### T-7 ~ T-1：准备

1. FEV（§1）全部通过，D1–D3、D6 已决策并获 Human `APPROVED`。
2. 现网接口基线已录制（[`02`](02-客户端接口兼容契约.md) §5）。
3. 用**现网库副本**在测试环境完整演练：建库 → 导入 → 校验报告 → 启动新栈 → 回放基线 → 真机冒烟。记录导入耗时，用来确定停机窗口长度。
4. 主机上镜像已 `docker load`，`mssql`、`redis` 已启动并通过健康检查；`.env`、`secrets/appsettings.secret.json` 已就位（内容取自现网 `appsettings.secret.json`，连接串改为 MSSQL、Redis 改为 `redis:6379`）。
5. D2-B：`UM-Proxy` 站点已建好、处于停止状态，规则已在测试端口验证。

### T0：切换窗口（选无称重作业的时段）

| 步骤 | 操作 | 检查点 |
|------|------|--------|
| 1 | 通知现场：服务端维护，客户端会自动重试 | — |
| 2 | **停止旧 IIS 站点 / 应用池** | 5233 无响应；旧进程已退出（Gov 同步 Worker 随之停止） |
| 3 | 复制 `UrbanManagement.db` **及同目录 `-wal`、`-shm` 文件**、`Uploads\`、`ClientLogs\` | 漏拷 WAL 文件会丢失最后一批写入 |
| 4 | `um-migrator` 建库（`InitialSqlServer`）→ 执行 SQLite 导入 → 生成校验报告 | 报告全部通过（[`04`](04-数据库迁移SQLite到MSSQL.md) §4.3） |
| 5 | 附件拷入 `um-uploads` 卷，运行附件存在性核对 | 缺失清单为空或已确认 |
| 6 | 启动 `um-app` + `um-gateway`（只监听 `127.0.0.1:15233`） | `/health/ready` 正常；日志含 `Attachment storage root resolved to /app/Uploads` |
| 7 | 本机回放基线（R1–R11 + Hub） | 结构与状态码一致 |
| 8 | 切入口：D2-B 启动 `UM-Proxy`；D2-A 网关改绑 `0.0.0.0:5233` | 外部 `curl` 通 |
| 9 | 观察 30–60 分钟 | 工控机 Hub 全部重连；积压上报回落；管理端可登录、照片可预览；政府平台无重复记录 |

### T+1 ~ T+3：观察期

- 旧 IIS 站点与 SQLite 副本**原样保留、不删除**。
- 每天对比流量计量日志中各接口的错误率。
- 观察期结束 → 标注 `docs/UrbanManagement/windows-server-deploy.md` 为 `HISTORICAL`，补写 Docker 版运维手册。

## 4. 回滚

| 触发条件（任一） | 示例 |
|------------------|------|
| 客户端契约接口 5xx 或结构不一致，且 30 分钟内无法修复 | `receive` 报错、tus `Location` 指向内部地址 |
| Hub 无法连接或推送失效 | 审批后客户端收不到 `WeighingRecordApproved` |
| Gov 同步异常导致漏报/重报 | 政府平台数据异常 |

操作：停新入口（D2-B 停 `UM-Proxy`；D2-A 停网关）→ 启旧 IIS 站点。

**回滚的数据问题（D6）：** 切换后写入 MSSQL 的数据旧栈看不到。

- 观察期内若需回滚：用导入工具的反向模式把 MSSQL 中 `CreationTime > 切换时间` 的记录（含**同步状态字段**）写回 SQLite；不带同步状态写回会导致 Gov Worker 重复上报。
- 若接受丢失：客户端已标记为"已上报"的记录不会自动重传，需评估现场补录成本。
- 因此回滚窗口应尽量短（建议当天内决定），超过窗口后只做前向修复。

## 5. Phase 2 上线（纯内部变更）

1. 新镜像带角色开关；网关路由表更新为 [`03`](03-目标架构与服务拆分.md) §5。
2. 顺序：`docker compose up -d um-migrator` → 停 `um-app` → 起 `um-ingest`、`um-console`、`um-worker` → 网关重载路由。
3. 确认**只有** `um-worker` 开启了 Gov 同步与快照开关。
4. 回滚：网关路由指回单个 `um-app`，停掉三个角色容器。客户端只会感知一次 Hub 重连。

## 6. 日常运维

| 场景 | 做法 |
|------|------|
| 发版 | 打新镜像标签 → `docker load`（离线）→ 修改 `.env` 的 `UM_TAG` → `docker compose up -d`（migrator 先跑） |
| 查日志 | `docker compose logs -f um-ingest`；文件日志在 `um-logs` 卷 |
| 改配置 | 修改 `secrets/appsettings.secret.json` → 重启对应容器（现有 `reloadOnChange` 对挂载文件不一定生效，以重启为准） |
| 开机自启 | Docker 服务开机启动 + 所有容器 `restart: unless-stopped`；WSL2 方案另需开机任务（U4） |
| 健康监控 | 外部定时探测 `http://191.12.234.212:5233/health/live`（仅网关健康），内部看各容器 `docker ps` 健康状态 |
