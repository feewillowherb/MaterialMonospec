# UrbanManagement 升级蓝图：IIS + SQLite → Docker + MSSQL + 服务拆分

> 状态：`ACTIVE` · 知识状态：蓝图整体为 `INFERRED`（基于 2026-11-02 代码考古），标注 `CONFIRMED` 的条目有代码证据。
> 本夹是**设计蓝图**，不是 OpenSpec change。进入实现前须 Human `APPROVED` 并走 `/opsx:propose`（建议按阶段拆成多个 change，见下文）。

## 1. 目标与硬约束

| # | 约束 | 含义 |
|---|------|------|
| C1 | **不改客户端代码** | MaterialClient / MaterialClient.Urban 二进制与配置均不动；旧版 GovClient（`POST /Api/Post`）同样不动 |
| C2 | **兼容旧客户端接口** | 路径、HTTP 方法、请求/响应 JSON 形状、枚举序列化、错误形状、SignalR Hub 路径与方法签名全部冻结 |
| C3 | **对外地址不变** | 客户端唯一入口仍是 `http://191.12.234.212:5233/`（REST、tus、`/hubs/devicestatus` 共用） |
| C4 | **托管改为 Docker** | 应用不再由 IIS inprocess 托管；IIS 与 Docker 同机共存 |
| C5 | **SQLite → MSSQL** | MSSQL 以 Docker 容器在本机部署；存量 SQLite 数据完整迁移 |
| C6 | **服务尽可能拆分** | 在 C1–C3 前提下，把数据面、实时面、管理面、后台任务拆成独立容器 |

## 2. 结论（TL;DR）

1. **可行，但"拆分"的上限由进程内状态决定。** `DeviceStatusHub`、`ClientLogAppService`、`TusAttachmentResultStore` 使用进程内静态字典（`CONFIRMED`），所以 Hub 与日志拉取必须同进程、tus 上传与 commit 必须同实例。合理形态是**共享数据库的模块化单体，按角色（role）多容器部署**，而不是各自独立库的微服务。
2. **对外 API 不变靠"网关 + 同一份代码"实现：** 一个网关容器独占 5233 端口，按路径前缀把请求转发到不同角色容器；所有角色用同一镜像、同一套 Controller/AppService 命名，ABP 自动路由天然不变。
3. **分三阶段落地：** 阶段 1 先做"原样搬家"（单应用容器 + MSSQL + Redis + 网关），完成 IIS 切换；阶段 2 按角色拆成 ingest / console / worker / migrator；阶段 3（可选）再把实时面与管理面、附件面进一步拆开。每一阶段客户端都无感。
4. **最大的未知数在宿主机，不在代码：** MSSQL 官方只提供 Linux 容器镜像，所以这台 Windows 机器必须能跑 Linux 容器（WSL2 或 Hyper-V），且外部流量要能进到 5233。须先做 FEV 实验（见 [`05`](05-部署与切换回滚.md) §1）。
5. **必须修的服务端坑（客户端无感）：** `decimal` 精度、容器时区、附件路径分隔符、Data Protection 密钥持久化、EF 迁移需为 SQL Server 重建基线、Gov 同步 Worker 切换时防止重复上报。

## 3. 阶段路线

```text
Phase 0  可行性 & 契约冻结
         ├─ FEV：宿主能否跑 Linux 容器 / 5233 外部可达 / MSSQL 版本授权
         └─ 抓取现网 IIS 接口基线（golden request/response），作为回归标准
Phase 1  原样搬家（lift & shift）
         ├─ EF Provider: Sqlite → SqlServer；新建 SQL Server 迁移基线
         ├─ DbMigrator：SQLite → MSSQL 数据迁移（含路径规范化）
         ├─ 容器化：gateway + um-app(role=all) + mssql + redis
         └─ 切换：停 IIS 站点 → 网关接管 5233（或 IIS 改为纯反代，见 D2）
Phase 2  角色拆分（同镜像多角色）
         ├─ um-ingest   客户端数据面（REST 上报、附件、激活、Legacy）
         ├─ um-console  Blazor 管理端 + SignalR Hub + 日志拉取
         ├─ um-worker   Gov 同步 / 状态快照（全局单实例）
         ├─ um-migrator 一次性迁移任务
         └─ Redis SignalR backplane：worker 侧推送可达 console 上的客户端连接
Phase 3  深度拆分（可选）
         ├─ um-realtime（Hub + 日志）与 um-admin（Blazor）分离，日志拉取改内部 API
         ├─ um-attachment 独立；tus 结果表迁 Redis，可多副本
         └─ ingest 多副本（有状态部分已外置后）
```

## 4. 待人工决策（Decision Needed）

| ID | 决策 | 选项 | 建议 |
|----|------|------|------|
| D1 | Linux 容器运行方式 | A. WSL2 + Docker Engine；B. Hyper-V Linux VM + Docker；C. 不容器化 MSSQL | 由 FEV 结果决定；Windows Server 2019 无 WSL2，只能 B |
| D2 | 5233 入口归属 | A. 网关容器直接监听 5233；B. IIS 保留 5233 绑定，只做 ARR 反向代理到容器 | 阶段 1 选 **B**（回滚只需改一条 IIS 规则）；稳定后可换 A |
| D3 | MSSQL 版本/授权 | Express（免费，单库 10 GB 上限）/ Standard（需授权）/ Developer（**禁止生产**） | 先评估库体积；`LegacyWeighingRejectStagings` 存 Base64 不限长，需关注 |
| D4 | 拆分止步于哪个阶段 | 阶段 1 / 2 / 3 | 至少到阶段 2；阶段 3 视运维能力 |
| D5 | 网关实现 | YARP（.NET 项目）/ Nginx（零代码） | **YARP**：路径匹配默认大小写不敏感，天然兼容 `/Api/Post` 与 `/api/...` 混用 |
| D6 | 回滚窗口内的新数据 | 接受丢失 / DbMigrator 反向导出 | 窗口限当天；DbMigrator 预留 `mssql→sqlite` 应急方向 |
