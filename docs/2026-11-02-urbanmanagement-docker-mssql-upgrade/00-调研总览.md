## 2. 结论（TL;DR）

1. **可行，但"拆分"的上限由进程内状态决定。** `DeviceStatusHub`、`ClientLogAppService`、`TusAttachmentResultStore` 使用进程内静态字典（`CONFIRMED`），所以 Hub 与日志拉取必须同进程、tus 上传与 commit 必须同实例。合理形态是**共享数据库的模块化单体，按角色（role）多容器部署**，而不是各自独立库的微服务。
2. **对外 API 不变靠"网关 + 同一份代码"实现：** 一个网关容器独占 5233 端口，按路径前缀把请求转发到不同角色容器；所有角色用同一镜像、同一套 Controller/AppService 命名，ABP 自动路由天然不变。
3. **分三阶段落地：** 阶段 1 先做"原样搬家"（单应用容器 + MSSQL + Redis + 网关），完成 IIS 切换；阶段 2 按角色拆成 ingest / console / worker / migrator；阶段 3（可选）再把实时面与管理面、附件面进一步拆开。每一阶段客户端都无感。
4. **正式环境已切换（2026-11-04）：** 生产流量走 Docker Phase 3（MSSQL + Redis 容器、YARP 网关）；宿主对外转发 **`5233`（正式口）与 `2222`（SSH）**；**宿主侧 5333 验收旁路已退役**。VM 内 gateway 仍发布 `UM_PUBLIC_PORT=5333`（portproxy 目标），**不必**改成 5233。日常发版走 `ops/deploy-urban-acceptance`（SCP + 远端构建；探针 `5233`），**不要**再用 IIS `robocopy` 发正式包（IIS 手册已标 `HISTORICAL`）。
5. **已修的服务端坑（客户端无感）：** `decimal` 精度、容器时区、附件路径分隔符、Data Protection 密钥持久化、EF SQL Server 基线、Gov 同步仅 `um-worker` 单实例。观察期内仍按 [`05`](05-部署与切换回滚.md) §4 保留 IIS/SQLite 回滚能力。

## 3. 阶段路线

```text
Phase 0  可行性 & 契约冻结
         ├─ FEV：宿主能否跑 Linux 容器 / 5233 外部可达 / MSSQL 版本授权
         └─ 抓取现网 IIS 接口基线（golden request/response），作为回归标准
Phase 1  原样搬家（lift & shift）
         ├─ EF Provider: Sqlite → SqlServer；新建 SQL Server 迁移基线
         ├─ DbMigrator：SQLite → MSSQL 数据迁移（含路径规范化）
         ├─ 容器化：um-app(role=all) + mssql + redis（D11：Phase 1 无网关）；Uploads 经 SMB 共用 IIS 目录（D10）
         └─ 切换：停 IIS 站点 → 5233 指向 um-app（IIS 纯反代或宿主转发，见 D2）
Phase 2  角色拆分（同镜像多角色）
         ├─ um-ingest   客户端数据面（REST 上报、附件、激活、Legacy）
         ├─ um-console  Blazor 管理端 + SignalR Hub + 日志拉取
         ├─ um-worker   Gov 同步 / 状态快照（全局单实例）
         ├─ um-migrator 一次性迁移任务
         └─ Redis SignalR backplane：worker 侧推送可达 console 上的客户端连接
Phase 3  深度拆分（可选）
         ├─ um-realtime（Hub + 日志）与 um-admin（Blazor）分离，日志拉取改内部 API
         ├─ um-attachment 独立；tus 结果表迁 Redis，可多副本
         └─ ingest 多副本（有状态部分已外置后）
```
