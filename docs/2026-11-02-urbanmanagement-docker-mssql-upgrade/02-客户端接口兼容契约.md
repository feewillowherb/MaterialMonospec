# 02 客户端接口兼容契约（冻结清单）

> 本清单是升级的**验收标准**。任何阶段上线前，下列接口在新栈上的行为都必须与现网 IIS 一致。
> 客户端侧证据：`repos/MaterialClient/src/MaterialClient.Urban/Api/IUrbanManagementApi.cs`、`src/MaterialClient.Common/Api/IUrbanAuthApi.cs`、`UrbanTusAttachmentClient.cs`、`DeviceStatusSignalRClient.cs`。

## 1. 入口

| 项 | 冻结值 |
|----|--------|
| Base URL | `http://191.12.234.212:5233/`（HTTP，非 HTTPS） |
| Hub URL | `http://191.12.234.212:5233/hubs/devicestatus` |
| 鉴权 | Urban REST 无鉴权头；`/Api/Post`、`/api/urban/auth/activate` 匿名 |

**规则：** 不得引入 HTTPS 强制跳转（`UseHttpsRedirection`）、不得给上述接口加鉴权、不得改变端口或路径前缀（包括大小写：`/Api/Post` 是大写 `A`）。

ABP 自动路由由 **AppService 类名 + 方法名** 推导（如 `UrbanWeighingRecordAppService.ReceiveAsync` → `/api/app/urban-weighing-record/receive`）。拆分时**禁止重命名**这些类与方法，也禁止把它们挪进命名不同的新类。

错误形状：ABP 异常返回 `{error:{code,message,details,data}}` 与对应 HTTP 状态码；客户端虽未细解析，但仍按现网保持（同一套 ABP 管道即可保证）。

## 3. SignalR `/hubs/devicestatus`

协议：默认 JSON Hub 协议，传输由客户端协商（WebSockets 优先，回落 SSE / LongPolling）。

### 客户端 → 服务端

| 方法 | 参数 |
|------|------|
| `UploadStatus`（Send） | `DeviceStatusMessage` |
| `RegisterLogCapability` | `clientId`、`LogCapabilityInfo`、`proName` |
| `ReturnLogList` | `ClientLogListResultDto` |
| `ReceiveFileChunk` | `requestId`、`chunkIndex`、`totalChunks`、`byte[]`、`totalFileSize` |
| `ReceiveFileError` | `requestId`、`errorMessage` |
| `VerifyJwtAsync` | `jwtToken`、`proId` → `JwtAntiTamperResult`（`RevocationReason` 为**整数**枚举） |
| `GetClientProjectLicenseInfo` | `proId` → `ClientProjectLicenseInfoDto` |

### 服务端 → 客户端

`HelloResponse`、`DeviceStatusUpdate`、`UpdateClientLicense`、`ReceiveLogListRequest`、`ReceiveFileContentRequest`、`WeighingRecordApproved`。

**规则：** Hub 路径、方法名、参数个数与顺序、DTO 字段名、枚举表示（Hub 内 `RevocationReason` 用整数；不要因为给 Hub 统一加 `JsonStringEnumConverter` 而改变）全部冻结。Hub 的 `MaximumReceiveMessageSize`（16 MB）、`KeepAliveInterval`（15 s）、`ClientTimeoutInterval`（60 s）保持。

## 4. 代理层必须满足的传输要求

| 要求 | 原因 |
|------|------|
| WebSocket 升级透传（`Upgrade`/`Connection` 头） | SignalR WebSockets |
| 关闭响应缓冲 / 支持长连接（≥ 120 s 空闲不切断） | SignalR SSE / LongPolling 回落 |
| 放行 `PATCH`、`HEAD`、`DELETE`、`OPTIONS` | tus |
| 透传 `Tus-*`、`Upload-*` 请求与响应头 | tus |
| 请求体上限 ≥ 16 MB；tus 建议关闭请求缓冲 | multipart / Base64 / tus |
| `Location` 头不得泄露内部地址（`http://um-ingest:8080`） | tusdotnet 返回相对路径 `/api/urban-attachment/tus/<id>`，客户端按 `BaseAddress` 解析后发 PATCH（Phase 2 实测，`05` §5.2）；若改为绝对地址，必须是对外地址 |
| 路径匹配大小写不敏感 | `/Api/Post` 与 `/api/...` 共存 |
| 不改写 JSON / 不压缩改写 Content-Type | 契约稳定 |

`Location` 由 tusdotnet 根据请求的 Host / Scheme / PathBase 生成，因此应用必须启用 `UseForwardedHeaders`（信任网关网段），网关必须转发原始 `Host`（或 `X-Forwarded-Host`）与 `X-Forwarded-Proto`。

## 5. 回归验收方法

1. **基线抓取（Phase 0，现网 IIS）：** 对 R1–R11 与 Hub 各方法录制请求/响应样本（脱敏），保存 HTTP 状态码、响应头（重点 `Location`、`Content-Type`）、响应体 JSON 结构。建议用 `/gen-probe-pipeline` 生成 probe 类 Graph 承载，避免手工测试（权威流程见 `pipelines/AGENTS.md`）。
2. **影子回放：** 新栈启动后（未切流量），用同一批样本回放，对比结构与状态码（`recordId` 等动态值只比类型）。
3. **真机冒烟：** 用一台测试工控机只改 `appsettings.secret.json` 指向新栈临时端口（这是**测试机本地配置**，不是客户端代码变更），跑一轮：激活 → 称重上报（multipart 与 tus 各一次）→ 卡口/成品上报 → 管理端审批 → 客户端收到 `WeighingRecordApproved` → 拉取客户端日志。
4. **切换后观察：** 监控 `HttpTrafficMeteringMiddleware` 流量日志中各路径的 4xx/5xx 比例与切换前对比。

> 回放 PASS 只是 Pipeline 证据（P0–P3），不等于产品通过；上线仍需 Human `APPROVED`。
