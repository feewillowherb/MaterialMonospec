# headless 测试与改进建议

## 目标与分层（INFERRED 建议）

| 层 | 测试对象 | 真实依赖 | 应验证的结果 |
|---|---|---|---|
| 规则 | 稳定窗口、候选车牌优先级、匹配决策、重量换算 | 无设备、网络、数据库、窗口 | 给定输入序列产生确定的决策与理由 |
| 用例 | 上磅→稳定→创建→匹配→下磅；一轮上传 | fake 设备流、可控时间、替换 I/O | 状态变化、持久化次数、副作用意图、取消结果 |
| 持久化 | SQLite 查询、唯一性、事务与产品扩展 | 隔离 SQLite | 数据实际落库，失败边界可回滚/恢复 |
| 界面适配 | 命令参数、展示状态、消息订阅释放 | 必要时使用 Avalonia 测试宿主 | UI 与用例之间映射正确 |
| 硬件契约 | SDK 回调、串口协议、关闭与句柄释放 | 指定设备/原生 SDK | 独立于普通业务测试运行，保留环境与设备信息 |

无窗口不等于无依赖。测试名称中有 Integration 或 UI 也不能直接决定归类，应检查是否启动宿主、连接设备及访问网络。现有 UI.Tests 引用了 UI 与 AttendedWeighing 项目，见 `repos/MaterialClient/tests/MaterialClient.UI.Tests/MaterialClient.UI.Tests.csproj:10`；`Tests/DefaultDeliveryTypeStartupTests.cs:28` 已通过替身构建 ViewModel，但这不证明整个测试程序集均无需 UI 调度器。

## 推荐顺序

1. **优先：建立可重复执行的业务测试入口。** 在现有测试上识别纯规则、SQLite、设备三类，明确筛选标记。正常业务集合应断网、无设备、无窗口可运行；关闭生产 worker 与设备启动，不以“异常被吞掉”作为隔离手段。先记录实际结果，再设 CI 门禁。
2. **优先：修复已确认的 UI Repository 穿透。** 先覆盖详情加载与保存，再将数据访问迁入有业务意图的 Service；避免顺带清扫其他模块。
3. **随后：可控时间与稳定序列回放。** 让同一重量/车牌输入可快速重放；覆盖阈值边界、稳定前离磅、同车牌重复回调、稳定匹配后离磅去重、取消与关闭中到达的回调。
4. **随后：降低匹配与上传用例的构造成本。** 抽取纯决策和单轮上传入口；优先复用已有状态、策略与记录服务，保留产品变体差异。
5. **按证据决定：程序集拆分。** 先测量构建依赖、测试启动成本和 SDK 初始化路径，再决定 Common 拆分范围。不建议一次性重写为微服务或另造通用工作流引擎。

## 其他改进方向

- **故障可恢复性**：为上传明确业务幂等键、重试分类、退避与人工补偿。先追踪现有实现，验证远端成功/本地失败、附件部分成功、重启恢复，不能直接推定当前缺失。
- **可观测性**：称重周期、记录、上传尝试应能关联；记录状态迁移原因与耗时，避免记录凭证和原始敏感载荷。指标优先关注重复建单、待上传积压、连续失败与关闭超时。
- **生命周期**：关注 singleton 状态隔离、订阅 Dispose、取消传播及 SDK 回调与 UI 退出的竞态。真实 native 阻塞必须有设备验证，fake 无法证明句柄正确释放。
- **产品组合根**：核对 Urban、Recycle、主客户端各自启动的模块、worker、设备与设置默认值，增加组合根冒烟测试。Urban 必须保留开机启动和主窗口前台约束，headless 是测试入口，不是改变工控交互方式。
- **类型与依赖纪律**：纯规则默认不注册 DI；多值结果用命名 record；状态变更归类型自身，投影用 From/To，不新增 mapper Service；数据关联保持逻辑 Id，禁止引入数据库 FK。
