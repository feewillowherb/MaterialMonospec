## 主要发现

### 1. 界面层穿透数据边界

**CONFIRMED**：`repos/MaterialClient/src/MaterialClient.AttendedWeighing/ViewModels/AttendedWeighingDetailViewModelBase.cs:51`、`:76` 持有并通过 IServiceProvider 解析 WeighingRecord 与 Waybill Repository。与根仓 viewmodel-no-repository 规则冲突。

**INFERRED**：详情交互测试需要理解 Repository 与数据装配，业务查询边界难以独立复用。优先把详情查询与保存意图交给应用 Service，ViewModel 保留输入、展示、命令与 UI 调度。Service 写操作遵守 UnitOfWork；不要仅将 Repository 包进通用 CRUD 转发器。

### 2. Common 的程序集边界比业务边界宽

**CONFIRMED**：`repos/MaterialClient/src/MaterialClient.Common/MaterialClient.Common.csproj:5` 固定 win-x64，同文件引入 SQLite、ABP、ReactiveUI、System.Management、串口、FlashCap、System.Drawing，并复制两家设备 SDK 原生文件。

**INFERRED**：纯规则测试也会继承较大的构建与部署依赖面；这不证明执行时一定加载 SDK，也不证明不能无窗口运行。候选方向是先让纯规则不触发设备初始化，再按收益决定是否抽出独立业务程序集；硬件适配与平台限制留在边缘。不要以跨平台为前提阻塞 Windows headless 测试。

### 3. 匹配服务聚合多种变化原因

**CONFIRMED**：`repos/MaterialClient/src/MaterialClient.Common/Services/WeighingMatchingService.cs:137` 至 `:154` 同时依赖多个 Repository、平台 API、推荐逻辑和设置；`:229` 处理打印时间，`:1318` 处理推送完成状态。

**INFERRED**：数据查询、匹配判断、打印投影与远端同步变化集中在同类，测试替身成本较高。先按公开用例画调用链，再抽出匹配决策的纯输入/输出；查询与 I/O 留给协调层。partial 文件拆分本身不能证明职责分离。不建议按行数机械拆 Service。

### 4. 时间尚未形成可控测试边界

**CONFIRMED**：`WeighingStreamPipeline.cs:58`、`:74` 使用未显式传 scheduler 的定时 Buffer；`AttendedWeighingService.cs:132` 使用 DateTime.Now，`:335` 使用 Task.Delay。以上文件均在 `repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/`。

**INFERRED**：依赖真实时间的稳定窗口与退出竞态测试可能变慢或波动；尚未测得实际 flaky 比例。建议 Rx 时间通过显式 IScheduler 控制，普通计时通过 TimeProvider 控制，时间戳作为输入传入纯规则；两种时间机制需同一测试时间线。

### 5. Urban 轮询同时承担调度与批处理编排

**CONFIRMED**：`repos/MaterialClient/src/MaterialClient.Urban/Backgrounds/PollingBackgroundService.cs:58` 起在私有静态方法中解析多个 Service，处理称重及通行两类待上传列表、逐条容错与事件发布；外层 WithUow 包围整个批次。

**INFERRED**：独立验证“一轮上传”的入口不够直接。候选方向是暴露可注入的批次用例，由 Worker 只负责定时触发；该用例确有 I/O，满足 DI 门槛。批次 UoW 不等于长数据库事务（当前 isTransactional:false），不能仅据此宣称锁表。远端成功但本地状态保存失败的幂等性需要继续追踪上传 Service 和服务端契约，当前为 UNKNOWN。
