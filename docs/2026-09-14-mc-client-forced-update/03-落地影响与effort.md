# 落地影响与 effort

## 落地规模

**L（跨 MaterialClient / UrbanManagement，约 40万–100万 token）**

建议拆会话，不要一次改完两个仓：

1. UM：旁路更新宿主、清单、静态目录或 OSS URL、回报接口（不碰称重业务表）
2. MC：公共看守进程、版本号、下载与租约、三个 WinExe 接线
3. 铺开：第一版如何把看守和更新服务器地址送到已安装机器（见下）

## 第一版铺开（现有机器没有看守）

远程更新通道自己不会出现在还没装过它的机器上。第一版仍要一次接触：

- 安装包带上看守，并写入登录启动（值名按产品区分）
- 写入更新服务器 BaseUrl（三个产品都要，不能只配在城管的 `UrbanManagement` 段）
- 安装目录改为现场实际路径，且对该用户可写

这一次可以用现有 Inno，但是**一次性安装/迁目录**，不是日后的更新机制。之后只替换主 exe（及需要时的看守 exe）。看守自己若也要更新，用同一租约规则，且不能让看守在替换自己的那一段没有备份拉起手段——第一版可把看守做得很小、很少改，避免和主程序绑死同一发布节奏。

已装在 Program Files 的机器：这次接触时迁到可写目录，并改登录启动里的路径。不要假设所有机器路径相同。

## 会碰到的现有缺口（本需求内必须改，不是顺便重构）

| 缺口 | 处理 |
|------|------|
| 无运行时版本 | WinExe 写入 `<Version>`，清单用同一版本 |
| 自启默认关、值名冲突、Urban 未接线 | 改为按产品启动看守，而不是继续用 `WindowsAutoStartService` 的固定值名 `MaterialClient` 当保活 |
| 单文件锁定 | 旁路下载 + 进程外替换 |
| 配置会被安装包覆盖的风险 | 更新路径永不写 `appsettings*.json` 和数据库；与 Inno `onlyifdoesntexist` 对齐 |
| 主程序/Recycle 没有 UM 地址 | 新配置键，三产品都有 |

`WindowsAutoStartService` 的「设置里勾选开机启动」可以留着给人用，但不能当「必须在跑」的实现。两套不要写同一个注册表值。

## 开放问题

1. **称重中硬截止要多长？** 建议数分钟量级，且短于 30 分钟租约。若业务不允许切断正在过磅的一车，强制更新会在这一台上被无限推迟——需要确认能否接受硬切断。
2. **登录前要不要在跑？** 当前方案不做。若要，只能开机自动登录 + 登录任务，不是更新服务器能解决的。
3. **第一版包放 OSS 还是更新宿主磁盘？** 两种都应由清单 `packageUrl` 表达。内网地磅机访问不了公网 OSS 时只能磁盘或内网 OSS。不要在客户端写死。
4. **谁可以发布版本？** 更新宿主需要单独的发布鉴权，不要复用地磅机业务登录。
5. **清单如果只走 HTTP**：sha256 防的是损坏和半截文件，防不了同一链路上的篡改。现场若是局域网 HTTP，把网络当可信，或另做清单签名。不要为此把业务 HTTPS 改造塞进同一 change。

## 建议的实现边界（若开 OpenSpec）

- 能力：客户端强制更新、看守保活、更新宿主清单
- 明确不包含：差分包、Velopack 换安装器、把界面改成 Windows Service、顺手重做 Inno 默认目录以外的安装体验、业务 OSS 密钥治理
