# 现状考古

## 现场客户端

三个 WinExe，均为 self-contained、单文件、`win-x64`。已发布体积约：

| 产品 | exe | 约体积 | 安装脚本版本 |
|------|-----|--------|----------------|
| 物料主程序（含有人值守窗口） | `MaterialClient.exe` | 341 MB | `scripts/installer/MaterialClient.iss` `1.0.26` |
| 城管 | `MaterialClient.Urban.exe` | 328 MB | `MaterialClient.Urban.iss` `1.0.17` |
| 资源化利用厂 | `MaterialClient.Recycle.exe` | 331 MB | `MaterialClient.Recycle.iss` `1.0.5` |

发布命令见 `scripts/publish.cmd`（及 `publish-urban.cmd` / `publish-recycle.cmd`）：`PublishSingleFile` + `SelfContained`。依赖已打进主 exe，现场更新单位就是这个 exe，外加要覆盖的 `appsettings`。运行中的单文件 exe 被锁定，不能就地覆盖，必须先退出再换文件。

csproj / `Directory.Build.props` **没有** `<Version>`。运行时不知道「当前安装版本」，版本只存在于 Inno 脚本的 `MyAppVersion`。三个产品版本号互不相关。

## 安装方式与路径

Inno Setup 共同点：

- `PrivilegesRequired=admin`
- `DefaultDirName={autopf}\...`（通常是 `C:\Program Files\...`）
- 主 exe `ignoreversion`；脚本把 `appsettings.json` / `appsettings.secret.json` 标成 `onlyifdoesntexist`（安装器默认不覆盖已有文件）
- **现场实际做法与脚本相反**：通常覆盖 `appsettings` 和主进程 exe。因为依赖已打进单文件，没有一堆 dll 要单独替换。脚本标志只说明 Inno 默认行为，不能当成更新策略。
- **没有** `AppMutex`，安装器无法干净关掉正在跑的实例
- `AppUpdatesURL` 是占位 `http://www.example.com/`，没有更新检查

现场要求「路径不统一、通常不在 C 盘」与脚本默认值不一致。更新逻辑不能读注册表卸载项里的默认路径，也不能写死盘符。

## 保活：只有可选登录自启

`WindowsAutoStartService`（`repos/MaterialClient/src/MaterialClient.Common/Services/WindowsAutoStartService.cs`）：

- 写入 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
- 值名写死为 `MaterialClient`（主程序与 Recycle 会互相覆盖）
- 值是 `Environment.ProcessPath`（这一点对「不在 C 盘」是对的）
- `SystemSettings.EnableAutoStart` 默认 `false`
- 只在 `StartupService`（主程序）和 `RecycleStartupService` 里同步
- **Urban 没有调用** `IWindowsAutoStartService`

这只保证「该用户下次登录时可能启动」。崩溃、被结束任务、更新后退出，都不会再拉起。没有计划任务「失败时重启」，没有看守进程。

三个 `Program.cs` 都已有单实例 Mutex，并在启动时 `Directory.SetCurrentDirectory(AppContext.BaseDirectory)`，注释写明注册表/计划任务自启时工作目录常为 `System32`。说明现场已经会碰到「非交互启动、cwd 不对」；新看守必须同样把工作目录钉在 exe 旁。

只有 Urban 有进程内重启钩子：`App.RequestProcessRestart()` → 退出后 `Process.Start(Environment.ProcessPath)`。主程序和 Recycle 没有。这解决不了「更新进程自己挂了」或「替换 exe 期间没人看守」。

## 与 UM 的现有连接

- UM 只有一个宿主：`repos/UrbanManagement/src/UrbanManagement.App`。`UseStaticFiles` 用于 `ClientLogs` 和默认 wwwroot，不是客户端安装包通道。
- 城管客户端用 `UrbanManagement:BaseUrl` 和 `SignalR:ServerUrl`（`/hubs/devicestatus`）连业务宿主。主程序 / Recycle 的 `appsettings.json` **没有** 这段，不能把「更新服务器地址」默认成城管 BaseUrl。
- `DeviceStatusHub` 是设备状态与连接生命周期，不适合当安装包下发通道；且只有城管在用。
- `MachineCodeService` 已能给出硬件哈希，可作回报身份，不是授权体系。
- UM 侧没有 OSS SDK。Material 主程序另有长期密钥直传 OSS（业务附件），更新包不应复用这条把密钥下发到地磅机的路径。参见 [客户端 OSS 直传调研](../2026-09-11-client-aliyun-oss-direct-upload/00-调研总览.md)。

## 对三条需求的直接含义

1. **推送**：运维发布一个版本后，客户端必须收下。传输上应以客户端轮询清单为准（地磅机经常离线）。SignalR「立刻检查」只能当提示，不能当唯一通道。
2. **30 分钟**：这是「允许不在跑」的上限，不是设计目标停机。约 330MB 应在主程序仍运行时下到旁路文件；真正退出只用于换 exe 和拉起。换包失败要留 `.bak` 并拉起旧进程，不能把失败态留成「没人在跑」。
3. **路径不统一**：定位只依赖看守进程自己的目录。安装目录必须对运行用户可写。若个别机器仍装在 Program Files，无人值守现场点不了 UAC，第一版不能依赖提权覆盖。
