## 2. 逐项深度分析与关键技术点

### R1：列表行内直接展示 2 张图片（替代「查看照片」弹窗）

- **范围确认**：
  - 移除 `WeighingRecord`、`CheckpointPassage`、`FinishedProductPassage`、`WeighingApproval` 4 个页面操作列中的「查看照片」按钮，以及专用的 `WeighingPhotoDialog`、`PassagePhotoDialog`。
  - 在上述 4 个表格中新增图片展示列（可合并为 1 列「照片」内并排 2 张缩略图，或分为 2 个图片列，如「全景图 / 车牌图」或「图 1 / 图 2」）。
  - **交互建议**：行内展示 2 张清晰缩略图，点击单张缩略图仍支持原生放大灯箱预览（如 Element Plus `el-image` 的 `preview-src-list`），兼顾「无需弹窗即可扫一眼看图」与「需要看清细节时可放大」。
  - **边界说明**：`WeighingApproval` 的「审批」弹窗内仍保留照片核对与本地替换上传功能（仅移除列表行的「查看照片」按钮）。
- **关键性能与后端设计约束（NON-NEGOTIABLE）**：
  - **禁止在列表中直接塞入大量原图 Base64**：若 1 页 20 条 × 2 张图 = 40 张原图 Base64，单次列表 JSON 将达 10–20MB，无论 Blazor Server（会直接触发 SignalR `MaximumReceiveMessageSize` 断连）还是 Vue SPA 都会严重卡顿。
  - **禁止列表逐行调 `GetApprovalAttachmentsAsync`（N+1 请求）**。
  - **推荐做法**：
    1. 列表 DTO（`UrbanWeighingRecordOutputDto` 与 `UrbanPassageListItemDto`）返回轻量的 **图片 URL 列表（最多 2 张，含槽位标签）**；
    2. `UrbanManagement.Admin` 提供带 `UrbanAdmin.Session` Cookie 鉴权的附件图片输出端点（支持 `Cache-Control` 浏览器缓存，可选缩略图尺寸参数），前端用 `<img loading="lazy">` / `el-image lazy` 按可视区懒加载。

### R2：全表格可滚动容器 + 所有表头支持手动调整列宽

- **交互目标**：
  - 表格外层采用固定高度或自适应视口的独立滚动容器（表头吸顶 `sticky`，横向/纵向独立滚动，不撑破外层卡片）。
  - **所有列**的表头右边界均可鼠标拖拽调整宽度，调整结果即时生效且不触发表格错位。
  - 可选增强：将用户手动调整的列宽按「页面 + 列 key」存入 `localStorage`，下次打开保持个人习惯（附带一键重置列宽）。

### R3：彻底修复项目搜索长名称展示缺陷

- **问题根因**：当前 `.searchable-select` 触发器宽度窄、下拉菜单跟随触发器窄宽度且文本溢出截断，萧山城管工程项目名称常达 25–45 字，前 10 字往往雷同（如「杭州市萧山区某某街道……」），导致用户根本无法区分选项。
- **修复方案**：
  - 下拉弹层宽度与触发器解耦：设置最小宽度（如 `480px`–`600px`，视口不足时自适应），选项文本允许**多行自动换行**完整展示项目名称，绝不在下拉列表里做单行省略；
  - 触发器输入框适当加宽，已选项目名过长时在 hover 时弹出完整名称 Tooltip；
  - 支持按项目名称关键词与对接码即时模糊过滤，支持键盘上下键选择与一键清空；
  - 统一复用到称重记录、异常审批、卡口进出、成品进出等所有含项目筛选的页面。

### R4 / R5 / R6 / R7：项目管理表格精简与抓拍机状态直出

- **列结构收敛**：
  - **项目地址（R4）**：默认列宽缩小（例如 `100px`–`120px`，溢出省略 + hover Tooltip 展示完整地址），把空间让给项目名称与状态列；用户需要时可通过 R2 手动拉宽。
  - **客户端 → 工控机（R5）**：表头文案改为「工控机」，状态筛选文案统一对应工控机在线/离线/未注册。
  - **授权过期时间格式改为日期（R7）**：`ProjectManagement.razor:97` 原先展示 `yyyy-MM-dd HH:mm:ss`，改为纯日期 `yyyy-MM-dd`（与同页离线授权弹窗保持一致，且同步收窄列宽）。
  - **新增「抓拍机」列 & 移除「设备」按钮与弹窗（R6）**：
    - 表格中直接展示抓拍机（LPR）状态徽标（在线 / 离线 / 未上报；若存在多路抓拍机可展示 `在线 2/2` 或 `异常 1/2` 并在 hover Tooltip 显示各路 IP/状态）。
    - 移除操作列的「设备」按钮与整个 `Device Detail Modal`；地磅（Scale）与摄像头（Camera）状态不再在 Admin UI 展示（后端心跳与存储数据保持不动，仅 UI 丢弃）。
    - **后端补齐**：在 `DeviceStatusAppService.GetClientListAsync` 返回的 `ClientConnectionDto`（或项目管理聚合结果）中直接带出该项目的抓拍机状态汇总，同时一并消除原先弹窗误传 `project.Id` 而非 `SourceProId` 的缺陷。
    - 精简后，资源化项目行若无「称重」跳转按钮，操作列甚至可进一步收窄或按产品按需展示。

## 3. 这 7 项需求对「是否迁移 Vue」的决定性影响

结合上述 7 项具体需求重新审视方案 A（留 Blazor）与方案 B（迁 Vue 3 + Element Plus），**天平已明显倒向迁 Vue 3**：

| 需求 | 留在 Blazor Server（手写 HTML/CSS）的真实成本 | 迁移 Vue 3 + Element Plus 的实现方式 |
|------|------------------------------------------------|--------------------------------------|
| **R1 行内 2 张图 + 预览** | 手写缩略图网格 + 自己维护灯箱组件 + 需小心避免 Base64 撑爆 SignalR Circuit | `el-image` 内置 `lazy` 懒加载、`fit="cover"`、`preview-src-list` 大图缩放/旋转/切换、`preview-teleported`，开箱即用 |
| **R2 全表滚动容器 + 表头拖拽调宽** | **高痛点**：Blazor 无内置列宽拖拽，必须手写 JS Pointer 事件修改 `<col>` 宽度，且 **Blazor 每次 `StateHasChanged()` 重新渲染都会与 JS 改过的内联宽度打架**，极易闪烁或复位 | `el-table` 开启 `border` + `height`/`max-height` **原生内置吸顶滚动容器 + 全表头拖拽调宽**，零手写拖拽代码 |
| **R3 长项目名搜索完整展示** | 重写 `.searchable-select` 的定位、弹层防溢出（靠近窗口边缘自动翻折）、换行与键盘导航 | `el-select`（`filterable` + `clearable` + `popper-class` 宽弹层自动换行 + `el-tooltip`），防溢出由 Popper.js 自动处理 |
| **R4/R5/R6 项目管理瘦身** | 删掉设备弹窗后工作量较小 | 删掉设备弹窗后，`ProjectManagement` 迁移为 Vue 的复杂度大幅下降，整体迁 Vue 工作量进一步可控 |

### 更新后的选型建议

- **结论**：在这 7 项需求（尤其是 **R1 行内图片预览 + R2 全表格拖拽调宽 + R3 复杂项目搜索弹层**）加入后，继续在 Blazor Server 手写 CSS + JS 桥接不仅开发与调试成本高，而且交互质感与稳定性（SignalR Circuit + DOM Diff 冲突）明显劣于 Element Plus。
- **推荐路线**：**直接采用方案 B（迁移 Vue 3 + Element Plus）**，将这 7 项修改需求直接作为新 Vue 版 Admin 的默认交互规格一次性落地，避免「先在 Blazor 里硬写一遍拖拽列宽和搜索框、过几个月又要重写成 Vue」的双重浪费。
- **落地规模复核**：因 R6 移除了设备详情弹窗、R1 移除了 2 个独立照片弹窗，迁 Vue 的 UI 总量反而比初评更精简；计入 R1（图片 URL 端点）与 R6（列表聚合 LPR 状态）两项轻量后端扩展，总规模仍为 **L**（单仓 `UrbanManagement`，约 **45万–75万 token**，分 3 个 Stage 实施）。
