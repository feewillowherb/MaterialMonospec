# 01 · 设计稿：萧山地磅 / 卡口 / 成品三路上报

## 1. 目标与范围

### 1.1 目标

统一描述向萧山渣土监管服务平台上报的三类数据通道，锁定：

- 各通道使用的 HTTP 路径与报文形态
- **卡口 vs 成品** 的区分规则（同接口、不同 `buildLicenseNo`）
- 地磅专用能力（称重上报）

### 1.2 范围内

| 业务通道 | 含义（设计语义） |
|----------|------------------|
| 地磅 | 地磅称重结果上报 |
| 卡口 | 场地出入口车辆抓拍进出记录 |
| 成品 | 成品相关进出记录（与卡口同协议） |

### 1.3 范围外（本稿不展开）

- 地磅心跳（`/sapi/sysdevicemng/heatBeat`）：**不做**
- 资源化利用厂 HMAC 批量接口（见 `docs/SyncDoc/杭州市资源化利用厂数据接入接口V1.0.md`）
- UrbanManagement 内部落库模型、重试队列的具体代码改动（留给 OpenSpec）
- 正式环境基址、证书、鉴权（SyncDoc 原文写「请求公共参数：无」；现场以联调为准）

## 2. 通道总览

```text
                    ┌─────────────────────────────────────┐
                    │  萧山监管平台 Base（示例）            │
                    │  http://{host}:8899                 │
                    └─────────────────────────────────────┘
                                      ▲
          ┌───────────────────────────┼───────────────────────────┐
          │                           │                           │
   ┌──────┴──────┐            ┌───────┴───────┐           ┌───────┴───────┐
   │   地磅       │            │    卡口        │           │    成品        │
   │ Weighbridge │            │    Gate        │           │   Product     │
   └──────┬──────┘            └───────┬───────┘           └───────┬───────┘
          │                           │                           │
          │ POST                      │ POST                      │ POST
          │ /sapi/v1/inoutRecord/     │ /sapi/v1/inoutRecord/save │ 同左
          │   lantu/saveRecord        │                           │
          │                           │                           │
          │ buildLicenseNo = L        │ buildLicenseNo = L        │ buildLicenseNo
          │ （平台颁发原值）            │ （平台颁发原值）            │ = L + "-02"
          └───────────────────────────┴───────────────────────────┘
```

| 通道 | 接口 | `buildLicenseNo` | 额外约定 |
|------|------|------------------|----------|
| 地磅 | `POST /sapi/v1/inoutRecord/lantu/saveRecord` | 原值 `L` | 需 `dataSource` 等地磅字段 |
| 卡口 | `POST /sapi/v1/inoutRecord/save` | 原值 `L` | 场地进出记录全文 |
| 成品 | `POST /sapi/v1/inoutRecord/save` | **`L + "-02"`** | **与卡口同一接口与字段集**；仅场地标识不同 |

> **硬规则（成品）**：成品与卡口使用**相同接口、相同请求体 schema**；唯一业务区分是在原有 `buildLicenseNo` 后拼接后缀 `-02`。  
> 例：卡口 `330106202212120101` → 成品 `330106202212120101-02`。

## 3. 地磅通道

**权威**：[`docs/SyncDoc/地磅数据上传对接接口（萧山）V1.0.md`](../SyncDoc/地磅数据上传对接接口（萧山）V1.0.md)

> SyncDoc 中另有心跳接口；**本设计明确不做心跳**，仅实现称重上报。

| 项 | 值 |
|----|-----|
| 路径 | `/sapi/v1/inoutRecord/lantu/saveRecord` |
| Method | `POST` / `application/json` |

关键字段（摘录）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `carNo` | 是 | 车牌号 |
| `carNoColor` | 是 | 黄 / 蓝 |
| `buildLicenseNo` | 是 | 场地标识原值 `L` |
| `dataSource` | 是 | 文档取值 `WEIGHBRIDGE_XIAOSHAN`（示例曾见 `WEIGHBRIDGE_TELECOM`，联调确认） |
| `inOutType` | 是 | `0` 进 / `1` 出 |
| `goodsWeight` | 是 | 货物重量 |
| `snapTime` | 是 | 称重时间 |
| `snapImages` | 是 | Base64 数组 |

## 4. 卡口通道

**权威**：[`docs/SyncDoc/杭州市工程渣土监管服务平台场地数据接口（萧山）V1.0.md`](../SyncDoc/杭州市工程渣土监管服务平台场地数据接口（萧山）V1.0.md)

| 项 | 值 |
|----|-----|
| 路径 | `/sapi/v1/inoutRecord/save` |
| Method | `POST` / `application/json` |
| `buildLicenseNo` | 原值 `L`（平台颁发的场地唯一标识） |

关键字段（摘录）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `carNo` / `carNoColor` / `carType` | 是 | 未识别车牌可填「无」 |
| `snapTime` | 是 | `yyyy-MM-dd HH:mm:ss` |
| `snapImages` | 是 | Base64 数组，去掉 Data URL 头；约定 `[大图, 小图]` |
| `deviceID` | 是 | `01` 进 / `02` 出 |
| `buildLicenseNo` | 是 | **卡口用原值 `L`** |
| `siteType` | 是 | `1` 工地 / `2` 消纳场（默认 `1`） |
| `areaCode` | 是 | 如 `330109` |
| `goodsWeight` | 否 | 千克 |
| `spaceName` | 否 | 场地名称 |

成功判定：响应 `code == 200`。业务错误示例：`501` 字段空、`502` 格式异常。

## 5. 成品通道

### 5.1 协议复用

| 项 | 与卡口关系 |
|----|------------|
| URL | **相同** `POST /sapi/v1/inoutRecord/save` |
| 请求字段集合 | **相同** |
| 成功 / 错误码 | **相同** |
| `buildLicenseNo` | **不同**：`{原 buildLicenseNo}-02` |

### 5.2 标识变换

```text
let L = 平台颁发的场地标识（与卡口配置同源）
卡口上报: buildLicenseNo = L
成品上报: buildLicenseNo = L + "-02"
```

约束建议（实现时）：

1. 后缀固定为字面量 `-02`（ASCII 连字符 + `02`），不要用其它分隔符。
2. 变换只做一次：若配置侧已存带 `-02` 的成品标识，上报层勿再二次拼接。
3. 地磅通道的 `buildLicenseNo` **不**拼接 `-02`（地磅始终用原值 `L`，除非运营另行颁发）。

### 5.3 示例对照

假设场地原标识 `L = 330106202212120101`：

| 通道 | `buildLicenseNo` 上报值 |
|------|-------------------------|
| 地磅 | `330106202212120101` |
| 卡口 | `330106202212120101` |
| 成品 | `330106202212120101-02` |

## 6. 地磅 vs 卡口/成品：协议差异摘要

| 维度 | 地磅称重 | 卡口 / 成品 |
|------|----------|-------------|
| 路径 | `/sapi/v1/inoutRecord/lantu/saveRecord` | `/sapi/v1/inoutRecord/save` |
| `dataSource` | 有（必填） | 无此字段 |
| 进出字段名 | `inOutType`（`0`/`1`） | `deviceID`（`01`/`02`） |
| 场地类型字段 | `placeType`（可选） | `siteType`（必填） |
| 区划 / 场地名 | 无 | `areaCode` 必填；`spaceName` 可选 |
| 成品后缀 `-02` | 不适用 | 仅成品通道 |

实现上建议拆两个 Client / 两个 payload builder，避免把地磅字段误塞进卡口报文。

## 7. 配置模型（设计建议）

命名 `record`，避免 tuple：

```csharp
// 概念草图 — 非最终实现签名
public record XiaoshanSiteUploadOptions(
    string BaseUrl,
    string BuildLicenseNo,           // 原值 L
    string? AreaCode,                // 卡口/成品必填来源
    string? SpaceName,
    string? DataSource               // 地磅；联调确认后固化
);

public static class XiaoshanBuildLicenseNo
{
    public const string ProductSuffix = "-02";

    public static string ForGate(string licenseNo) => licenseNo;

    public static string ForProduct(string licenseNo) =>
        licenseNo.EndsWith(ProductSuffix, StringComparison.Ordinal)
            ? licenseNo
            : licenseNo + ProductSuffix;

    public static string ForWeighbridge(string licenseNo) => licenseNo;
}
```

业务入口按通道选择变换函数，再映射到对应 HTTP Client。

## 8. 与既有 GovSync 的关系

- 历史联调路径 `/sapi/v1/inoutRecord/save` 与**卡口/成品**同族（见 `docs/gov-sync-postweight-analysis.md`）。
- 本设计新增明确的三通道语义；若现网 PostWeight 仅覆盖「单一场地进出」，扩展时需：
  - 区分调用方是卡口还是成品（决定是否加 `-02`）；
  - 另开地磅 Client（仅 `lantu/saveRecord`，不做心跳），勿与 `save` 混用同一 payload。

管线权威：`pipelines/graphs/govsync/xiaoshan-weighbridge/`、`xiaoshan-gate/`、`xiaoshan-product/`（见 `pipelines/AGENTS.md`）与后续 OpenSpec；本夹只定协议边界。历史单一 save 管线见 `_retired/2026-08/postweight/`。

## 9. 开放问题

| ID | 问题 | 影响 |
|----|------|------|
| Q1 | 地磅 `dataSource`：文档 `WEIGHBRIDGE_XIAOSHAN` vs 示例 `WEIGHBRIDGE_TELECOM` | 称重上报可能被拒 |
| Q2 | 成品 `-02` 是否由平台预先登记该虚拟场地，还是上报时动态识别 | 成品首次联调可能 4xx/业务失败 |
| Q3 | 同一物理场地是否共用一个 `L`，地磅/卡口/成品三通道是否全部启用 | 配置与运营流程 |
| Q4 | 卡口 `deviceID`（01/02）与地磅 `inOutType`（0/1）在业务上是否必须一一对应 | 进出语义一致性 |
| Q5 | 基址：文档示例 `172.18.34.209:8899` vs 既有联调 `191.12.15.58:8899` | 环境配置 |

## 10. 验收口径（设计级）

1. 地磅称重打 `lantu/saveRecord`，`buildLicenseNo` 为原值 `L`；**不上报心跳**。
2. 卡口打 `inoutRecord/save`，`buildLicenseNo = L`。
3. 成品打**同一** `inoutRecord/save`，`buildLicenseNo = L + "-02"`，其余字段规则与卡口一致。
4. 不把地磅专用字段（如 `dataSource`）写入卡口/成品报文；不把 `-02` 拼到地磅或卡口原值上。
