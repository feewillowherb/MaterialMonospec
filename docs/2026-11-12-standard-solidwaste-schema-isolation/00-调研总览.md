# Standard / SolidWaste 表结构独立维护

日期：2026-11-12。Lifecycle：ACTIVE。研究状态：PENDING_VALIDATION。

## 目标与来源

用户明确提出：将 Standard 与 SolidWaste 的表结构拆分，分别独立维护。前一条“拆分数据库”的表述已由用户修正为“拆分表结构”。本 Topic 记录该目标、当前源码证据及下一轮调查入口；不把候选方向写成已批准架构，不实施代码或迁移。

期望解决的问题：后续某一 Product 新增合同关系、产品字段或调整存储模型时，其表模型和迁移有明确归属，减少迫使其他 Product 一并升级和重新验收的情况。表结构拆分只解决数据边界；共享服务、启动与设备变更仍需独立评估影响范围。

## 原表结构调查范围

- 重点调查 Standard、SolidWaste 的称重记录、运单、产品扩展字段及相关关联表的归属。
- 识别材料、供应商、附件、配置、授权与会话等现有内核表是否继续共享，逐项形成归属结论。
- 研究独立 DbContext、模型快照、迁移历史和产品启动迁移选择，避免仅换目录却仍由共享迁移控制产品表。
- 研究既有数据库的无损升级、失败恢复与历史业务结果一致性。
- 保持 Urban、Recycle 现有数据兼容；若迁移共享表所有权会影响它们，必须明确列出，不能隐含改变。

物理拆分 SQLite 文件不作为当前目标。完整客户端重构、动态能力插件、全量 headless、合同功能实现及材料/供应商数据源切换均不在本 Topic 的实施范围；后两者只作为检验边界是否支持定制的示例。

## 原方案比较（数据库实施前）

**独立 Context / 独立迁移，不自动等于表结构独立。** 如果两个 Product 仍映射同一组物理表，或共享一个会传播字段变化的实体映射，仍需解释谁拥有表与版本。

下一轮必须区分并比较：

1. 仅将固废专属字段迁入扩展表，共享称重/运单仍保留。
2. Standard 与 SolidWaste 各自拥有产品业务表及迁移，公共部分仅保留经确认的基础设施与稳定契约。

第一种只能称“产品扩展表隔离”，不能冒充第二种完整的产品业务表独立维护。最终采用哪一种，需要先完成表归属与迁移影响调查。

## 初始结论状态（基于 5169b27e，数据库实施前）

- CONFIRMED：现有共享内核 Context 承载材料、供应商、称重记录、运单等；迁移历史常量中已有 Kernel、Urban、Recycle，没有 Standard / SolidWaste 专属历史常量。
- CONFIRMED：固废专属字段通过 ExtraProperties 扩展写入现有称重记录与运单。
- INFERRED：仅补一个 SolidWasteDbContext 不能自动消除共享模型变更带来的产品耦合。
- UNKNOWN：现场是否存在同库混合模式历史数据、各表的实际引用完整性，以及可支持的旧版本升级范围。
- PENDING_VALIDATION：最终表归属、映射方案、迁移与恢复路线、运行期服务切换及回归证据。

## 既有部署升级要求（用户补充，2026-11-12）

拆分后的版本需要支持现有已部署客户端更新后继续正常运行：保留历史称重、运单、附件关联、设置与待同步状态，完成必要的数据迁移，并验证新记录写入与历史数据读取。此处按停旧进程、升级、重启理解；没有要求进程内热更新或不停机切换。

旧版本支持范围、升级中断恢复及回退兼容需要后续用证据确定，不能把本要求写成已经实现的保证。新建空库可运行不足以满足本目标。
