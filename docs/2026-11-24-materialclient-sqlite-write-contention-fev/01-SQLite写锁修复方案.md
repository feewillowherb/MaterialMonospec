# 01 · MaterialClient SQLite 写锁修复方案

状态 `PENDING_VALIDATION`。适用范围是 SolidWaste 客户端。目前已有阶段性改动缩短建单 UoW，并移除了恢复完成和失败标记强制开启独立 UoW 的做法。现场锁源仍未确认，全库写入串行化仍在 OpenSpec 任务中。

## 方案对比

| 方案 | 解决的问题 | 代价与适用条件 |
|---|---|---|
| A. 同库业务写入串行 | 协调称重建单、后台恢复、自动匹配、轮询落库和人工编辑 | 首选主方案。需要逐一接入写入口，并核对 ABP 提交前的事件是否沿用外层事务。 |
| B. 缩短 UoW 和共享事务 | 缩短持锁时间，避免一次业务操作对同一文件发起独立事务 | 与 A 配合。需要明确哪些状态一起提交，哪些工作在提交后继续。 |
| C. 有界重试和恢复 | 处理短暂外部持锁，给持续失败的建单保留明确结果 | 仅重试可安全重放的操作。需要按 CycleId 核对是否已有记录，并避免重复执行副作用。 |
| D. 部署写入互斥 | 避免客户端与独立升级工具同时写部署库 | 部署流程需要确认客户端已退出、连接已释放，再启动升级工具。适用于已知的跨进程写入。 |

## A. 从业务写入口串行化

以实际 SQLite 文件为协调范围。在最外层写入入口取得写入资格，再开始 UoW。提交或回滚并释放 UoW 后，下一项才进入。普通查询保持原有入口。

优先接入称重建单和后台恢复，再覆盖自动匹配、轮询的本地保存阶段和人工编辑。ABP 提交前执行的事件如果参与当前操作，应沿用同一事务。需要独立提交的事件安排在提交后，避免回调再次排队等待自己所在的外层操作。

## B. 把事务限制在需要一起落库的步骤

- **称重建单**：记录和初始恢复状态一起提交，照片处理和后续匹配在事务释放后执行。
- **恢复任务**：认领和保存结果各占一段短 UoW。保存前重读记录并核对认领状态，避免用扫描时的旧实体覆盖并发修改。
- **自动匹配**：内核运单、称重匹配标记和固废扩展共同提交。验证两个 DbContext 复用实际连接和事务。
- **轮询同步**：先取得远端结果，再进入队列保存本地变化。外部请求和附件操作放在事务之外。

## C. 对暂时性锁冲突提供有界恢复

如果需要覆盖短暂外部持锁，针对 SQLite Error 5，在失败事务已释放后，按有限次数和时间预算重试业务写入。重试前按 CycleId 核对是否已经落库。耗尽预算时应让调用方看到明确的保存失败。若要求重启后继续恢复，需要单独验证尚未落库的周期是否有可靠的待处理记录。

## D. 在维护时协调其他写库进程

独立升级工具、客户端和其他会写同一部署库的运维工具应顺序执行。维护窗口内确认客户端退出，升级完成后再启动客户端。客户端内写入队列负责本进程内的竞争，部署流程负责已知的跨进程竞争。

## 验证顺序

1. 用真实文件和 ABP UoW 让称重建单与恢复写入重叠，验证后到的写入在先到事务释放后开始。再验证回滚、取消后下一项能继续。
2. 让匹配事务在内核写入后、扩展写入前失败，验证两边一起回滚。记录连接和事务标识，确认提交前的事件没有重复取得写入资格。
3. 接入轮询和人工编辑后，跑 API 称重与后台写入的组合验证，核对同一 CycleId 的建单数、恢复结果和日志。
4. 如实施有界重试，使用外部锁 Graph 分别验证锁在预算内释放和持续占用两种情况。已有合成 Run `fev-sqlite-write-contention-repro/2026-11-24T141850` 提供失败基线。

建议先完成 A 和 B 的称重与恢复链，并使用测试固定事务边界，再扩展到匹配、轮询和人工编辑。C 根据外部锁的失败体验决定是否实施，D 作为部署约定执行。
