# 使用手册：用 Pipeline 代替人力测试

## 1. 适用与不适用

### 适合用 Graph 替代人测

| 人测痛点 | Pipeline 做法 |
|----------|----------------|
| 每次发版点一遍同一页面 / API | `observe` / `probe` 固定步骤 + 新 `runs/` |
| 「本地库迁完了吗」靠肉眼看表 | `probe` / `ingest` dryRun + 结构化证据 |
| 客户端与 Web 两边对不上 | `reconcile` 双侧摘录 + diff |
| 政府对接要反复 POST / 对照回执 | `govsync` 下 `probe` / `transform` |
| 回归要留「当时绿过」的证据 | 永不覆盖的 `runs/<yyyy-MM-ddTHHmmss>/` |

### 不适合（仍要人 / 别硬套）

- 首次探索未知 UI（可先手测一轮，再**固化**成 Graph）  
- 真机硬件（地磅、海康实机）无 mock / 无注入点时  
- 需要改 `repos/` 业务代码才能「测过」——那是 OpenSpec，不是 pipeline  
- 生产写库且未声明可回滚 / 未确认 `dryRun: false`

## 2. 心智模型（对人测同事）

```text
以前：人操作 → 脑子里记住结果 → 口头「过了」
现在：意图 → 选/建 Graph → cook → runs/ 证据 → 人看报告闸门
```

与 OpenSpec 同构、**不是** OpenSpec：

| OpenSpec | Pipeline |
|----------|----------|
| `/opsx:propose` | `/gen-pipeline`（或 `/gen-<family>-pipeline`） |
| apply 改代码 | `/run-pipeline` cook（采证，默认真改产品） |
| archive | Graph 退役进 `graphs/_retired/`（见 AGENTS） |

## 3. 标准流程（从人测需求到证据）

### Step A — 说清「测什么」

用一句话写出：**产品**（materialclient / urban / …）、**断言**（看到什么算过）、**环境**（local / 指定库 / 站点）。缺一项就 Ask，**禁止猜**。

### Step B — 选型（先找现成）

1. 打开 [`pipelines/AGENTS.md`](../../pipelines/AGENTS.md) §3 选型算法与 §6.1 现行索引。  
2. 抽取 `domain` / `family` / `goal`。  
3. **0 命中** → 进入 Step C 新建；**1 命中** → Step D；**>1** → 人挑选。

### Step C — 没有图就生成（仍不写业务仓）

```text
/gen-pipeline
# 或 /gen-observe-pipeline · /gen-probe-pipeline · …
```

落盘位置：**必须** `pipelines/graphs/<domain>/<slug>/`（含 `pipeline.md`、`config.yaml`、`secrets.example.yaml`）。  
密钥只进 `secrets.local.yaml`（gitignore）。

### Step D — 执行 cook

```text
/run-pipeline <domain>/<slug>
```

Agent 应：

1. 读该图 `pipeline.md` + `config.yaml`（`graph.status: active`）  
2. 解析 secrets（缺则 Ask）  
3. Cook → 写入**新的** `runs/<本地时间戳>/`  
4. 产出报告；文末保持：**等待用户验收，尚未通过。**

### Step E — 人闸（你才是验收方）

打开本次 `runs/…/report`（或图约定的报告路径），对照 `pipeline.md` 的断言：

- 证据齐全且符合预期 → 你标记通过（会话/工单/PR 描述均可）  
- 缺证 / 红灯 → 修 Graph 配置或环境，**禁止**为「变绿」去改 `repos/` 业务逻辑（业务缺陷走 OpenSpec）

## 4. 与 OpenSpec / 发版的衔接

| 时机 | 建议 |
|------|------|
| OpenSpec `tasks.md` 写验收 | **指向**具体 Graph 路径 + goal，不要把步骤只写在 docs |
| Apply 完成后 | `/run-pipeline` 采证附在 PR / change 说明 |
| Archive 前 | 至少有一次与本 change 相关的绿证据包（若场景可自动化） |
| 修产品行为 | OpenSpec change → 子仓实现；pipeline **只**验证，不「顺手改产品」 |

## 5. 禁区（MUST NOT）

1. **覆盖**旧 `runs/` 目录  
2. Agent **宣布** L3 / 业务验收通过  
3. 把密码、连接串、Token 写进 `pipeline.md` / `config.yaml` / 提交的证据明文  
4. 用 runner **修补**产品缺陷冒充测试通过  
5. 为单次人测在业务仓塞临时开关（应用 `urban-license-probe` 一类正规图，或 OpenSpec）  
6. 新建 Graph 放在与 `_shared` 平铺的错误路径（见 AGENTS）

## 6. Family 怎么选（人话）

| 你想验证 | family |
|----------|--------|
| 页面/桌面长什么样、点得开 | `observe` |
| HTTP/API/健康、请求响应 | `probe` |
| 往库/文件灌数（先数后写） | `ingest`（默认 dryRun） |
| 两边数据是否一致 | `reconcile` |
| 本地派生文件/种子，不写生产 | `transform` |

细则与反模式见哲学目录；路径规则只认 `pipelines/AGENTS.md`。

## 7. 常见翻车与对策

| 现象 | 对策 |
|------|------|
| 没有 secrets | 复制 `secrets.example.yaml` → `secrets.local.yaml`，Ask 补全 |
| 图很多不知选哪个 | 按 goal 过滤；仍多则人点名 slug |
| cook 要写库 | 确认 `dryRun` / `environment`；非 local 先口头确认 |
| 证据里有密码 | 脱敏重跑；检查 collector 配置 |
| 「上次绿这次红」 | 对比两次 `runs/`；环境漂移优先于改业务 |
| 想测硬件抓拍 | 先评估是否有注入/mock（如 LPR 伪造手册）；无则保留人测 |

## 8. Agent 协作话术（可直接复制）

```text
用 pipeline 代替人测：
- 产品：UrbanManagement
- 断言：AccessCode 迁移后 Web 能起，称重列表 HTTP 200
- 环境：本地 _tmp 库副本，不写回原件
请按 pipelines/AGENTS.md 选型；没有合适图就 /gen-probe-pipeline，有则 /run-pipeline。
```
