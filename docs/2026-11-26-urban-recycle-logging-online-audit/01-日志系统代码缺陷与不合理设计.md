# 01 - 日志系统代码缺陷与不合理设计（Urban & Recycle）

知识状态：`CONFIRMED`（基于当前 `main` 分支源码核对）。生命周期：`ACTIVE`。

---

## L1. `ClientLogPullService` 放错分层，导致 Urban 与 Recycle 割裂

- **源码位置**：
  - `repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs`
  - `repos/MaterialClient/src/MaterialClient.Urban/Dtos/LogCapabilityInfo.cs`
  - `repos/MaterialClient/src/MaterialClient.Urban/Dtos/LogFileDto.cs`
- **问题现象**：
  - 底层依赖 `IDeviceStatusSignalRClient`、`ClientLogScanner`、`SerilogFileLogConfigurator`、`ILicenseService` 全部已经在 `MaterialClient.Common` 中；
  - 唯独 `ClientLogPullService` 及其 DTO 写在 `MaterialClient.Urban` 宿主项目里，导致 `MaterialClient.Recycle` 无法复用，若照搬只能再拷贝一份 400 行重复代码。
- **改进方向**：下沉至 `MaterialClient.Common`，Urban 与 Recycle 通过统一入口初始化。

## L2. `Client:Id` 空串回退缺陷与多模块身份口径分裂

- **源码位置**：
  - `repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs:68`
  - `repos/MaterialClient/src/MaterialClient.Common/Events/DeviceStatusEventHandler.cs:88`
  - `repos/MaterialClient/src/MaterialClient.Urban/Services/Updates/ClientOtaControlService.cs:63-64`
- **问题现象**：
  - `ClientLogPullService` 写法为 `_configuration.GetValue<string>("Client:Id") ?? Environment.MachineName`。一旦外部配置或环境变量存在 `"Client:Id": ""`，`??` 不会触发回退，`_clientId` 变成 `""`，导致 `TryRegisterCapabilityInBackground()` 在 `string.IsNullOrEmpty(_clientId)` 处直接静默跳过，远程日志功能完全失效。
  - 更深层问题是**身份口径不统一**：`DeviceStatusEventHandler` 硬编码 `Environment.MachineName`，`ClientLogPullService` 用 `??`，`ClientOtaControlService` 用 `IsNullOrWhiteSpace`，三处各自为战。
- **改进方向**：抽离单一 `ClientIdentityResolver`（纯静态方法，无 DI），统一全仓 `ClientId` 解析规则。

## L3. 0 字节日志文件导致远程拉取永久挂死至超时

- **源码位置**：
  - 客户端：`repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs:344-364`
  - 服务端：`repos/UrbanManagement/src/UrbanManagement.Core/Services/ClientLogAppService.cs:56-72`
- **问题现象**：
  - 客户端按 `totalChunks = (int)Math.Ceiling((double)fileInfo.Length / chunkSize)` 计算分片数，并用 `while ((bytesRead = await fileStream.ReadAsync(...)) > 0)` 发送分片；
  - 当日志文件大小为 0 字节时，`totalChunks == 0`，循环 0 次不发送任何分片，也不报错误；
  - 服务端 `OnServerFileChunk` 依赖 `chunkIndex == totalChunks - 1` 触发 `TaskCompletionSource.TrySetResult(true)`，导致请求一直悬空直至 120 秒超时。
- **改进方向**：0 字节文件显式发送单个空分片（`chunkIndex = 0, totalChunks = 1, data = []`）或在协议层显式完成空文件传输。

## L4. 路径穿越校验存在同前缀绕过漏洞

- **源码位置**：`repos/MaterialClient/src/MaterialClient.Urban/Services/ClientLogPullService.cs:320-331`
- **问题现象**：
  - 代码直接用 `!fullPath.StartsWith(_logBaseDirectory, StringComparison.OrdinalIgnoreCase)` 判断是否越界；
  - 未先调用 `Path.GetFullPath`，且 `_logBaseDirectory` 末尾未补目录分隔符（`\`），若同级存在 `LogsBackup\` 等同前缀目录可能误判通过。
- **改进方向**：对 `baseDir`（补尾分隔符）与 `fullPath` 均先做 `Path.GetFullPath` 再比较。

## L5. `ClientLogScanner` 历史胶水与 SignalR 大文件内存缓冲风险

- **源码位置**：
  - `repos/MaterialClient/src/MaterialClient.Common/Logging/ClientLogScanner.cs:44-48`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/ClientLogAppService.cs:42`
- **问题现象**：
  - `ClientLogScanner` 仍硬编码扫描字面量 `{YYYY}/{MM}/{DD}` 目录（历史 Serilog 路径模板写错的遗留兼容）；
  - 服务端拉取日志时将客户端经 SignalR 发来的 64KB 分片全部写入进程内 `MemoryStream`（`_pendingFileBuffers`），单文件上限 50MB、按日批量拉取多文件时易在 160MB–384MB 容器内存限制下造成明显内存压力。
- **改进方向**：
  - 短期：保留扫描兼容但收紧服务端分片落盘（直接流式写临时文件替代 `MemoryStream`）；
  - 中期：评估客户端收到日志拉取指令后直接通过 HTTP POST 上传（复用 `um-attachment` 或流式端点），SignalR 只传控制指令。

## L6. `MaterialClient.Recycle` 缺失远程日志能力

- **源码位置**：`repos/MaterialClient/src/MaterialClient.Recycle/MaterialClientRecycleModule.cs`
- **问题现象**：
  - Recycle 宿主已配置 `SerilogFileLogConfigurator` 写本地按日日志（`MaterialClient.Recycle-.log`），但未接入 `DeviceStatusSignalRClient` 与远程日志拉取服务；
  - 现场一旦出现称重或上传异常，运维无法从 Admin 远程拉取 Recycle 日志，只能远程桌面或跑现场拷文件。
- **改进方向**：随 L1 下沉后与 Urban 统一接入，通过 `ProductCode` / `ClientKind` 区分日志来源。

## L7. `ClientLogController` 缺失鉴权，且 `DownloadBatch` 存在临时 ZIP 删除竞态与磁盘泄漏

- **源码位置**：`repos/UrbanManagement/src/UrbanManagement.Realtime/Controllers/ClientLogController.cs:13-14, 71-90`
- **问题现象**：
  1. **匿名暴露风险**：`ClientLogController`（`/api/client-log/download/{id}` 与 `/api/client-log/download-batch`）未加 `[Authorize]`，且 `um-gateway` 将 `/api/client-log/**` 直接转发到 `um-realtime`，绕过了 Admin Cookie 鉴权；
  2. **临时 ZIP 清理 Bug**：`DownloadBatch` 打开 `FileStream` 准备返回 `File(stream, ...)` 的同时，在 `finally` 里立刻执行 `File.Delete(result.FilePath)`——在流尚未写出给浏览器时就尝试删除文件，Windows 下因句柄占用触发异常被空 `catch` 吞掉导致临时 ZIP 永久堆积，Linux 下则直接 unlink 掉句柄背后文件。
- **改进方向**：补齐鉴权（或短期签名票据），下载流使用 `FileOptions.DeleteOnClose` 或直接流式打包输出。
