# 03 - 目标重构设计与 1.0 兼容方案

创建日期：2026-11-26。生命周期：`ACTIVE`。知识状态：4 条核心设计原则与 1.0 兼容边界已由用户确认（`CONFIRMED`）；具体 OpenSpec 拆单实施待逐单推进。

---

## 1. 四大核心设计原则（已确认）

| # | 设计主题 | 目标形态 | 替代的旧设计 |
|---|---------|---------|-------------|
| **D1** | **30s 轻量心跳 + 外设快照** | 客户端每 30s 上报 `ClientHeartbeat`（含在线保活、版本、OTA 状态与全部外设当前快照），外设状态突变时 1s 真去重防抖立刻补发；服务端只写 **Redis**（TTL 90s，不写 SQL Server 热路径），90s 无心跳即判离线。 | 取消“无心跳、靠外设翻转顺带保活”与 3600s 超长超时；取消 `DeviceStatusEventHandler` 假节流与热路径 `[UnitOfWork]` 读库。 |
| **D2** | **日志拉取：SignalR 发指令 + HTTP Zip 上传** | Admin 触发拉取 → Realtime 经 SignalR 发极简控制指令 `RequestLogUpload(requestId, dateFolder, uploadUrl)` → 客户端将目标日期日志本地压缩为 `.zip` → 普通 HTTP multipart 流式 POST 上传到服务端落盘。 | 淘汰 SignalR 64KB 分片传输、客户端 `Task.Delay(10)` 限流与服务端 `MemoryStream` 全量内存缓冲，彻底根除 0 字节挂死与容器内存放大。 |
| **D3** | **Hub 单一会话 + Redis 真相源** | 客户端建连/重连后仅调 1 次 `RegisterSession`（一次性上报 `ClientId`、`ProductCode`、`ProId`、`ProName`、`AppVersion`、`Capabilities`）；Hub 内存仅保留一张路由表 `ClientId → ConnectionId`；所有可读状态统一写 Redis，Admin 列表直接读 Redis。 | 合并 `DeviceStatusHub` 中分裂的 3 套静态字典（`_connectionProIdMap` / `_logCapabilityRegistry` / `_otaStatusRegistry`）。 |
| **D4** | **共享客户端运维层（Urban & Recycle 统一）** | 将 `ClientIdentityResolver`（单一 `ClientId` 来源）、`ClientSessionAgent`（心跳/快照/会话）、`LogUploadAgent`（Zip HTTP 上传）、`OtaAgent` 下沉到 `MaterialClient.Common`；`Urban`（5001）与 `Recycle`（5020）100% 共用，仅传各自 `ProductCode`。 | 消除 `ClientLogPullService` / `UrbanUpdateService` 绑死在 `MaterialClient.Urban` 导致的重复；下线服务端平行空壳 `RecycleDeviceStatus` 与 `/recycle/device-status`。 |

## 2. 1.0 客户端兼容矩阵（允许功能降级，不破坏正常使用）

在 1.0 客户端（旧版 `MaterialClient.Urban` 与存量 `Fdsoft.Weight.GovClient`）逐步退网前，服务端采用 **Expand-Only + 能力分级展示** 策略：

| 客户端代际 | 称重与业务上传 | 在线与设备状态 | 远程日志拉取 | 远程 OTA | Admin 展示策略 |
|-----------|---------------|---------------|-------------|---------|---------------|
| **2.0 客户端**（Urban / Recycle） | 正常 | `RegisterSession` + 30s `ClientHeartbeat`（TTL 90s，全外设明细） | SignalR 指令 + HTTP Zip 流式上传 | 完整支持 | 全能力可用 |
| **1.0 SignalR 客户端**（存量 Urban 1.x） | 正常（无改动） | **保留 `DeviceStatusHub.UploadStatus` 入口**，写入同一套 Redis 键空间（标记 `ProtocolVersion = "1.0"`）；不报错、不断连 | 保留 `RegisterLogCapability` 静默接收（不抛 HubException）；Admin 标记“需升级 2.0”或按需降级 | 不支持（灰显提示） | 正常显示在线与基础设备状态，标注 `1.0` |
| **老客户端**（`GovClient` HTTP） | 正常（`/Api/Post` 无改动） | 保持既有 `legacy:{AccessCode}` 逻辑 | 不支持 | 不支持 | 标注 `Legacy` |

### 1.0 兼容硬约束
1. **绝不删除或破坏性修改** `DeviceStatusHub.UploadStatus(DeviceStatusMessage)` 的方法名与参数签名；
2. 1.0 客户端调用旧 `RegisterLogCapability` 时，Hub 允许静默返回成功（不因删除方法而触发客户端循环报错重试）；
3. Redis 键结构向前兼容：新字段全部可空带默认值，1.0 写入的记录反序列化无异常。

## 3. 建议 OpenSpec 拆单与落地规模（按 `effort-token-estimate`）

建议拆分为 **3 个独立 OpenSpec change** 按顺序落地（每单独立可测、可灰度、可回滚）：

| 顺序 | 建议 Change ID | 范围与核心产出 | 涉及仓库 | 预估档位 |
|------|---------------|---------------|----------|----------|
| **Change 1** | `unify-client-session-and-heartbeat` | ① 统一 `ClientIdentityResolver`；② 修复 `DeviceStatusSignalRClient._isStarted` 与 `DeviceStatusEventHandler` 假节流/去 `[UnitOfWork]`；③ 新增 `RegisterSession` + 30s `ClientHeartbeat`（含外设快照 + `AppVersion` + `OtaState`），Hub 合并三套字典为单一路由表 + Redis 真相源，**保留 1.0 `UploadStatus` 兼容**；④ 下线服务端 `RecycleDeviceStatus` 空壳并将 `MaterialClient.Recycle` 接入统一会话。 | `MaterialClient` + `UrbanManagement` | **L**（~40万–80万 token） |
| **Change 2** | `refactor-client-log-http-zip-upload` | ① 服务端新增流式日志 Zip 接收端点（`/api/client-log/upload-zip`）与 SignalR `RequestLogUpload` 控制指令；② 客户端在 `MaterialClient.Common` 实现共享 `ClientLogUploadAgent`（本地打 Zip + HTTP POST 上传，彻底消除 0 字节挂死与 64KB 分片内存缓冲）；③ Urban 与 Recycle 共用，Admin `/client-logs` 接入新拉取流（保留旧缓存浏览与下载）。 | `MaterialClient` + `UrbanManagement` | **M**（~20万–40万 token） |
| **Change 3** | `enhance-device-health-and-camera-polling` | 补齐摄像头定时巡检、纳入道闸 IO（`GateIoControlService`）在线状态、通过结构化快照展示多路外设明细与 Admin 异常筛选视角。 | `MaterialClient` + `UrbanManagement` | **M**（~15万–35万 token） |
