# 02 - 在线状态与设备监控代码缺陷与不合理设计（Urban & Recycle）

知识状态：`CONFIRMED`（基于当前 `main` 分支源码核对）。生命周期：`ACTIVE`。

## O1. Urban 与 Recycle 在线监控两套体系割裂，服务端存在平行空壳

- **源码位置**：
  - 客户端：`repos/MaterialClient/src/MaterialClient.Recycle/App.axaml.cs`、`MaterialClientRecycleModule.cs`
  - 服务端：`repos/UrbanManagement/src/UrbanManagement.Core/Services/RecycleDeviceStatusAppService.cs`、`repos/UrbanManagement/src/UrbanManagement.Admin/Pages/RecycleDeviceStatus.razor`
- **问题现象**：
  - `MaterialClient.Urban` 走 SignalR `DeviceStatusHub`（`UploadStatus`）上报客户端与外设在线状态；
  - `MaterialClient.Recycle` **完全没有启动 `DeviceStatusSignalRClient`**，也没有调用 HTTP `record-heartbeat`；
  - 服务端却额外建了 `RecycleDeviceStatus` 表、`RecycleDeviceStatusAppService` 和 Admin 独立菜单 `/recycle/device-status`，形成一套无客户端接入的平行空壳。
- **改进方向**：按统一架构原则，Recycle 直接接入同一套 `DeviceStatusHub` 在线与设备状态体系（以 `ProductCode=5020` 标识），下线独立的 `RecycleDeviceStatus` 空壳与菜单。

## O2. `DeviceStatusSignalRClient._isStarted` 首连失败后永不置 `true`

- **源码位置**：`repos/MaterialClient/src/MaterialClient.Common/Services/DeviceStatusSignalRClient.cs:213-237, 266-275`
- **问题现象**：
  - `StartAsync` 中仅在首次 `await _connection.StartAsync()` 成功时执行 `_isStarted = true;`（line 216）；
  - 工控机开机时若网络尚未就绪或服务端重启中，首次连接抛异常进入 `StartReconnectLoop()`，此时 `_isStarted` 保持 `false`；
  - 即使后台重连循环随后连接成功（`_connection.State == HubConnectionState.Connected`），后续每次 `UploadStatusAsync` 仍会在 line 268 `if (_connection == null || !_isStarted)` 命中早退，**永久将消息只入队不发送**。
- **改进方向**：取消冗余的 `_isStarted` 发送门禁（直接以 `_connection?.State == HubConnectionState.Connected` 为准），并在重连成功回调中确保刷新队列与状态。

## O3. `DeviceStatusEventHandler` 假节流 + 每次状态事件开 `[UnitOfWork]` 查 SQLite

- **源码位置**：`repos/MaterialClient/src/MaterialClient.Common/Events/DeviceStatusEventHandler.cs:46-95, 115-139`
- **问题现象**：
  1. **假节流（Bug）**：line 54-62 注释写着 `max 1 message per device type per second`，但 `if (ShouldThrottle(...))` 分支内部只做了 `eventData = latestStatus;`，**没有 `return` 也没有延迟合并调度**，代码继续往下照常执行 `UploadStatusAsync`，实际完全没有节流效果。
  2. **热路径数据库事务开销**：方法标注 `[UnitOfWork]`，每次设备状态事件都要开启 SQLite UoW 读取 `_licenseService.GetCurrentLicenseAsync()` 获取 `ProId`/`ProName`，在称重并发写库期间增加不必要的 SQLite 锁竞争。
  3. **身份硬编码**：line 88 直接写死 `ClientId = Environment.MachineName`，与 `Client:Id` 配置脱节。
- **改进方向**：
  - 改为真正的状态去重/节流（状态未变且在节流窗口内直接跳过，窗口到期补发最新状态）；
  - 缓存 `ProId`/`ProName`（仅在授权变更事件时刷新），移除事件处理器上的 `[UnitOfWork]`；
  - 改用统一的 `ClientIdentityResolver`。

## O4. 客户端无定时心跳，引发 Redis TTL 饥饿与掉线延迟双失真

- **源码位置**：
  - `repos/MaterialClient/src/MaterialClient.Common/Services/DeviceStatusSignalRClient.cs`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Hubs/DeviceStatusHub.cs`
- **问题现象**：
  - 客户端目前没有任何定时心跳机制，只有在外设状态布尔翻转时才调用 `UploadStatus`；
  - **正常工控机误报离线**：外设长时间稳定在线无状态变化时，超过 Redis Live TTL（2 小时）未刷新即被判离线；
  - **故障工控机发现过慢**：为缓解断连误判，服务端曾将 `ClientTimeoutIntervalSeconds` 设为 `3600`（1 小时），导致真正断电/断网的工控机延迟长达 1 小时才在 Admin 变灰。
- **改进方向**：
  - 引入轻量定时心跳（如每 30 秒一次，仅刷新 Redis TTL 与内存活跃时间，**不写 SQL Server / EF 热路径**）；
  - 将 SignalR `ClientTimeoutIntervalSeconds` 收敛回合理秒级（如 60–90 秒），实现分钟级掉线感知。

## O5. `DeviceStatusHub` 存在三套并行的客户端内存注册表

- **源码位置**：`repos/UrbanManagement/src/UrbanManagement.Core/Hubs/DeviceStatusHub.cs:33, 94, 746+`
- **问题现象**：
  - 同一台已连接的 `MaterialClient.Urban`，当前在 `DeviceStatusHub` 中分别维护在 3 个静态字典里：
    1. `_connectionProIdMap`（由 `UploadStatus` 首次触发写入）
    2. `_logCapabilityRegistry`（由 `RegisterLogCapability` 写入）
    3. `_otaStatusRegistry`（由 `ReportOtaStatus` 写入）
  - 三处各自维护 `ConnectionId → ClientId` 映射与断线清理逻辑；客户端启动时也要各自独立轮询重试注册；且全部驻留在单机静态内存中，一旦 `um-realtime` 容器重启，在线列表需等待客户端逐个重连并分别重新调用 3 个方法才能恢复完整视图。
- **改进方向**：收敛为单一的 `ClientSessionRegistry`（单次 `RegisterClientSession` / `ClientHeartbeat` 同时上报 `ClientId`、`ProductCode`、`ProId`、`ProName`、`AppVersion`、`Capabilities`、`OtaState`），统一生命周期与断线清理；必要时持久化快照到 Redis 供 Admin 直接读取。

## O6. 外设在线巡检存在覆盖盲区

- **源码位置**：`DeviceManagerService`、`LprDeviceOnlineStatusService.cs`、`GateIoControlService`
- **问题现象**：
  - 摄像头仅在启动时探测一次，运行期断网无定时巡检；
  - 道闸 IO（`GateIoControlService`）未纳入统一设备在线状态上报；
  - 多路相机 / 多路 LPR 在聚合上报时被压扁为单一布尔值，Admin 无法直接定位具体哪一路设备离线。
- **改进方向**：统一外设健康巡检接口，补充相机定时探测与道闸 IO 接入，通过 `AdditionalData`（结构化 JSON）携带每路设备明细。

## O7. 1.0 客户端列表显示「在线」，但点开「设备」弹窗为空（4 个精确根因）

- **源码位置**：
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/UrbanWeighingRecordAppService.cs:124`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/DeviceStatusService.cs:182-198, 215-255, 520-546`
  - `repos/UrbanManagement/src/UrbanManagement.Admin/Pages/ProjectManagement.razor:604-614`
- **4 个直接根因**：
  1. **称重 HTTP 上报调用 `TouchOnlineAsync` 只写在线、不写设备**：无论是无 SignalR 的老版 `GovClient`，还是踩中 O2（`_isStarted == false`）发不出 `UploadStatus` 的 1.0 `MaterialClient.Urban`，只要有称重记录 HTTP 提交，`TouchOnlineAsync` 就会往 `_clientConnectionCache` 写入 `IsConnected = true`，但 `_deviceStatusCache` 从未写入任何设备数据。
  2. **在线缓存与设备缓存分键存储、TTL 各自独立过期**：1.0 无心跳，外设长期无翻转时 `_deviceStatusCache` 先过期清空；期间称重请求又给 `_clientConnectionCache` 续了期，若尚未落过每日 EF 快照，查询设备即返回空列表。
  3. **Redis Key 大小写/格式不一致**：写在线连接缓存时先通过 `TryParseWireProId` 规范化为标准小写 `Guid`（`DeviceStatusService.cs:234`），但写设备缓存时直接用原始 `message.ProId` 作 Redis Key（`DeviceStatusService.cs:184`）；Admin 弹窗按小写 `project.Id.ToString()` 查询，Redis Key 大小写敏感导致“在线查得到、设备查不到”。
  4. **弹窗传参错位**：`ProjectManagement.razor:606` 的 `OpenDeviceModal` 传入 `project.Id.ToString()`，对 `Id != SourceProId` 的项目查错 Key。
- **改进方向**：D1 + D3 合并心跳与外设快照至同一份规范化 `ProId` 的 Redis 记录，并区分 `1.0 / Legacy / 2.0` 能力展示。

## O8. SignalR 闪断重连竞态：旧连接晚断把新连接一把打成「离线」

- **源码位置**：
  - `repos/UrbanManagement/src/UrbanManagement.Core/Hubs/DeviceStatusHub.cs:111-144`
  - `repos/UrbanManagement/src/UrbanManagement.Core/Services/DeviceStatusService.cs:326-366`
- **问题现象**：
  - 工控机网络闪断并在数秒内快速重连成功（建立新 `conn-new` 并上线）后，旧连接 `conn-old` 的 TCP 超时晚到触发 `OnDisconnectedAsync`；
  - `OnDisconnectedAsync` 未校验当前 `(ProId, ClientId)` 绑定的最新 `ConnectionId` 是否仍是 `conn-old`，直接调用 `UpsertClientDisconnectedAsync` 并把该实例全部设备标为 `Offline`，将已经在线的新连接误杀为离线。
- **改进方向**：单一会话路由表校验「仅当断开的 `ConnectionId` 等于当前注册的 `ConnectionId` 时才执行离线转换」。

## O9. 工控机克隆镜像 `Environment.MachineName` 撞名互相覆盖

- **源码位置**：`repos/MaterialClient/src/MaterialClient.Common/Events/DeviceStatusEventHandler.cs:88`
- **问题现象**：
  - 现场批量部署的工控机常由同一系统镜像克隆，`Environment.MachineName` 完全相同；
  - `DeviceStatusEventHandler` 硬编码 `Environment.MachineName` 作为 `ClientId`，同项目下多台工控机（或重装克隆机）在服务端互相覆盖在线状态、日志能力与 OTA 连接。
- **改进方向**：`ClientIdentityResolver` 优先使用显式 `Client:Id`，缺省时使用基于硬件特征的确定性 `MachineCode`（或 `MachineName + 短机器码后缀`），彻底避免同主机名冲突。
