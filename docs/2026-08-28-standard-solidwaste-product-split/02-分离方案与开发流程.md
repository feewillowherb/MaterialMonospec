# 02 · 分离方案与开发流程

## 不变量（沿用已采纳方案 B）

详见 [`../2026-08-28-materialclient-product-ef-isolation/02-方案细节.md`](../2026-08-28-materialclient-product-ef-isolation/02-方案细节.md)。

- 同一 `MaterialClient.db`；产品自己的 DbContext + `__EFMigrationsHistory_*`（若固废将来有独立表）。  
- 标准新装 **不**创建固废专用表（若有）。  
- 无跨 Context FK；`minimal-di` + `type-owned-methods`；ViewModel 不碰 Repository。  
- **禁止**把本次拆分写进未归档的 `refactor-common-product-layers`（范围已是 Urban/Recycle EF）。

固废字段今日在 ExtraProperties：**第一刀可以不建 SolidWaste 表**，只拆程序集与宿主；有独立查询/索引需求时再加 `Common.SolidWaste` 扩展表（对标 `UrbanWeighingExtension`）。

## 推荐形状

```text
内核：Common + Common.EntityFrameworkCore
        │
        ├── MaterialClient（WinExe）     ← 凡东智能物料验收 only
        ├── MaterialClient.SolidWaste    ← 新城管固废客户端（建议）
        ├── Common.SolidWaste            ← 固废 Service / ExtraProperties 扩展 / 导出 / 可选 DbContext
        ├── MaterialClient.Urban         ← 已有
        └── MaterialClient.Recycle       ← 已有；引用称重壳，不引用 Common.SolidWaste
```

`MaterialClient.UI` 仍只引用 Common。固废窗体可放在 `MaterialClient.SolidWaste` 或 `AttendedWeighing` 的固废切片项目；**不要**让标准宿主 ProjectReference `Common.SolidWaste`。

内核 Common 保留 `ISolidWasteRecordSideEffects`（或等价钩子）+ Null 实现；固废模块 `ReplaceServices`——与 Urban 侧效应同一模式，避免标准 exe 带上固废程序集。

## 建议 OpenSpec 切分（开发流程）

| 顺序 | 建议 change 名 | 内容 | 落地规模（effort 口径） |
|------|----------------|------|-------------------------|
| 0 | （当前）`refactor-common-product-layers` | 收口 / verify / archive | 已在做 |
| 1 | `refactor-solidwaste-product-layer` | `Common.SolidWaste`；钩子替换 `WeighingMatchingService` 内固废拷贝；标准宿主去掉固废 VM/导出 | **L**（约 40万–100万 token；AttendedWeighing 分支多、Recycle 条件要切开） |
| 2 | `add-solidwaste-host`（或并入 1 若同一会话吃不下再拆） | `MaterialClient.SolidWaste` WinExe + iss + 默认 `WeighingMode.SolidWaste` / ProductCode 5010 | **M–L** |
| 3 | `update-standard-host-product-boundary` | `MaterialClient` 仅 Standard；iss 显示名；授权不允许再进固废模式 | **M** |

开 change 时 effort **只**写入该 change 的 `.openspec.yaml`，不要写进 `proposal.md`。

## 固废 vs 标准：各自搬走什么

**搬进 `Common.SolidWaste` / 固废宿主**

- `SolidWasteService`、固废 Excel 导出与 DTO  
- `SolidWasteInfoExtensions` / `ISolidWasteInfo`（或变为类型归属方法后仍放产品程序集）  
- `SolidWasteWeighingDetailViewModel`、`SolidWasteModeFormView`、固废台账对话框  
- `SolidWasteTypeConfig` 的产品配置段  

**留在内核 / 标准宿主**

- `WeighingMode` / `ProductCode` 枚举值（判别用）  
- `WeighingRecord` / `Waybill` 表与通用匹配  
- `StandardWeighingDetailViewModel`、标准台账、磅差 UI  
- 地磅/相机等设备（产品通过策略注入，已有 Urban pipeline strategy 先例）  

**Recycle 专项**

- 列表条件从 `SolidWaste or Recycle` 拆成 Recycle 自己的策略/钩子，避免固废程序集成为 Recycle 依赖。

## 标准「也要分离」的含义

不是再复制一套 DbContext 叫 `StandardDbContext` 去映射内核表（那是方案倒退）。  
而是：**标准 = 内核消费者中的一个 WinExe**，与固废/Urban/Recycle **安装包互不捆绑**。内核 EF 项目继续只被各宿主引用，不出现「标准专用产品表」除非未来真有标准独有扩展实体。

## 风险

- Recycle 与固废 UI 条件缠在一起 → 拆漏会导致 Recycle 编译引用固废或运行缺详情页。  
- 旧 `MaterialClient` 安装已含固废数据（`WeighingMode=1` 行）：标准新 exe **应能只读忽略或只展示非固废**；不要内核 DROP。固废新客户端读同一文件或现场换装策略需在 OpenSpec 写清。  
- `UrbanMode` 与 `SolidWaste` Description 撞车 → 安装/授权文案在固废 change 里一并改 Urban 枚举说明（小，但是产品事故点）。

## 本调研不覆盖

- UrbanManagement / BasePlatform 服务端拆分  
- 是否为固废新建扩展表（可第二切片）  
- 未要求则不做存量 AttendedWeighing 大重构（技术债务规则）
