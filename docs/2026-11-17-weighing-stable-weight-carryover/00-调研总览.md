# 00 调研总览 — 稳定重量串到下一单

> 生命周期：`ACTIVE`  
> 研究状态：源码与现场日志已对齐；**未**授权改产品行为。  
> 类型：代码考古 + 现场日志 walkthrough（非 BMAD / 非 OpenSpec change）

## 1. 现象

有人值守称重日志里，上一车判稳写入的吨数，会在下一车上磅（甚至已 OffScale）之后，再落成**另一张** `WeighingRecord`，车牌常变成下一车或晚到的 LockedAt 牌。看起来像「重量传给下一单」。

样本：`_tmp/1117/MaterialClient-20261117.log`（2026-11-17 晨间约 07:41–08:34，记录 ID 19262–19281）。

## 2. 范围

| 要做（本夹） | 不做 |
|--------------|------|
| 用日志证明串重 / 双建单 | 改 `repos/MaterialClient` |
| 对齐 `AttendedWeighingService` 建单与异步队列 | 新建 OpenSpec change（需另开） |
| 说明「闭包旧重量」与音响为何拖到称重 | 修现场音响设备本身 |

## 3. 结论

| # | 结论 | 状态 |
|---|------|------|
| C1 | 不是地磅活读数串车；是入队时闭包的上一车 `StableWeight` 迟到建单 | `CONFIRMED`（日志 + 源码） |
| C2 | 同一次 `WaitingForStability → WeightStabilized` 会同时走 status-transition 与 backup，各 `Enqueue` 一次 `OnWeightStabilizedAsync`（因当时 `recordId` 仍为 null） | `CONFIRMED` |
| C3 | `CreateWeighingRecordAsync` **未**实现 spec「`recordId` 已非 null 则不得再建」；第二次照样 `Insert` | `CONFIRMED` |
| C4 | 异步流为 `Merge(maxConcurrent: 5)`；状态播报 `PlayTextV2Async` 与建单/抓拍共享并发槽 | `CONFIRMED` |
| C5 | 现场音响 `192.168.6.122:8888` 连不上时，单次播报最多 8 次、HTTP Timeout 约 30s，长时间占槽，把第二次建单拖到下磅甚至下一车 | `CONFIRMED`（本日志） |
| C6 | OffScale → `RewriteAndResetCycleAsync` → `ResetCycle()` 清空 `recordId`；迟到建单更易套上当前 LockedAt 车牌 | `CONFIRMED` |
| C7 | 本日志至少 6 组同吨双单（如 6.095 / 8.815 / 6.16 / 7.56 / 11.66 / 5.975）；第二单前无新的 `Weight stabilized (status transition)` | `CONFIRMED`（本日志） |
| C8 | 修复方向候选：去掉同帧 backup 双入队、建单入口补 `recordId` 守卫、音响移出称重关键队列或快速失败、`ResetCycle` 作废在途建单令牌 | `INFERRED`（未实现、未批准） |
