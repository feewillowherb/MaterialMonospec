# 03 异步队列与音响

> 回答两个常见误解：「闭包旧重量」是什么；音响为何能拖住称重建单。

## 1. 「闭包旧重量」是什么

不是秤上残留了上一车的物理读数，而是**任务入队时把当时的 `decimal` 捏进 lambda**。

| 时刻 | 发生什么 |
|------|----------|
| T0 判稳 | `weightToUse = 8.815`，入队 `() => OnWeightStabilizedAsync(8.815)` |
| T1 下磅 / 下一车上磅 | 地磅活读数已是 0.5t 或别的车 |
| T2 任务才执行 | 建单仍写 **8.815**，因为参数早已固定 |

所以叫「闭包里的旧重量」：闭包 = 捕获了入队时的变量值；旧 = 相对执行时刻已过期。

## 2. 音响是不是独立线程？

音响的 HTTP 调用跑在线程池 Task 上，**但调度上与建单共享同一条异步操作流**，不是「业务上互不影响的独立通道」。

`AttendedWeighingService.StartAsync`：

- `Subject<Func<Task>>` + `Select(FromAsync).Merge(maxConcurrent: 5)`
- 状态变化时：`Enqueue(OnWeightStabilizedAsync)` **与** `Enqueue(PlayTextV2Async)` 进**同一个** Subject

含义：

- 最多 5 个操作并行；
- 播报、抓拍、建单、ResetCycle、道闸策略侧效应都抢这 5 个槽；
- 某一个 `PlayTextV2Async` 在内部同步重试时，**一直占着一个槽**直到 8 次结束。

## 3. 现场音响如何放大问题

`SoundDeviceService.PlayTextV2Async`：

- 直连设备 HTTP，`Timeout = TimeSpan.FromSeconds(30)`；
- `maxRetries = 8`；
- 连不上时单次播报可阻塞约数分钟量级。

本日志设备：`192.168.6.122:8888` 大量 `SocketException 10060`。  
连续过车会叠多条「上磅 / 称重已结束 / 下磅」播报，更容易把 `Merge(5)` 占满。

日志指纹：`Audio playback ultimately failed` 后立刻 `Starting capture ... (WeightStabilized)` → 第二次建单刚拿到槽位。

## 4. 与「串重」的合奏

```text
判稳 → 入队建单#1 + 播报 + 建单#2(同闭包吨数)
     → 建单#1 落库，设 recordId
     → 播报重试占槽（及前车残留播报）
     → 车下磅，ResetCycle 清 recordId
     → 下一车上磅 / 新牌 LockedAt
     → 建单#2 终于跑：Insert(旧吨数, 新牌)
```

即使把音响修通，**双入队 + 无防重**仍可在抓拍偏慢时打出近时双单；音响失败主要负责把第二单拖到「下一车窗口」，让现象像串车。
