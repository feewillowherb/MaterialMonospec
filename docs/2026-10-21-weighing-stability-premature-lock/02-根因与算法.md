# 02 — 根因与算法

## 稳定判定公式（现行）

核心逻辑在两处**同源复制**（改一处时须同步另一处）：

1. `WeighingStreamPipeline.CreateStabilityStream` — 驱动状态 `WaitingForStability` → `WeightStabilized`
2. `AttendedWeighingService` 内联 `stabilityStream` — 提供建单用的 `StableWeight`

伪代码：

```text
buffer = rawScaleSamples over last StabilityWindowMs
         (emit every StabilityCheckIntervalMs)

valid = buffer where w > MinWeightThreshold
minRequired = max(8, floor(StabilityWindowMs / StabilityCheckIntervalMs * 0.5))
            # 默认 3000/200 → max(8, 7.5) = 8

range = max(valid) - min(valid)
IsStable = (valid.Count >= minRequired)
        && (range <= WeightStabilityThreshold * 2)

StableWeight = IsStable ? (min+max)/2 : null
```

默认现场：`minRequired=8`，允许 `range≤0.1t`。

## 为何「窗口 3000ms」却能 ~0.8s 锁重

### 误解

| 常见理解 | 实际行为 |
|----------|----------|
| 必须等满 3000ms 才判稳 | **否**。3000ms 是滑动**回看**窗长度 |
| 每 200ms 一个样本、凑满 15 点≈3s | **否**。Buffer 吃的是**串口高频原始点**，50ms 一跳也能很快凑满 8 点 |
| `×0.5` 表示半窗时间 | 只降低**点数**门槛，与「必须半窗时间」不等价 |

### 正确时间线（管道已运行）

`Buffer(windowMs, skipMs)` 在**长运行**进程里每 200ms 吐出「最近 3000ms 内全部原始点」：

1. 重量刚过 0.5 → 进入 `WaitingForStability`
2. 爬升中出现 0.54~0.55 短平台，串口密集报数
3. 约 8 个有效点、极差 ~0.01t → `IsStable=true`
4. 建单取 `StableWeight≈0.545`，随即 `WaitingForDeparture`

新鲜订阅时，首个 Buffer 要等满约一个 `windowMs` 才关闭；现场 Urban 已启动数分钟，故表现为亚秒级锁重（单测需先 warmup，见 `03`）。

## 与产品期望的差距

| 维度 | 现行 | 期望（2026-10-21 确认） |
|------|------|-------------------------|
| 最短等待 | 无（点数门槛） | 必须凑满 `window/interval` **全部周期**（默认 15≈3s） |
| 采样 | 原始高频点 | 宜先按 `StabilityCheckIntervalMs` **降采样**再滑窗 |
| 窗口内无效点 | 只计 `>MinWeightThreshold` 的点 | 期望「所有窗口期」均有效（升中途低点应打断） |

仅把 `×0.5` 改成 `×1.0` **不够**：高频下 15 个原始点仍可在亚秒内到达。

## 建单后为何不更新

`AttendedWeighingService.OnWeightAndStatusChanged`：一旦 `WaitingForStability` → `WeightStabilized` 且尚无 `recordId`，立即 `OnWeightStabilizedAsync(StableWeight)`。记录写入后状态强制 `WaitingForDeparture`，后续重量爬到 1.05t **不会改写本笔**。
