# Recycle 重构的代码质量建议

日期：2026-11-17。知识状态：INFERRED；生命周期：ACTIVE。

## 范围与依据

需求权威仍在 [Recycle resource alignment Topic](../2026-11-16-materialclient-recycle-resource-alignment/00-调研总览.md) 和对应 OpenSpec；本篇只评审客户端代码设计。Cursor 正在推进实现，下面是重构参考，不把工作区中尚未出现的实现判为缺陷，也不改变原有产品决策。

已读需求明确：Recycle 未发布，无旧版兼容需求；客户端采集毛重、车牌、现场照片，上传我方平台；皮重、净重、合同和业务表单由 Web 承担。可参考 [客户端目标说明](../2026-11-16-materialclient-recycle-resource-alignment/02-recycle客户端重构.md)。

本轮读取的是当前工作区中的 `MaterialClient.Recycle/MaterialClientRecycleModule.cs` 与 `.csproj`。Module 仍可见 RecycleSync、HMAC Handler、市接口 Refit 注册，因此这些只作为旧结构参考，不代表正在开发分支的最终结果。

## 1. 借鉴边界，避免照搬 Urban 全部结构

Urban 可以提供采集、照片上传、离线队列的行为参考；不要因此让 Recycle 依赖 Urban 可执行项目、Urban 专属实体或产品码。共享硬件与采集基础设施，产品接收 DTO、配置和上传适配保留各自归属。先识别真正相同的代码，再抽取公共部分，避免复制整个宿主或用源码链接依赖另一个 exe 内部文件。

## 2. 未发布产品应明确删除旧业务链

新路径确定后，客户端的市平台 HMAC、直连接口、合同/供应商/材料必填与旧业务同步注册应一起退出实际调用链。只隐藏控件而保留后台旧任务，会使产品职责仍然混杂。无需照搬固废为了存量库而形成的旧属性与扩展表双写结构；无兼容要求不等于可以擅自删除真实数据，具体库结构与数据处置仍按 change 范围执行。

## 3. 本地数据以采集事实和上传状态为中心

客户端保存毛重、车牌、采集时间、照片引用与上传状态；不要为了复用旧 Waybill 流程伪造皮重、净重、合同或材料。是否继续使用公共 WeighingRecord，要根据其不变量是否适合单次采集决定，而不是按类型名决定。

需要明确：哪些字段是不可变采集事实，哪些允许人工更正；平台补全后的业务数据是否真的需要回写客户端。没有实际读取需求时不增加第二份业务权威。

## 4. 上传模型要能表达重试与重复请求

候选方向：每次采集生成稳定标识，重试沿用该标识；第一跳协议明确单位，避免吨/千克口径隐含在调用链里。附件上传成功、记录提交成功和平台业务补全属于不同状态，不能用一个模糊 Success 同时表示。

网络调用放在本地采集事务之后，由上传服务处理；不要让设备回调等待远端，也不要在网络调用期间持有数据库事务。远端是否支持幂等必须与平台契约共同确认，不能由客户端单方保证。

## 5. 采集流程与产品同步各自负责自己的状态

公共采集层负责设备事件到本地记录的生命周期，Recycle 上传模块负责发送与重试。避免公共 WeighingMatchingService 继续增加 Recycle 合同字段或市平台分支。

重点审视一次采集周期是否有明确身份与状态转换：重复稳定回调、车辆离磅、异步操作完成较晚时，不能让上周期状态污染下一周期。这里是审查方向，不是认定本轮 Recycle 已存在同样缺陷。

## 6. 宿主组合要完整且身份一致

当前 Recycle Module 已注册公共 Refit 客户端，可参考这一点避免固废宿主曾遗漏的授权依赖。产品码 5020、模式 301、上传目标、配置段与数据目录应在启动时形成一致的产品上下文；避免不同服务分别推断当前产品。

界面通过 Service 访问数据；纯映射采用类型归属方法或静态方法，不新建 Mapper Service，不为纯逻辑增加 DI。产品扩展使用逻辑 ID，不增加跨 Context 外键。

## 给 Cursor 的审查顺序

1. 先看依赖图：Recycle 是否还依赖 Urban exe、客户端市接口或旧业务表单链。
2. 再看数据权威：是否新增重复字段、虚构必填值或无必要回写。
3. 再看生命周期：采集、落库、照片、上传的状态由谁维护，异步边界是否清楚。
4. 最后看宿主组合：产品身份、配置、HTTP 客户端与后台任务是否一致。

本篇不包含测试、安装、发布或 Capability 验收结论，不自动扩大 Cursor 当前 change 的范围。后续针对实际 diff 的评审应记录提交 SHA，再把建议更新为有源码证据的具体发现。
