# 02 固废称重极端工况设计

状态为 PENDING_VALIDATION。实验目标是验证重车和轻车分别识别到同一车辆时，测试地磅积压是否影响落库和配单。历史 run 继续作为单次识别反例。

## 工况矩阵

| 工况 | 输入时序 | 可验证结果 |
| --- | --- | --- |
| A 按节拍对照 | 重车前识别，等待重车落库并完成离磅，轻车前再次识别同一车牌，再完成轻车和最后离磅 | 两条正确称重记录关联同一张新固废运单。若失败，先调查基线，暂停将差异归因于积压。 |
| B 积压配单（主实验） | 重车前识别。连续提交重车 12.50 t、离磅 0.20 t、轻车 1.37 t、离磅 0.20 t。轻车周期开始且重车周期清理完成后、轻车稳定前，再识别同一车牌 | 四档在诊断端被接收，且有队列积压证据。最终先重后轻，各一条，两条属于不同周期、车牌相同、模式为 1，并关联唯一一张本次新固废运单。 |
| C 缺失轻车识别 | 重复 B 的重量输入，只在重车前识别 | 轻车保持未识别，不继承重车缓存，不产生该车的自动配单。历史 run 提供了这一形态的证据。 |
| D 车牌隔离 | 重复 B，第二周期注入另一辆车的唯一车牌 | 两条记录分别保留各自车牌，不跨车误配。执行前确认匹配配置及没有可配的历史记录。 |

## B 的执行与观测

1. 使用独占的 SolidWaste 测试宿主，确认称重窗已启动、收料、测试地磅模式以及离磅重量低于当前上磅阈值。记录宿主版本、配置摘要、数据库记录 ID 基线和日志游标。每组使用新车牌。
2. 在四档入队前注入重车车牌。重量请求连续发送，避免在其中插入查库、状态轮询或识别等待。并行观察诊断信号。
3. 第二次识别以三个可关联的条件为门槛：第一周期的异步清理已完成、已进入轻车周期且周期 ID 已更新、该周期尚未进入重量稳定。需要记录车牌事件实际被轻车周期接纳的证据。HTTP 200 只说明请求成功返回。
4. 用队列深度，或每档关联 ID 的入队、出队时间，确认爆发期间至少有待消费档位。若只有 HTTP 返回时新增称重行为零，记录这一代理指标，队列积压仍待证实。
5. 在最后一档消费完成、轻车离磅和匹配处理完成后，按基线查询 SQLite，核对记录数、主键顺序、两档重量（沿用 0.05 t 容差）、车牌、模式、WaybillId 和新运单的存在性。保留最终快照，观察有无延迟重复写入。排序使用记录 ID，周期关联使用产品日志或诊断事件。

### 当前观测能力

检查了桌面诊断入口与状态代码。已有重量和车牌 POST，称重日志能看到进入 WaitingForStability 的周期 ID。离磅日志之后才异步调度 RewriteAndResetCycleAsync，因此看到 OffScale 日志时还无法确认旧周期已清理。主实验优先检查现有日志是否提供可关联的重置完成、车牌接纳和队列消费信号。如果缺信号，后续可在测试诊断路径补只读结构化事件，或在隔离的 .NET 实验宿主使用可控事件源。固定延迟可用于探索窗口，正式 P2 需要记录上述时序。 [桌面诊断入口](../../repos/MaterialClient/src/MaterialClient.Desktop.Hosting/Services/MinimalWebHostService.cs#L40) · [称重状态切换](../../repos/MaterialClient/src/MaterialClient.Common/Services/AttendedWeighing/AttendedWeighingService.cs#L497)

## 判定

- **P0** 验证宿主前置、基线和观测能力。
- **P1** 验证四档请求被接收、积压形成、两次车牌输入的时序及接纳均有证据。诊断信号缺失或第二次车牌错过窗口，记录 blocked / INCONCLUSIVE。
- **P2** 在 P1 已满足后按每组结果判定。主实验中的缺行、重复、错序、串牌或未配单均为失败。场景先各跑一次，对照通过后主实验用三个独立车牌复验，逐次保留 HTTP、时序、SQL 快照及证据清单。
- **P3** 由用户判定。相机超时、数据库锁和进程重启留给独立工况，分别保留各自的触发与证据。

设计依据为 [车牌锁定规范](../../openspec/specs/plate-number-locking/spec.md#L46)、[按节拍对照](../../pipelines/graphs/materialclient/fev-solidwaste-weigh-lpr/pipeline.md#L48) 和 [现有实验](01-FEV-极端工况.md)。
